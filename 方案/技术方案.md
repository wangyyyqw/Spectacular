## 1. 目标与边界

### 1.1 目标

| 项 | 目标 |
|---|---|
| 平台 | iOS、Android 首发；包结构预留 Windows/macOS |
| 渲染 | 自研排版引擎，`TextPainter` 测量 + `Canvas` 绘制，无 WebView |
| 书籍类型 | 中文小说为主；含表格、图文混排、诗歌、引用框；含 ruby、竖排、内嵌字体 |
| 形态 | 分页阅读（一期），上下滚动（二期） |
| 能力 | 书库、目录、进度、书签、高亮笔记、字体主题、字号边距设置 |
| 定位 | 可上架产品 |

### 1.2 明确不做

- EPUB3 脚本内容、音视频、媒体叠加
- 固定版式（`rendition:layout` 非 reflowable）→ 全书单一路径
- 双栏 / `columns`
- DRM（Adobe ADEPT / LCP）
- CFI 与外部阅读器互通（一期只做内部自洽；CFI 结构对齐标准，便于后期开放）

## 2. 参考实现结论

工作区 `参考/` 有 5 个工程和一份对「阅微 2.3.2 beta」的静态分析。结论：

| 工程 | 渲染方式 | 无 WebView | 分页 |
|---|---|---|---|
| katbook_epub_reader | `html` 解析 → 原生 Widget；`TextPainter` 预测量装页 | 是 | 有（按段装页 + `PageView`） |
| epub_viewer_pro | `epubx` + `flutter_widget_from_html` | 是 | 无（流式滚动） |
| anx-reader | `flutter_inappwebview` + 本地服务 + foliate-js | **否** | 有（JS 侧 paginator） |
| flutter_readium | Readium Navigator（Kotlin/Swift），内部 WebView + JS 排版 | **否**（Flutter 侧是原生视图，渲染仍在 WebView） | 原生 |
| 阅微（反编译） | 自研 Kotlin 排版引擎 + Compose 测量与自绘 | 是 | 自研 CFI 分页 |
| Reeden 2.0.0（逆向） | Flutter/Dart 自研排版引擎（Echo* 一族），与本项目同栈（TextPainter/Canvas） | 是 | 自研分页 + 二进制页索引（RPI2） |

**取阅微的架构**：它是唯一在移动端做到「HTML/CSS → 排版树 → 行级分页 → 自绘」且无脚本引擎的完整实现。只借架构与算法，不复制代码。

**Reeden 的角色（v1.4）**：`参考/reeden/` 是对商业阅读器 Reeden 2.0.0（build 781，「全新排版引擎」内测版）的完整静态逆向，51 份报告（`参考/reeden/reports/`）。它与本项目同栈（Flutter + 自绘），提供的是**规格级素材**：UA 样式表 134 规则、三层缓存二进制 schema、断行与标点行为文档、设置失效矩阵、性能预算总表。接入纪律三条：

1. **骨架不变**：架构与算法仍以阅微 + 本项目实验结论为准（S4 引擎断行、主 isolate 分帧让出、CFI 唯一坐标均不因 Reeden 改向）；
2. **只补空档**：Reeden 素材用于阅微未覆盖、本项目尚无实测数据的领域（标点三件套、缓存序列化格式、失效矩阵、UA 表细节、诊断码体系）；
3. **标注来源**：引用一律给出报告路径并区分〔实测〕/〔建议〕；Reeden 与本项目冲突的做法（无 CFI、isolate 池排版、整段最优断行、搜索无索引）只作对照记录，不采纳为方案——分级清单见 §82.7。

> 上表的“无 WebView”指正文渲染是否依赖 WebView。`flutter_readium` 的 Flutter 层虽是原生 `PlatformView`，但 Readium Navigator 内部仍用 WebView 排版，因此不算无 WebView 路线。

## 3. 总体架构

```
导入层   解包 → OPF/spine/NCX/nav → 资源索引 → 字体解混淆（产物落缓存目录）
解析层   html 包解析 XHTML → 文档树 → 规范化为 EpubNode 树
样式层   csslib 解析 → 规则表 → 选择器匹配 → 层叠 → 继承 → ComputedStyle
布局层   BoxConstraints/占位 → 块流 → 文本行分割 → 分页游标 → PageSlice
绘制层   PageRenderCache → Canvas 逐页绘制
交互层   命中测试 → CFI → 选区 / 高亮 / 跳转
业务层   书库、进度、目录、书签、笔记、设置
```

## 4. 数据模型

### 4.1 结构与位置

```dart
class BookMeta {
  final String title, author, language, identifier; // identifier 用于字体解混淆密钥
  final String opfPath;
  final List<SpineItem> spine;
  final List<TocEntry> toc;          // NCX 优先，退 NAV
  final Map<String, String> manifest; // id → href
  final Map<String, String> guide;
}

class SpineItem {
  final int index;
  final String idref, href, mediaType;
  final bool linear;
  final bool isNavigation;
}

/// 标准 EPUB CFI 结构：spine/itemref/body/steps/offset/sideBias
class EpubCfi implements Comparable<EpubCfi> {
  final int spine;
  final int? itemref;
  final int? textNodeIndex;          // 文本节点序号
  final List<CfiStep> steps;         // /2/4、[id]、:7
  final int? characterOffset;
  final SideBias sideBias;           // before / after
  EpubCfi copyWithSideBias(SideBias);
  bool isBefore(EpubCfi other);
}
```

CFI 是整个定位系统的唯一坐标：页范围、目录跳转、书签、高亮、笔记全部存 CFI。**不存页码**，页码是重排后的派生量。

> 本节是结构速览。`EpubCfi` 的**权威定义**在 §81.2（含 `!` 间接、范围形式、`CfiSide`）；上面这段早期简化版（`textNodeIndex`）已作废。

### 4.3 文档树

```dart
sealed class EpubNode {}

class BlockNode extends EpubNode {          // ContainerDom
  final ComputedStyle style;
  final EpubCfi cfi;
  final List<EpubNode> children;
}

class TextBlockNode extends EpubNode {      // ContentDom
  final ComputedStyle style;
  final EpubCfi cfi;
  final String text;                        // 规范化后的文本
  final List<TextRun> runs;                 // 样式区间
  final Map<int, RubyAnnotation> ruby;      // 键：基字起始偏移
  final Map<int, EmphasisMark> emphasis;
  final Map<int, ImagePlaceholder> placeholders; // 行内图片/内联块
  bool continuesAfter;                      // 该块是否跨页续接
}

class TableNode extends EpubNode {          // TableDom
  final ComputedStyle style;
  final List<TableRow> rows;
}

class ImageNode extends EpubNode {          // 块级图片

  final String resourceHref;
  ImageSize? intrinsic;                     // 解码后回填

```

`TextRun` 保存 `start/end + TextStyle`；`ComputedStyle` 是**一次算完**的不可变对象，布局阶段不再回查 CSS。

## 5. 导入层

### 5.1 流程

```
选择文件 → 复制到书库目录（保留原始文件，不再修改）
  → 解包到 cache/<bookId>/（保留目录结构）
  → 读 META-INF/container.xml → rootfile → OPF
  → 解析 metadata / manifest / spine / guide / NCX 或 NAV
  → 建立资源索引（href 规范化 + 大小写容错）
  → 字体解混淆（如需要，产物写到 cache/<bookId>/_fonts/）
```

### 5.2 与阅微的关键差异：不改写原书

阅微在导入时**原地改写** XHTML（`HtmlOptimizer`：把 body 下裸文本包成 `p`、处理段首全角空格与空段、重写脚注链接）并重写 OPF。

我们不这么做：

| 问题 | 阅微做法 | 我们的做法 |
|---|---|---|
| 裸文本节点 | 回写 `<p>` | 解析期在内存里当隐式段落处理 |
| 段首全角空格 | 回写删除 | 解析期标记 `preserveIndent`，排版时按书内 `text-indent` 决定 |
| 空段落 | 回写删除 | 排版期跳过零高度块 |
| 脚注链接 | 回写 DOM 结构与 id | 点击时按 `href` 解析同文档锚点 → 弹层显示目标块，不改 DOM |
| 资源引用大小写 | 回写 OPF/XHTML | 资源索引做大小写不敏感查找，命中即用 |

理由：可逆、可重复导入、可与原文件对拍、出错不污染书库。代价是解析层要多处理几种不规范结构，这部分工作量已经计入 M2。

### 5.3 字体解混淆

阅微只做**检测**（渲染样本比对 + 写 `.font-obfuscated` 标记），不解密。我们实现真实解密：

- IDPF：前 1040 字节与 `SHA-1(identifier 去除空白)` 循环 XOR
- Adobe：前 1024 字节与 UUID 密钥做 RC4

密钥来自 OPF `unique-identifier` 指向的 metadata 值。解混淆产物写缓存，不改原文件。失败则字体回退并记警告。

## 6. 定位系统

### 6.1 CFI 需要的操作

```dart
EpubCfi parse(String cfi);
String  serialize(EpubCfi cfi);
int     compare(EpubCfi a, EpubCfi b);      // 全序，用于页范围与选区
EpubCfi collapseToTextNode(EpubCfi cfi);    // 命中测试结果归一到文本节点
int     offsetInNode(EpubCfi cfi);          // 取字符偏移
```

CFI 与文档树的对应关系在解析期建立：每个 `EpubNode` 持有创建它的 `EpubCfi`（步骤链 + 文本节点序号）。分页产出页范围时只做 `copyWithSideBias`，不重新解析字符串。

### 6.2 与 DOM 失效的关系

书内样式导致重排时，CFI 依赖的是"第几个元素/第几个文本节点/第几个字符"，与像素无关，因此**字号、边距、字体变化后 CFI 依然有效**。这正是选它做唯一坐标的原因。

## 7. 样式层

### 7.1 解析

用 `csslib` 得到语法树，转成 `CssRule` 列表（阅微里叫 `RuleSet`，见 §52）：

- 选择器：tag / `.class` / `#id` / 后代 / 子 / 属性 / 结构伪类（`:first-child` 等）
- 不支持即丢弃：`@media`、`@supports`、`@layer`、`@keyframes`、`:hover` 等交互伪类
- `@import` 按规范插在当前位置，限制递归深度 8，带 visited 集合防环
- `@font-face` 单独收集，交给字体子系统

### 7.2 层叠

特异性用标准四元组 `(inline, id, class, type)`，逐位比较。合并顺序：

```
UA 默认表
  → 作者样式普通规则（按特异性升序）
  → 作者样式 !important
  → HTML 属性映射（width/height/align/valign/hspace/font 等）
  → style 属性
  → 阅读器覆盖层（用户设置，最高优先级）
```

上面这一条是**独立判断**，与阅微不同：阅微用简化分数（`.a.b` 与 `.a` 都是 10）、同规则内 `!important` 会被后声明覆盖、`@import` 顺序颠倒。这些都是可确认的缺陷，不继承。

### 7.3 继承与计算值

- 可继承属性：`color`、`font-*`、`line-height`、`letter-spacing`、`text-align`、`text-indent`、`writing-mode`、`white-space`、`list-style-type`、`text-emphasis-*`、`ruby-align`
- 单位换算：`em` 相对当前字号，`rem` 相对根字号，`%` 相对父值，`vw/vh` 相对视口；`pt/pc/in/cm/mm` 按 96dpi 折算；`calc` 只支持二元加减乘除
- 自定义属性：从父样式继承 `var(--x, fallback)`，替换上限 32 次
- 计算产物 `ComputedStyle` 不可变，所有值已经是逻辑像素或比例

### 7.4 UA 默认表

沿用阅微的关键项（`UserAgentStylesheet`）：`body { display:block; width:100%; font-size:1em !important }`，`h1..h6` 的字号与 margin，`table` 的 inset 边框，`p` 的段落间距，`img` 的块级化默认。

`body` 上那条 `!important` 是有意为之：正文基准字号必须锚定阅读设置，不能被书内 `body{font-size:0.8em}` 拉走。

> **Reeden 对照（v1.4）**：Reeden 的 UA 表有 134 条规则、逐条注明规范出处，并与浏览器刻意保留了 6 处差异（标题 `break-after:avoid` 避页底、`sub/sup` 借行距、ruby 注音 `text-indent` 归零、列表嵌套类型、`noscript` 隐藏、表单控件静态尺寸）。完整规格见 §2.2 / 630 号报告，扩充落地为 P7-03。

### 7.5 阅读器覆盖层

书内样式算完后依次应用，顺序固定：

1. 字号基准（用户设置 → 根字号）
2. 行高下限（书内低于设置值时抬起）
3. 段间距与段首缩进（正缩进的 `p` 归一，按设置重算）
4. 全局字距、全局粗体
5. 深色模式颜色替换：亮度 ≤ 0.179 的不透明色替换为主题色，保留 alpha
6. 页边距（合并进 body 的内边距）

### 7.6 字体选择

```
书内 @font-face（若用户允许内嵌字体）
  → 用户选定字体
  → 平台默认中文字体
```

按字符脚本分段套用（`applyScriptFontFallback` 的等价实现）：CJK 段用中文字体，拉丁段与符号段用正文西文字体，避免中文全角符号被西文字体排成异形。

## 8. 布局层

### 8.1 约束与占位（浮动核心）

照搬 `BoxConstraints` 的模型：

```dart
class LayoutConstraints {
  final double containerWidth;
  final double contentWidth;
  final List<Occupied> occupiedList;   // 高度区间 + 左右被占宽度
  bool get isOccupied;
  ({LayoutConstraints next, List<PlaceholderNode> placeholders})
      createPlaceholders(double currentY, EpubCfi location);
}
```

每排一块内容前，按当前 y 调用 `createPlaceholders`：把该 y 以下被浮动挤掉的左右空间变成占位节点插入流中，同时返回收窄后的约束。正文行自然绕排，不需要单独的行内浮动逻辑。

浮动的进入与清除（`float` / `clear`）在同一处维护 `occupiedList`，元素退出时移除对应区间。

### 8.2 文本行分割

`TextBlockNode` 首次测量时构建：

```dart
class TextLayout {
  final List<LineBox> lines;
  final double height;
}
class LineBox {
  final int start, end;        // 字符区间（半开）
  final double top, baseline, height, width;
}
```

Flutter 侧实现要点：

1. 用 `TextPainter` 按可用宽度 layout 一次
2. `computeLineMetrics()` 拿到行数、行高、baseline、行宽
3. 行边界字符索引用 `getLineBoundary(TextPosition)` 逐行取
4. 行高取该行最大 `fontSize × lineHeight`，半行距按 CSS 规则分配到 baseline 上下

**不采用逐字 `getOffsetForCaret` 作为主路径**（1200 次/页的 API 调用风险高），只在两处使用：段落内起点偏移换算、竖排逐字定位。

### 8.3 分页器

状态：`beginCfi`、`movedCfi`、`unusedHeight`、`textBuffer`、`pages`。

```
measureChapter(spineIndex):
  windowHeight = 内容区高度
  unusedHeight = windowHeight + 边界补偿 - 首页顶部留白
  for (block, i) in body.children:
      await onMeasure(block, windowHeight, prev: children[i-1])
      if (i % 20 == 0) await yield()        // 让出主线程
  收尾：若末页非空则记录
  return pages

onMeasure(block, pageHeight, prev):
  if block.pageBreakBefore: recordPage(movedCfi, pageHeight)
  switch block:
    TextBlock:
       如果整块高度 ≤ unusedHeight → 整块收进，unusedHeight -= 高度
       否则：
         lastFit = 满足 lineBottom(i) + 2px ≤ unusedHeight 的最大行号
         若没有整行放得下 → recordPage 后在新页重排该块
         否则：
           lineEnd = lines[lastFit+1].start
           前段 → 本页；尾段 → 游标带回，下一轮继续
           对前段单独做对齐
    Image:  高度超过剩余 → recordPage；超过整页 → 等比缩到页高
    Table:  逐行推进，行放不下 → 在行间 recordPage（跨页行用 rowSpan 跳过已画行）
  if block.pageBreakAfter: recordPage(block.endCfi, pageHeight)

recordPage(cfi, pageHeight):
  if cfi == beginCfi: return false          // 不产生零长度页
  pages.add(EpubPage(beginCfi, cfi+bias, textBuffer))
  textBuffer.clear(); beginCfi = cfi; unusedHeight = pageHeight
```

与阅微一致的两处细节：只有第一页扣顶部留白；`2px` 容差防止浮点误差把刚好放下的行挤到下一页。

### 8.4 中文两端对齐

条件：`text-align: justify` 且该行含 CJK 且不是硬换行结尾。

```
extra = 行可用宽 - 行实际宽
gaps  = 该行可分配间隙的索引（见下）
ls    = extra / gaps.length
for i in gaps:
    // 只给“间隙左侧字符”加一个单字符 SpanStyle
    span[i].letterSpacing = 原有 letterSpacing + ls
```

间隙规则：

1. 取相邻字符 `(i, i+1)` 之间；
2. 跳过含换行的间隙；
3. 跳过两侧都是拉丁字母/数字的间隙（不拆英文单词内部）；
4. 纯中文 20 字 → 19 个 gap；中英混排按第 3 条扣除；
5. 末字之后不设 gap，因此不会在右缘留下一个多余 `ls`。

末行不拉伸（除非书内显式 `text-justify: distribute`）。西文仍走“拉伸词间空格”，不给西文词内加字距。

对比：阅微的 `adaptiveJustify` 就是这套做法——`cjkJustifyGapIndices` 取间隙，`ls = extra / gaps.size`，再给每个间隙左侧字符加单字符 `SpanStyle`（并保留原 `letterSpacing`）。我们采纳算法，但不采纳它的 `isCjk` 范围判断（见 §16 与参考代码备注）。

> **S3 实测（2026-10-22，`方案/spike/s3-result.md`）**：20 个全角字、目标宽 320/336/400 三组，整行 `ls = extra / 20` 时测量宽误差 0、字框无重叠；**`TextAlign.justify` 单独对纯中文不拉伸**（320 目标下仍是 320），必须手工实现。补充对比显示：整行方案会在末字后多留一个 `ls`（本实验 0.8px / 4px），gap 方案把间距只落在字符之间，末字起点更靠右；纯中文 gap 数 19，中英混排样本 9。逐字 caret 间距有取整波动，断言用“总宽误差 + 字框不重叠”，不要要求 caret 等距。

> **Reeden 对照（v1.4）**：Reeden 在 gap 对齐之外补齐了中文精排的「标点三件套」——悬挂（行尾句读挂到版心外）、挤压（相邻标点挤掉整格空白）、空格整理（半角标点转全角、白名单豁免数字与符号、不改换行），四件套（含中西文间距）均为独立开关且书内 CSS 优先；另解析 `text-justify` 四值与 `text-align-last`。行为文案与证据见 §2.2 / 150 号报告；落地为 P7-18～P7-21。

### 8.5 表格

两遍测量：

1. 第一遍：按内容自然宽度测每列，得到列宽候选
2. 第二遍：`table` 宽度既定则按列宽比例分配，否则按 `width` 属性/内容取最大
3. 逐行测每格高度，行高取行内最大
4. 行放不下时切页；跨页行按 `RowSpan` 记录已绘制高度并跳过

`colspan` 支持；`rowspan` 二期（阅微支持但有已知边界）。

### 8.6 图片

- 解码用 `instantiateImageCodec(targetWidth:)` 按目标显示宽度降采样，避免大图占内存
- 尺寸：书内 `width`/`height` 优先，`auto` 用原始比例，超出容器等比缩
- 块级图片高于整页：等比缩到页高
- 图页判定（阅微的 `isFullScreen`）：章节只有一张无宽高属性的图片时走满屏路径，边距归零

## 9. 绘制层

### 9.1 一页的绘制顺序

```
1. 页背景
2. 逐块：
   平移（margin 起点）→ box-shadow → transform(rotate/translate)
   → 背景（纯色 → 图片 → 渐变，多层按 CSS 顺序）
   → 边框（四边、圆角；solid/dashed/dotted/double）
   → 裁剪到 padding 区
   → 内容
3. 文本行：按 LineBox.baseline 定位，逐 run 绘制
4. 装饰层：ruby、着重号、文字阴影、下划线/删除线
```

### 9.2 行绘制与缓存

每页首次绘制时构建 `PageRenderCache`：

```dart
class LineRender {
  final List<ui.Paragraph> paragraphs;  // 每 run 一个段落，内容是该 run 在本行的子串
  final List<Offset> offsets;
}
```

- 子串已经确定，段落用 `maxWidth: infinity` layout，保证单行不折行
- 缓存挂在 `PageSlice` 上，翻回来直接复用，不重建
- 内存控制：只保留当前页 ±2 页的渲染缓存

### 9.3 竖排

Flutter 无原生竖排，逐字处理：

1. 字符沿垂直方向排，行沿水平方向从右到左
2. 标点旋转表：`。，、；：？！（）「」『』` 等，按字符映射旋转 90° 或替换竖排字形
3. 拉丁字母与数字成组保持正向，组内不旋转
4. ruby 移到基字右侧
5. 竖排下 `text-indent` / `line-height` / `letter-spacing` 的轴向互换

验收范围：常见中文竖排可读。不做日文拗音小字、组合括号旋转、竖排西文精修。

## 11. 缓存与性能预算

### 11.1 缓存

| 层 | 键 | 上限 |
|---|---|---|
| CSS 规则表 | 内容 hash（见 52.4） | 2048 条，按 bookId 分区 |
| 计算样式 | (节点身份, 视口 hash, 设置 hash) | 按章生命周期 |
| 章节分页结果 | (spineIndex, 视口, 设置 hash) | 当前章 ±2 章 |
| 页渲染缓存 | 页对象引用 | 当前页 ±2 页 |
| 图片位图 | (href, 显示宽, DPR) | 按字节封顶（如 64MB），LRU —— 见 50.6 |
| 图片尺寸 / 透明标记 | href | 512 / 128 条，LRU —— 见 50.6 |
| 字体 | family + 字重 | 全局 |

设置变化（字号/边距/字体/行高/段距）→ 清排版与页缓存，保留图片与字体缓存。

> **Reeden 对照（v1.4）**：Reeden 把缓存分为 {document, styles, pagination} 三层，键=「影响该层的最小变量集」，并有 21 行「设置→失效层→是否重定位→是否可增量」矩阵（字号只失效 styles+pagination、主题/配色零失效、几何与字体全失效）；分页结果序列化为 5 字段二进制页索引（RPI2）落盘复用。见 §2.2 / 550、650 号报告；分层与失效矩阵落地为 P7-22、P7-23、P7-29。

### 11.2 预算

| 指标 | 目标 |
|---|---|
| 冷启动进书首屏 | < 1s（先显示已缓存的首章，排版在后台推进） |
| 翻页 | < 16ms（命中缓存路径） |
| 首次排版一章（30 页级） | < 400ms，分帧让出，可中断 |
| 峰值内存 | 单本 < 200MB |

P7-10 增补（完整三要素与采集方式见 [P7-性能指标表](验收记录/P7-性能指标表.md)，对照 Reeden 570 号总表）：

| 指标 | 目标 |
|---|---|
| 章节首排（万章书单章 2KB 级） | < 600ms，可中断 |
| 跨章跳转到可交互 | < 300ms（本地零网络等待） |

### 11.3 让出策略

分页在**主 isolate**跑（`TextPainter` 依赖引擎字体集合，不能进 isolate）。做法与阅微一致：每处理约 20 个顶层块让出一次，让 UI 保持可响应；排版结果按页增量产出，已完成的页立即可翻。

## 12. 容错

| 情况 | 处理 |
|---|---|
| container.xml / OPF 缺失 | 判定为无效 EPUB，提示并拒绝导入 |
| spine 项指向不存在的文件 | 跳过该项，目录中标记为不可用 |
| NCX 存在但损坏 | **回退到 EPUB3 NAV**（阅微此处直接返回空目录，是缺陷） |
| CSS 解析失败 | 该文件整体忽略，其余样式继续 |
| 字体文件损坏/不支持 | 回退字体，记录警告，不中断阅读 |
| 图片解码失败 | 占位框 + alt 文本 |
| 单章内容超大（> 2MB 文本） | 分段解析，先出前若干页 |
| 无效 CFI（损坏的进度记录） | 回退到章首 |

上表是**运行时**的降级行为。**导入期**的修复与五级可读性判定另见 §54、§55——两者不要混在一起写，否则会出现两套互相矛盾的处理说明。

## 15. 风险与验证 Spike

方案里有五处不能只靠推理，M0 必须做实验。其中 **S4 优先级最高**，它决定整个测量路径走"引擎断行"还是"自建断行"（见 19、24）。**每个实验的可执行步骤、记录字段与判定方法见 §79**。

| Spike | 问题 | 通过标准 | 不通过的后备 |
|---|---|---|---|
| S4 | Flutter 文本引擎是否支持中文避头尾禁则 | 19.1 的 10 个场景中禁则相关 5 项全部符合 | 自建断行器 + 逐字定位，工作量约 +1200 行 |
| S5 | `FontLoader` 同 family 多字重能否按 `fontWeight` 正确选中 | 同一 family 加载 regular + bold 后，700 字重渲染出粗体 | 按字重拆成不同 family 名，样式层加一层映射（见 28.2） |
| S1 | `TextPainter` 行边界与行高能否稳定复现 CSS 行高模型 | 三本样本行数/行高与预期一致，误差 < 0.5px | 自建行高与 baseline 计算，只用 `TextPainter` 取行宽 |
| S2 | 逐行构建 `ui.Paragraph` 并缓存，一页 30～90 个段落的构建耗时 | 单页构建 < 8ms，翻页命中缓存 < 4ms | 合并为整页单段落，改用 `TextPainter.paint` 整块绘制 |
| S3 | `letterSpacing` 方案做 CJK 两端对齐的视觉精度 | 行宽误差 < 1px，无字符重叠 | 逐字自绘，用 `getOffsetForCaret` 取 x |

上表五项会**改变实现路径**，所以叫 Spike。另有 **S6（SQLite 是否启用 FTS5）** 与 **S7（`instantiateImageCodec` 的 targetWidth 是否生效）** 是两个低成本确认项——它们不改主路径，只决定某个存储实现或优化是否成立，做法见 §79.6。

**S4 已实测（2026-10-22）**：引擎禁则基本成立，唯一例外是 `「……」` 在 2em 窄宽下被拆；严格判定不通过，工程上采用引擎断行 + 3em 宽度下限。数据与取舍见 `方案/spike/s4-result.md` 与 §79.7。

**S1 / S3 已实测（2026-10-22）**：S1 通过，但必须设 `leadingDistribution: even`，否则基线最大偏差 4.745px；S3 通过，采用“按 gap 分配 + 单字符 span”，三组目标宽误差均为 0，`TextAlign.justify` 对纯中文不生效。分别见 `方案/spike/s1-result.md`、`方案/spike/s3-result.md`。

其他风险：

1. **竖排**：Flutter 零原生支持，逐字绘制 + 标点旋转，验收范围受限（见 9.3）。
2. **分页性能**：`TextPainter` 只能在主 isolate，长章首次排版会有可感知延迟，必须配进度提示。
3. **交叉场景**：浮动图跨页 + 表格跨页 + ruby 跨行同时出现时边界最多，容易出"缩进错位/行高跳动"。
4. **字体格式**：`ttc` / `woff` / `woff2` 不支持，精排版书可能回退。
5. **样式保真度上界**：这是书籍子集引擎，不是浏览器。必须对外明确"不保证像素级复刻出版社版式"。

## 17. 虚拟页窗口（分页与翻页组件的桥）

### 17.1 问题

分页按章产出：第 3 章有 17 页，第 4 章有 23 页。但翻页组件（`PageView` 类）需要**连续递增的页码**。直接把章内页号当页码会断号，且跳到未加载的章节时页码未知。

阅微的实际解法（`ReaderViewModel`）：维护一套**虚拟页号 ↔ 真实位置**的双向映射，按需向前后扩张窗口。

### 17.2 阅微的数据结构

| 字段 | 类型 | 作用 |
|---|---|---|
| `spinePagesCache` | `Map<Int, List<EpubPage>>` | 章 → 该章全部页 |
| `virtualToReal` | `Map<Int, Pair<Int,Int>>` | 虚拟页 → (spineIndex, 章内页号) |
| `realToVirtual` | `Map<Pair, Int>` | 反向 |
| `loadedSpines` | `Set<Int>` | 已完成分页的章 |
| `virtualPages` | `Map<Int, EpubPage>`  + `virtualPagesRevision` | 虚拟页 → 页对象 |
| `minLoadedSpine` / `maxLoadedSpine` | `Int` | 已映射的章区间 |
| `initialPagerPage` / `pagerMinPage` / `pagerMaxPage` | `Int` | 组件页码范围 |
| `pagerCorrection` | `SharedFlow` | 窗口扩张后的页码修正事件 |
| `virtualPageLoadMutex` | `Mutex` | 防止并发扩张 |
| `windowKey` / `appliedLayoutKey` | `String` | 布局指纹，变化即整窗重建 |
| `lastVisibleCfi` | `EpubCfi` | 重排/换章后恢复位置的锚点 |

关键方法：`ensureVirtualPageWindow(minPagesEachSide)`、`loadAroundVirtualPage`、`recenterVirtualWindow(targetCfi)`、`loadSpineForward/Backward`、`publishVirtualWindow`、`findVirtualPageForCfi(cfi)`、`countMappedPagesLeft/Right`。

### 17.3 Dart 设计

```dart
class VirtualPager {
  final Map<int, List<EpubPage>> spinePages = {};
  final Map<int, (int, int)> virtualToReal = {};   // 虚拟页 → (spine, 章内页)
  final Map<(int, int), int> realToVirtual = {};
  final Set<int> loadedSpines = {};
  final Map<int, EpubPage> virtualPages = {};

  int minLoadedSpine = 0, maxLoadedSpine = -1;
  int pagerMinPage = 0, pagerMaxPage = 0;
  int totalVirtualPages = 0;

  Future<void> ensureWindow(int centerPage, {int minEachSide = 3});
  Future<void> loadAround(int page);
  Future<void> recenter(EpubCfi target, {bool resetPage = false});
  Future<void> loadSpineForward();
  Future<void> loadSpineBackward();
  int? findVirtualPageForCfi(EpubCfi cfi);
}
```

### 17.4 规则

1. **保底**：当前页前后各 ≥3 页已映射，否则扩张
2. **扩张顺序**：先补当前章剩余页，再按 spine 顺序向前/后各加载一章
3. **末端页号**：`maxLoadedSpine` 之后还有未加载章时，`pagerMaxPage` 设为"当前已映射末页 +1"，翻到该页触发再扩张，并把页码修正事件推给组件
4. **驱逐**：超出窗口（当前章 ±2 章）的页对象释放，只保留章索引；重新进入时按 CFI 重定位，不依赖旧页码
5. **跳转**：`recenter(targetCfi)` 先找到目标章 → 分页该章 → 建立新的虚拟页基准 → 通知组件修正页码。过程中显示 loading，并用**自增 token** 丢弃过期结果（阅微的 `jumpLoadingToken` 做法）
6. **重排**：`windowKey`（视口 + 排版配置指纹）变化 → 清空全部映射 → 用 `lastVisibleCfi` 定位后重建

这一层是翻页体验的核心，M0 就要搭出来，否则后面接翻页动画会返工。

## 18. 行内装饰的数据结构

三类装饰都按"文本字符区间"挂载，绘制时叠加：

```dart
class RubyText {                    // 对应 TextRuby
  final String id;
  final String rt;                  // 注音文本
  final RubyAlign align;            // start / center / space-between / space-around
  final RubyAlign rowAlign;         // 多行注音时的行内对齐
  final ImageContents? image;       // 注音使用图片的少数情况
}

class EmphasisMark {                // 对应 TextEmphasisDisplay
  final String style;               // dot / circle / double-circle / triangle / sesame
  final bool filled;                // 实心 / 空心
  final Color color;
  final double size;                // 相对字号比例
  final bool under;                 // 位置：基字上方 / 下方
}

class InlinePlaceholder {           // 对应 ImagePlaceholder
  final String id, path, name;
  final double width, height;       // 已按约束算好的尺寸
  final double x, y;                // SVG 用例
  final String? viewBox, fill;      // SVG
  final bool preserveAspectRatio;
}
```

两个要点：

- **位图与 SVG 统一成 placeholder**。SVG 走 `viewBox/fill/preserveAspectRatio` 的矢量路径绘制，位图走解码图片；对排版层只暴露宽高。
- 装饰不影响行宽（ruby 与强调号都是覆盖绘制），唯一的例外是**行内图片**，它参与行内流并影响换行。

## 19. 断行与中文禁则（未定项，需实验）

阅微**没有自己实现断行**，它把文本交给 Compose 的文本引擎（Android 上是 StaticLayout），中文避头尾由平台处理。这条路在 Flutter 上不能照搬——`TextPainter` 的断行由引擎 line breaker 决定，**中文禁则行为不能假定与浏览器或 Android 一致**。

这是方案里唯一一处"底层能力不确定"的地方，必须实测。

### 19.1 验收用的 10 个场景

| # | 场景 | 期望 |
|---|---|---|
| 1 | 行首不出现 `，。、；：？！` | 发生前移 |
| 2 | 行首不出现 `）」』】》` | 发生前移 |
| 3 | 行尾不出现 `（「『【《` | 发生后移 |
| 4 | 长串 `「……」` 在窄宽度下的处理 | 不出现空行首 |
| 5 | 数字 `2026` 不被拆开 | 保持整体 |
| 6 | 英文单词跨行 | 按词断开，不拆字母 |
| 7 | 中英混排 | 中文单字可断，西文按词 |
| 8 | 省略号 `……` | 不拆成 `…` + `…` |
| 9 | 破折号 `——` | 允许断在其后 |
| 10 | `word-break` 未设置时的长西文词 | 溢出或强断（记录实际行为） |

### 19.2 两种结果与对应方案

**若引擎支持禁则**：直接用 `TextPainter` 断行，行边界从 `computeLineMetrics` + `getLineBoundary` 取。方案其余部分不变。

**若引擎不支持**：需要自建断行器，此时**测量路径整体切换**为逐字：

```
预处理：文本切 cluster（CJK 单字 / 西文词 / 数字串 / 标点）
贪心：按宽度累积 cluster，宽度来自逐字测量缓存
禁则：若断点前是行首禁则字符 → 把前一个 cluster 一起下移
      若断点后是行尾禁则字符 → 把该字符一起上移
产出：LineBox 列表，与引擎无关
```

逐字宽度获取方式：

```
run 整段 layout 一次
  → 逐字 getOffsetForCaret(TextPosition(i)) 取 x
  → 差值即 advance，缓存 (styleKey, cluster) → advance
```

**代价**：自建断行意味着不能用 `TextPainter` 的折行结果，所有行都要自己算位置，绘制也要逐 run 定位。好处是禁则、竖排、精确对齐全部可控，且与桌面端行为一致。

### 19.3 决策点

S4 实验结论直接决定 S2/S3 的路线：

- 引擎支持禁则 → 走"引擎断行 + 逐行段落缓存"，实现量小
- 引擎不支持 → 走"自建断行 + 逐字定位"，实现量大但上限高

**实测结论（2026-10-22，见 `方案/spike/s4-result.md`）**：走引擎断行。`TextPainter` 在行首禁标点、行首禁后括号/后引号、行尾禁前括号/前引号、数字串、破折号上均符合；唯一例外是 `「……」` 在恰好 2 字宽时省略号对被拆开（≥3 字宽正常）。按严格口径 S4 记为不通过，但该失败属于极端窄宽，采用“引擎断行 + 正文宽度 ≥3em”兜底，不引入自建断行器。

> **Reeden 对照（v1.4）**：Reeden 的断行是「贪心为默认 + 整段最优断行（Knuth-Plass 类）可选项」，禁则走 `line-break: strict`（D22：句读/闭口符不落行首、开口符不落行尾、作者写了 line-break 就照书），见 §2.2 / 150、510 号报告。本项目 S4 已实测定案引擎断行，**维持不变**；D22 场景清单用于复核 3em 兜底的覆盖面（P7-07），整段最优断行仅记录不排期。

## 20. 翻页动画

阅微有四种，组件层独立于排版：

| 类型 | 实现 | 成本 |
|---|---|---|
| StaticPager | 无动画直接换页 | 最低 |
| OverlayPager | 新页覆盖 + 位移 + 边缘阴影 | 低 |
| CurlPager | 卷曲仿真，**先用 bitmap snapshot 抓当前页**再对图片做形变（`CurlPager_androidKt.captureBitmap`，Android 侧有 `LibraryPageCurlView`） | 高 |
| ScrollPager | 纵向滚动，另走 `readElements` 元素流 | 中 |

我们的规划：

- **一期**：Overlay + Static 两种，够用且可控
- **二期**：滚动（需要元素级测量器，与分页器分离）
- **可选**：卷曲仿真。关键技巧是**把页截图成 `ui.Image` 再变形**，不对文本做逐字变换，成本可控

Flutter 实现要点：

- 不用 `PageView`：它会预建相邻页 widget，且无法精细控制拖拽位移
- 自己实现：`GestureDetector` 横向拖拽 → `AnimationController` → 当前页 `Transform.translate` + 下一页 `Transform.translate` + 左边缘渐变阴影
- 页面用 `RepaintBoundary` 包裹，卷曲时 `toImage()` 取位图

## 21. 设置变更与重排链路

### 21.1 布局指纹

排版结果只对一组固定参数有效，指纹化后才谈缓存：

```
windowKey = viewport(width, height, dpr, 安全区)
          + ReaderConfig(
              textSize, lineHeight, paragraphSpacing, letterSpacing,
              padding, family, embeddedFonts, buildInFonts, boldFont)
```

阅微的 `ReaderEpubConfig` 字段就是这一组：`textSize`、`lineHeight`、`paragraphSpacing`、`letterSpacing`、`padding`、`family`、`embeddedFonts`、`bookEmbeddedFonts`、`buildInFonts`、`globalEmbeddedFonts`、`boldFont`。

### 21.2 变更处理

```
设置变化
  → 新 windowKey 与 appliedLayoutKey 比较
  → 不同：记录 lastVisibleCfi
        → 清 排版缓存 + 页缓存 + 虚拟页映射
        → 若字体变化：重载字体 + 清字体缓存
        → 重新分页当前章 → recenter 到 lastVisibleCfi
  → 相同：忽略
```

**位置恢复一律走 CFI，不走页码**。页码在重排后必然失效，CFI 不会。

### 21.3 标注变更的代价

阅微有 `remeasureAfterTagMutation`——标注（内联概念卡、脚注气泡）会占位并改变文本宽度，因此**必须重排该章**。

我们的策略：一期标注只允许不占位的视觉样式（背景色、下划线、波浪线），不插入任何行内元素，标注变更只触发重绘不触发重排。需要显示图标时改用行尾标记，把重排限制在单章并给出可感知的延迟保护。

## 22. 目录、进度与跳转

### 22.1 目录

目录项只存 CFI（阅微 `BookChapter` 带 `spineCfiIndex`）：

```
NCX navPoint → 解析 src + fragment → 转 CFI
NAV doc（EPUB3）→ 解析 href → 转 CFI
无 fragment → 该章起始 CFI
```

CFI → 目录项用二分查找（目录 CFI 天然升序）。当前章高亮 = 二分找到 ≤ 当前 CFI 的最后一项。

### 22.2 跳章

```
目标 = chapters[currentIndex + step]
→ pager.recenter(target.cfi)
→ recenter 内部：定位章 → 分页 → 建映射 → 推送页码修正
```

### 22.3 进度

两种算法，取舍不同：

| 算法 | 优点 | 缺点 |
|---|---|---|
| 字符偏移 / 全书字符总数 | 与分页无关，重排后不变，最稳定 | 需要导入时预扫全书字符，多一次 IO |
| 已映射页数 / 估算总页数 | 无需预扫 | 未加载章只能估算，进度条会跳变 |

**选字符偏移比例**。导入时顺序扫描各 XHTML 的文本长度（不做完整解析，只累计文本节点长度），得到每章字符区间；进度 = (章前累计字符 + 章内偏移) / 全书字符。这个值在字号变化、不同设备间都稳定，也便于和外部系统对齐。

## 25. 书壳页与脚注

### 25.1 书壳页

阅微把封面与后壳也当成"页"参与翻页序列：`EpubPage.contentType` 取 `CONTENT=0` / `BACK_COVER=1` / `COVER=2`，组件层另有 `EpubCoverPageKt`、`BookBackCoverPageKt`。

我们的设计：

```
虚拟页序列 = [封面页] + 正文页 + [后壳页]
封面页：由 OPF cover-image 或 guide 的 cover 引用生成，单独渲染（等比缩放铺满，不参与排版）
后壳页：可选，固定高度，承载"已读完"提示
```

两点注意：

- 封面不计入正文进度（`percentage` 计算时排除），否则进度条起点不在 0
- 封面页不进入 `spinePagesCache`，单独走一个渲染分支，避免污染分页逻辑

### 25.2 脚注

阅微的做法：在 `<a>` 元素上用自定义属性承载脚注内容，常量 `Attr.WR_FOOTER_NOTE = "data-wr-footernote"`（`org/epub/html/Attr.java:19`），阅读期由 `ContentDom` 读取（`:1021`、`:1126`、`:1148`），再用 `CommentTooltipKt`（约 1.1 万行）做浮层。

**属性由谁写入，未在反编译产物中找到**——`HtmlOptimizer` 里有脚注相关的 `optimizeA`／`resolveFootnoteItemContainer`／`backRefId` 方法，但直接写入该属性的代码落在 47 处未恢复方法中，因此只能记为"导入期处理脚注时的推断"，不能当作已确认事实。这也提醒一点：**阅微的脚注依赖导入期改写原书**，改坏或改不到就失效。

我们的做法（运行期解析，不改书）：

```
点击 <a href="#fn1">
  → 解析为同文档锚点
  → 在当前章的文档树里按 id 找目标节点（找不到再回退到 href 指向的其他文档）
  → 取该节点子树，现场排版成一个受限尺寸的块
  → 底部弹层渲染（可滚动，最大高度占屏 60%）
  → 弹层内的链接仍可跳转，跳转后关闭弹层
```

跨文档脚注（`href="../text/ch02.xhtml#fn1"`）需要先解析目标文档并分页该章，成本较高，一期改为"跳转到目标位置"而不是弹层。

### 25.3 与脚注相关的两个坑

1. **脚注编号样式**：`<sup><a>[1]</a></sup>` 的行内上标会抬高行高。排版时上标字号缩小但 line-box 仍按最大字号算，容易出现"某行行距突然变大"。解决：`vertical-align: super/sub` 只改变绘制偏移，不参与行高计算——这一条要写进布局层的规则里。**（已解决，P7-09：上下标墨迹只借已有行距，越出行盒才撑高——借行距判定见 `line_breaker.dart` `_applyBorrowedLeading`，对照 Reeden 630 号 §2-3 / fixups N5；用例 `test/layout/borrow_leading_test.dart`。）**
2. **往返位置**：从脚注返回正文必须回到原页原位置。用 `returnPositionCfi` 记录点击点，弹层关闭时若已跨页则 `recenter` 回去（阅微的 `captureReturnPosition` / `returnToOriginalPosition`）。

## 26. 表格跨页

### 26.1 阅微的 RowSpan 模型

`org/epub/html/RowSpan.java` 的字段：

```java
class RowSpan {
  ContainerDom dom;   // 跨行单元格
  int trIndex;        // 原始行号
  int span;           // 跨越行数
  int row;            // 当前所在行（可变，跨页时更新）
  float height;       // 已累计高度
  void setRow(int);
}
```

`row` 是可变字段，这是整个设计的关键：表格在行边界切页后，跨行单元格要在下一页**续绘**，续绘时把 `row` 指到新页的首行，`height` 继续累加。

### 26.2 分页时的表格处理

```
表格先行测量：rows[i].height + cell 行列归属
逐行推进累计高度：
  若 rows[i].height > unusedHeight
     → 在行边界 recordPage
     → 本页只保留前 i 行
     → 下一页从第 i 行继续
  跨行单元格（rowspan 覆盖切点）：
     → 在下一页重新登记 RowSpan(span 剩余, row = 0, height = 0)
     → 绘制时只画落在本页行区间内的片段
```

### 26.3 我们的设计

```dart
class TableSplitState {
  final List<double> rowHeights;
  final List<SpanningCell> spanning;   // {trIndex, span, startRow, heightAccum}
  int firstVisibleRow;                 // 本页从第几行开始
  int lastVisibleRow;
}
```

三件事必须一起做对，否则会出现"表格错行"：

1. **行高一致性**：切页后每页的列宽必须与首屏一致（列宽由整表测量决定，不能每页重算）
2. **跨行单元格续绘**：`firstVisibleRow` 在 span 内的单元格，绘制时裁掉已画部分
3. **边框连续性**：`border-collapse` 下相邻行的边框不重复绘制；切页后页首行要补上顶边

### 26.4 可选优化：重复表头

电子书表格跨页时重复 `thead` 是常见需求。阅微是否有此行为**未验证**（报告未涉及）。我们列为 P1 优化：若表存在 `thead` 且表格被分页切断，在后续每页顶部重复绘制表头，并相应减少可用高度。

## 27. 首屏与跳转的加载体验

### 27.1 阅微的加载状态

`ReaderJumpLoadingState { token: Long, title: String }`，配套 `jumpLoading` / `jumpLoadingToken` / `showJumpLoadingIfNeeded` / `clearJumpLoading`，UI 侧是 `ReaderJumpLoadingOverlay`。

两个设计点值得照搬：

- **token 防竞态**：每次跳转递增 token，任务完成时比对，与当前 token 不符就直接丢弃结果。用户连续点两次目录时不会出现"后到的旧结果覆盖新位置"
- **title 随状态走**：浮层能显示"正在打开 第三章"，而不是一个裸转圈

### 27.2 我们的设计

```
打开书
  ├─ 有上次退出位置的缓存页 → 立即渲染（<100ms）
  └─ 无缓存 → 渲染章首骨架（背景 + 行高占位）+ 排版进度条
              → 分片任务推进，每完成一页可翻一页
              → 全书排版完成后进度条消失

跳章 / 跳进度
  → 全屏浮层（目标章名 + 不确定进度转圈）
  → recenter(targetCfi)
  → 完成后淡入（150ms），失败回退章首并提示
```

### 27.3 排版任务的可取消设计

```dart
class PagedChapterJob {
  final int spineIndex;
  final CancelToken token;
  double get progress;        // 已排字节 / 总字节，用于进度显示
  Stream<EpubPage> get pages; // 增量产出
  void cancel();
}
```

切换章节、改字号、退出阅读都要能取消。取消后已产出的页保留（改字号除外），避免重复劳动。

## 28. 字体注册与回退

### 28.1 阅微的实现

`FontProvider` 的结构：

| 成员 | 作用 |
|---|---|
| `fonts: HashMap<String, HashMap<FontWeight, Font>>` | family → 字重 → 字体 |
| `coverage: HashMap<String, FontCoverage>` | 每个 family 的字形覆盖信息 |
| `embeddedPaths` / `embeddedFamily` | 已加载的内嵌字体 |
| `glyphCoverage: HashMap<String, Boolean>` | 码点覆盖缓存 |
| `attach(path, ruleSets)` | 解析 `@font-face` 并注册 |
| `embeddedHasGlyph(codePoint)` | 单字符覆盖检测（cmap 查表） |
| `clearEmbeddedFonts()` | 切书/改设置时清理 |

中文别名硬编码两组：宋体 `{宋体, ST, SONGTI}`、楷体 `{楷体, KT, KAITI, STKaiti}`。中文书的 `font-family: 宋体` 靠这个映射落到内置字体，否则会一路回退。

它还有 `builtInSerifFamily(einkBoldOnly)` —— 墨水屏模式下只提供粗体字族以提升对比度。

**已知缺陷（不继承）**：`@font-face` 的 `font-weight` 只认字符串 `bold`，其他值一律当 `Normal`（报告 F12）。而正文 `font-weight` 支持数字。结果就是"书里声明了 700 字重的内嵌粗体，实际用了常规体"。

### 28.2 Flutter 侧的关键差异（新增待验证项）

Compose 可以直接构造一个带字重的 `Font` 对象注册到 family。Flutter 的 `FontLoader` **以 family 为单位加载字节**，字重不是由我们声明的，而是由字体文件自身的 OS/2 表决定。

两种可能，取决于引擎行为：

- 引擎读字体自带字重 → 同一 family 下加载 regular + bold 两个文件即可，`TextStyle(fontWeight:)` 自动选
- 引擎不读 → 必须按字重拆成不同 family 名（`BookBody-Regular`、`BookBody-Bold`），在样式计算阶段按 `font-weight` 选 family

这条进 M0 的 S5 实验，不通过就走拆名字的方案（多一层样式映射，成本可控）。

### 28.3 回退链

```
书内 @font-face family（用户允许内嵌字体时）
  → 用户选定字体
  → 中文别名映射（宋体/楷体 → 内置字族）
  → 系统中文字体
  → 平台默认
```

`fontFamilyFallback` 按段指定字族优于整段回退：CJK 段走中文字族，拉丁与符号段走西文字族，避免中文全角标点被西文字体排成异形。

注意：阅微的 `applyScriptFontFallback` 实际是**逐字查字形覆盖**（`embeddedHasGlyph`）来决定字族，不是按 Unicode 区块切分。Flutter 拿不到 cmap，我们改用区块分段 + fallback 兜底，详见 §77。

### 28.4 字形覆盖检测

阅微能查 cmap，Flutter 不暴露字形表。**不做逐字覆盖检测**，改为：

- 字体文件解析阶段只校验格式（magic number + 表目录是否可读）
- 运行期遇到缺字由 `fontFamilyFallback` 兜底
- 记录"加载失败"与"格式不支持"两类警告，供用户排查

## 29. 全文搜索

### 29.1 参考情况

阅微反编译产物里**没有找到书内全文搜索实现**（只有 `BookRepository.searchByCloud` 这个云端书城搜索）。这一块没有可抄的，需要自己设计。

### 29.2 索引

导入时顺带做，与进度所需的字符统计合并成一次扫描：

```
for each spine item:
  解析 XHTML → 抽纯文本（跳过 script/style/nav）
  记录：文本内容 + 每章字符数 + 文本偏移 → 节点路径 的映射表
写入 SQLite：
  chapter_text(book_id, spine_index, text, char_start)      -- 表结构见 §66.3
  search_grams(gram, spine_index, char_offset, book_id)     -- 2-gram 倒排，见 §66.3
```

中文不需要分词，直接用 **2-gram**：把文本切成相邻二字组合建倒排，查询时同样切分，天然支持任意子串匹配，代价是索引体积约为原文的 2 倍。

**FTS5 只是存储选项**：SQLite 编译启用 FTS5 时可把倒排装进去省掉手写索引，未启用则用普通表 + 索引，两者功能等价。M0 需要实测 `sqlite3_flutter_libs` 的编译选项，但结论不影响设计（§66.7）。

### 29.3 命中转位置

搜索命中一段文本后要跳到正确位置，需要把"文本偏移"换回 CFI：

```
命中 (spineIndex, charOffset)
  → 查导入时保存的"文本偏移 → 节点路径"映射
  → 找到包含该偏移的文本节点与其内部偏移
  → 组装 CFI
```

映射表可以按节点存区间（`nodeStart, nodeLen, nodePath`），导入时一次生成，体积很小（每节点一条）。

### 29.4 结果展示

- 列表项：章名 + 命中上下文（前 12 字 + 命中 + 后 12 字），命中词高亮
- 点击 → `recenter(cfi)` → 目标页淡入后把命中范围用临时高亮标出（3 秒后消失）
- 搜索在导入完成后进行，跨全书；大书（500 万字）需要分页返回结果并支持中断

### 29.5 取舍

| 方案 | 索引成本 | 查询速度 | 中文效果 |
|---|---|---|---|
| SQLite FTS5 + 2-gram | 中 | 快 | 好 |
| 自建内存倒排 | 高（常驻内存） | 最快 | 好 |
| 逐章子串扫描 | 零索引 | 慢（全书 ~1s 级） | 好 |

**选 2-gram 倒排表**（SQL 见 §66.3）。若 SQLite 编译启用了 FTS5，则把倒排放进 FTS5 以省掉手写索引；未启用时直接用普通表 + 索引，功能等价。逐章子串扫描只作为最后兜底。

换句话说：**2-gram 是方案，FTS5 只是它的一种存储实现**，不是并列的两个选项。

## 30. 标注、选区与跨页重定位

### 30.1 阅微的模型

```java
// 选区载荷：两个 CFI 字符串 + 原文引用
class EpubSelectionPayload { String startCfi; String endCfi; String quote; }

// CFI 范围：三个 CFI
class EpubCFIRange { EpubCFI anchor; EpubCFI start; EpubCFI endExclusive; }
```

`ReaderViewModel` 的标注入口：`upsertHighlight(selection, style, color)`、`upsertIdea(note, privateVisible)`、`deleteMarkBySelection(kind)`、`upsertTag`、`upsertPresetTag`、`clearPresetTag`。

**`quote` 字段是整个设计的要点**：存 CFI 之外还存一份原文。作用有两个——高亮列表里显示摘录，以及 **CFI 失效时的兜底重定位**（书被替换、CFI 解析失败、不同版本间迁移）。

`anchor` 的存在说明它按标准 CFI 范围结构实现（`epubcfi(parent,start,end)` 形式），而不是简单存两个点。

### 30.2 我们的数据模型

```dart
class Annotation {
  final String id;
  final int bookId;
  final AnnotationType type;      // highlight / note / bookmark
  final String startCfi, endCfi;
  final String quote;             // 兜底重定位 + 列表展示
  final String? before, after;    // 各约 20 字上下文，见下文补充第 1 条
  final HighlightStyle? style;    // 下划线 / 波浪线 / 背景 / 边框
  final Color? color;
  final String? note;
  final DateTime createdAt, updatedAt;
}
```

SQLite 单表存，`(book_id, type)` 建索引，`quote` 建普通索引供兜底搜索。

两处补充（采纳自 flutter_readium 的做法，见 §82.1）：

1. **存上下文而不只存 quote**：再加 `before` / `after` 各约 20 字。只有 quote 时，同一段文字在书里出现两次就分不清；带上下文能把误判率压下来。
2. **`active` 只是运行期状态，不入库**。点中某条高亮时它要浮起来以区别于其他高亮，这是渲染态，不是数据。运行期用 UI 状态里的 `activeAnnotationId` 表示，不给每条标注单独存布尔。

**硬规则：任何持久化数据都不许存页面坐标**。`epub_viewer_pro` 用 `(x, y)` 存笔迹与笔记（§82.2），字号一变、屏一转就飘到别的段落。我们自绘引擎有 CFI 与字符偏移，页面坐标只能出现在当前帧的渲染中间态。

### 30.2.1 标注类型扩展（若做笔迹）

若将来支持手写，存储仍是文本锚点 + 相对偏移：

```dart
class StrokeAnnotation extends Annotation {
  final List<(double dx, double dy)> points;  // 相对"锚点字符的墨迹框左上角"的偏移
}
```

**相对偏移，不是绝对坐标**。绑到字符锚点上，重排后笔画跟着那段文字走——虽然会变形，但不会跑到无关段落。

### 30.3 跨页与跨块选区

选区的起止点可以落在不同页、不同块，甚至不同章。处理顺序：

```
命中测试得到两个 TextHit(cfi, charOffset)
  → 归一到文档树节点（起点在节点 A 偏移 a，终点在节点 B 偏移 b）
  → 生成区间列表：[A(a..end), A 之后的块..., B(0..b)]
  → 每页渲染时取"该页可见块"与区间列表的交集
  → 每个交集按字形框生成若干矩形（跨行断开）
```

绘制时矩形按行切分，行内框高取字号的 1.1 倍，垂直偏移对齐字形墨迹而不是行框。

### 30.4 重排后的重定位

```
CFI 可解析 → 直接定位（字号、边距、字体变化都不影响 CFI）
CFI 解析失败 or 指向不存在节点
  → 用 quote 在当前章文本中搜索
  → 命中唯一 → 重建区间
  → 命中多个 → 取最靠近原章位置的那个
  → 未命中 → 标注标记为"失效"，列表里置灰但保留数据
```

**不删除失效标注**。用户换设备、换排版后标注全丢是最伤信任的失败模式。

> **Reeden 对照（v1.4）**：Reeden **无 CFI**，批注锚「章节序号 + 字符区间 + 章节名快照」，重排后靠 relocate 管线（verified/relocated/migrated 三态）与 Deep Repair（逐章全文搜索引文 + 候选消歧「全部选离原位置最近的」）修复，失败分五类（quote_not_found/ambiguous_quote 等）——这条修复链路的全部成本是本项目 CFI 决策的反面验证。可吸收的两点：① 上下文指纹消歧（重复文本场景）；② 「区间直查 → 指纹重映射 → 比例兜底」的三级解析顺序，并入本节兜底链（P7-14）。见 §2.2 / 250、560 号报告。

### 30.5 交互

- 长按进入选择模式，拖拽手柄扩展；点空白退出
- 选择浮出工具条：高亮（4 种样式）、笔记、复制、搜索、分享
- 点击已有高亮 → 弹出该标注的编辑/删除
- 笔记用底部弹层输入，保存后在高亮旁显示小图标

## 31. 主题与背景

### 31.1 阅微的结构

`ReaderThemesKt` 里有 `ReaderBackground` 与 `pickBackgroundLauncher`——**支持用户自选背景图**，不只纯色主题。

`EpubBackgroundState`：

```java
class EpubBackgroundState {
  String background;   // 背景资源标识（路径或内置名）
  Bitmap? bitmap;      // 解码后的位图缓存
  int visualVersion;   // 变更计数，驱动重绘
}
```

`visualVersion` 这个做法的意义：背景图解码是异步且昂贵的，用版本号判断"是否需要重绘"比逐帧比较字符串便宜。

深色适配规则（报告已确认）：非透明、已指定且亮度 ≤ 0.179 的颜色，替换为主题色并保留 alpha。

### 31.2 我们的设计

```dart
class ReaderTheme {
  final String id, name;
  final Color foreground, secondaryForeground, linkColor, selectionColor;
  final ThemeBackground background;      // solid(color) 或 image(asset/bytes)
  final bool isDark;
}

class BackgroundCache {
  final Map<String, ui.Image> _images = {};
  int visualVersion = 0;
  Future<ui.Image> resolve(String key, Size pageSize);
}
```

### 31.3 配对约束

背景可自定义，就必须约束前景否则读不了：

```
背景为纯色：直接用主题定义的前景色
背景为图片：解码后降采样到 8×8，算平均亮度
  亮度 < 0.35 → 强制浅色前景
  亮度 > 0.65 → 强制深色前景
  中间 → 用主题前景 + 文字描边/阴影兜底
```

书内颜色再叠加一层规则：

- 暗色主题下，书内 `color` 亮度 ≤ 0.179 的替换为主题前景色
- 书内显式的浅色（如白字标题配深色背景块）**不替换**，否则会把作者设计的对比关系破坏掉
- 半透明色一律保留 alpha

### 31.4 背景图的性能

- 图片按页面尺寸解码一次（`instantiateImageCodec(targetWidth:)`），缓存 `ui.Image`
- 背景单独一层，用 `RepaintBoundary` 隔离，翻页时不重绘背景
- 纹理类背景（纸张）平铺绘制，用 `ImageRepeat.repeat`，不做逐页裁切
- `visualVersion` 变化才重建背景层

## 32. 竖排实现细节

### 32.1 阅微竖排的真实范围（已复核）

三处代码构成全部实现：

| 位置 | 行为 |
|---|---|
| `WritingMode.java` | 只注册 `horizontal-tb` / `vertical-rl` / `vertical-lr` |
| `ContentDom:1433/1457` | 非横排时删空白字符，用 `\n` 把每字连起来 |
| `ContainerDom:1048` | 非横排走另一个宽度分支 |

全库检索 `rotation` / `Rotat`：只有 `CSSRotateKt`（CSS `transform:rotate`）、SVG 路径、圆角与边框弧线，**没有任何竖排标点旋转**。

结论：阅微的竖排是"每字一行"，没有列序、没有标点朝向、没有縦中横、ruby 位置也不对。**不能参考，必须自己做。**

### 32.2 几何

```
横排：行沿 y 增长，字沿 x 增长，行宽 = 可用宽，行高 = line-height × 字号
竖排：列沿 x 递减（vertical-rl 从右往左），字沿 y 增长
      列宽 = line-height × 字号
      字距 = 横排的行距概念（letter-spacing 作用于 y 方向）
      行距 = 横排的字距概念
```

所以竖排本质是横排的一次**坐标转置 + 方向翻转**。如果测量层已经能做到逐字定位，竖排的增量在于：转置映射、标点处理、列序、分页方向。

### 32.3 标点处理

CSS Writing Modes 规定：竖排下需要旋转的字符用旋转替代，有竖排字形（`vert` feature）时优先用字形。

一期只需要一张表：

| 类别 | 字符 | 处理 |
|---|---|---|
| 句读标点 | `。，、；：` | 旋转 90° |
| 问号叹号 | `？！` | 旋转 90° |
| 省略号 | `……` | **不旋转**，按其竖排位置居中对齐 |
| 破折号 | `——` | **不旋转**，纵向连接 |
| 括号引号 | `（）「」『』【】《》〈〉` | 优先取竖排字形，无则旋转 90° |
| 间隔号 | `·` `～` | 居中不旋转 |

括号旋转后位置需要偏移补偿（旋转的是墨迹框，不是外接框），这一步做不到位最容易被用户看出问题。

### 32.4 明确不做

- **縦中横（tate-chu-yoko）**：让 2 位数字横向躺在竖排列中。真实日文排版需要，中文竖排书籍很少见，一期不做，数字也逐字竖排
- 日文拗音小字、长音符旋转组合
- 竖排下的西文单词整体旋转 90°（CSS 有 `text-orientation: sideways`，我们不做）

### 32.5 分页与翻页方向

- `vertical-rl`：列从右到左，**翻页方向与横排相反**（下一章在左侧，手势向左滑回退）
- 页码计算沿列序推进，与横排的行序逻辑同构，只是主轴不同
- 目录、进度、翻页动画的方向要全部跟随 `writing-mode`，这是容易漏的一串改动

### 32.6 验收

5 本竖排样本，逐项检查：标点朝向、括号位置补偿、列序、段首缩进在列顶、ruby 在基字右侧、翻页方向、跨页续列。

## 33. SVG 与内联图形

### 33.1 阅微的做法

`SvgPathRendererKt`（约 4900 行）是**自己写的 SVG 路径渲染器**：`parseSvgPath` / `tokenizePathData` / `parseViewBox` / `calculateTransform` / `createArcSegments`（弧转贝塞尔）/ 描边样式。

原因不难理解：EPUB 里的 SVG 五花八门，通用库覆盖不全，而排版引擎只需要"按 viewBox 缩放把 path 画出来"这一小撮能力。

### 33.2 我们的选择

分三级降级，不要一上来自己写渲染器：

| 级别 | 方案 | 覆盖 |
|---|---|---|
| 1 | `vector_graphics` + `flutter_svg` | 常规 path / transform / fill / stroke |
| 2 | 自写极简 path 渲染（参考阅微的能力面） | 只做 `path` 的 M/L/C/Q/A/Z + transform + viewBox，约 500～800 行 |
| 3 | 占位框 + alt | 滤镜、mask、外部引用、SVG 内文本 |

触发级别 2 的条件很明确：`flutter_svg` 解析失败但 path 数据合法时降级到自己的渲染器。**不预先自研**。

### 33.3 两种进入方式

- `<img src="x.svg">` 与 `<image xlink:href="x.svg">`：走图片占位，按宽高参与排版
- CSS `background-image: url(x.svg)`：走背景绘制，不参与排版流

两者都必须支持，中文书的章节装饰、分隔线、花边常用第二种。

### 33.4 已知坑

- SVG 里带 `width/height` 属性时按属性，只有 `viewBox` 时按可用宽度等比
- `preserveAspectRatio="none"` 要拉伸，不能用等比
- 引用了外部字体或图片的 SVG 一律降级到级别 3

## 34. 导入流程

### 34.1 阅微的流水线与进度

`EpubFileManager.import()` 的完整步骤与进度点：

| 进度 | 步骤 |
|---|---|
| 0 | `Opf.obtain(unzipDir).overwrite()` 重写 container/OPF |
| 5 | `EpubFileExecutor.restoreObfuscated()` 恢复被混淆的资源名 |
| 20 | `EpubFileExecutor.normalizeResourceReferencesCase()` 统一引用大小写 |
| 40 → 90 | `HtmlOptimizer.execute()` 逐文档改写 XHTML，进度按文档数线性映射 `(i×50)/total + 40` |
| 90 | 再次 `Opf.overwrite()` |
| 95 | 移动到 `books/<metadata.uuid>/`，已存在则 `mergeTreeInto` |
| 100 | 完成 |

### 34.2 spine 过滤规则

```
guide 里 type 含 "cover" 的 reference → href 归一（去 #fragment、去 ./ 前缀）→ coverSet
遍历 spine itemref：
  找 manifest 同 id 项
  保留条件：itemref.linear == true  或  item.href ∈ coverSet
  丢弃：manifest 无此 id、文件不存在、isNavigationDocument()
  记录：BookItemRef(spineIndex = (i+1)*2, originalIndex = i, idref, href, properties, size)
```

`spineIndex` 统一取 `(i+1)×2`（2,4,6…），`i` 是 spine itemref 的原序（0 起）。它同时是 CFI 里 `/6/` 之后的 itemref 步进：`epubcfi(/6/<spineIndex>!/4/...)`。**不要再写成 `index * 2`**——那会得到 0,2,4，与 CFI 的偶数步约定错位。这个约定只在 CFI 构造处出现一次，其余层一律把它当普通章节键使用。

### 34.3 我们的差异

| 步骤 | 阅微 | 我们 |
|---|---|---|
| OPF 重写 | 改写磁盘文件 | 只在内存构建索引对象 |
| 资源名恢复 | 回写文件名 | 索引里建立"原名 ↔ 磁盘名"双向往查表 |
| 引用大小写规整 | 回写 XHTML | 索引查找时大小写不敏感，命中即用 |
| HTML 优化 | 回写 XHTML | 解析期在内存规范化（见 5.2） |
| 书写入 | 移动/合并到 books/ | 解包到 `books/<uuid>/content/`，原 epub 文件原样保存在 `books/<uuid>/source.epub` |

少掉三次全量回写，导入更快，也可重放。

### 34.4 导入进度模型

```dart
enum ImportStage { unpacking, parsingOpf, indexingResources, parsingSpine, toc, statistics, cover, done }
```

各阶段权重：解包 40%、OPF 与资源索引 10%、spine 解析 25%、目录 10%、字符统计 10%、封面 5%。字符统计必须在导入期做（见 22.3 的进度算法与 29.2 的搜索索引），能顺带产出搜索索引，两件事合并扫一次。

## 35. 目录构建

### 35.1 阅微的规则（含缺陷）

```
manifest 里找 isNcx() 的项
  ├─ 找到 → 读 XML
  │    ├─ 有 navPoint → findChaptersByEpubV2(navPoints)
  │    └─ 没有 navPoint → 返回空列表        ← 缺陷：不回退 nav
  └─ 没找到 → 找 properties 含 "nav" 或 id=="nav" 的项
       └─ 读 XML → findChaptersByEpubV3Nav
读 XML 失败 → 空列表
```

代码确认了报告 F14 描述的问题：**NCX 存在但损坏或没有 navPoint 时，直接返回空目录**，明明有可用的 `nav.xhtml` 也不会去看。

### 35.2 我们的回退链

```
1. NCX（navPoint 或 pageList）→ 解析成功且非空 → 采用
2. EPUB3 nav（properties 含 nav，或 id 含 nav）→ 解析 <nav epub:type="toc"> 的 <ol>/<li>
3. 两者都失败 → 退化目录：
     遍历 spine，每个文档取首个 h1..h6 文本作标题
     没有标题则取 <title> 或文件名
     层级统一为 1
4. 仍然为空 → 目录只显示"共 N 章"，按 spine 顺序编号
```

**绝不返回空目录**。目录为空是用户能立刻感知的失败，退化的扁平目录远好于没有。

### 35.3 目录项模型

```dart
class TocEntry {
  final int depth;          // 嵌套层级，1 起
  final String title;
  final String href;
  final EpubCfi? cfi;       // 解析期算出；fragment 缺失时取该文档起始 CFI
}
```

`depth` 决定目录 UI 的缩进，阅读时"当前章"高亮取最后一个 CFI ≤ 当前位置且 depth 最浅的项（避免高亮落在子节上）。

### 35.4 与章节的关系

目录项 ≠ spine 项。目录可以多个项指向同一文档的不同锚点，也可以跳过某些 spine 文档（如版权页）。

因此：

- `chapters` 表按目录项建（用于目录 UI 与跳转）
- `spine_items` 表按 spine 建（用于分页与虚拟页窗口）
- 两者通过 `cfi.itemref`（= `spineIndex`）关联

## 37. 书库与导入队列

### 37.1 导入队列

导入是重任务（解包 + 解析 + 统计 + 索引），必须排队：

```dart
class ImportQueue {
  final List<ImportJob> _jobs = [];
  int get concurrency => 1;                 // 串行，避免 IO 争抢
  Future<void> enqueue(List<String> paths);
}
```

- **并发 1**：解包与索引都是磁盘密集，并发只会更慢且更难报进度
- 失败重试：解包失败可重试 1 次；解析失败进 `failed` 状态并记录原因，不自动重试
- 取消：导入中删书要能中断并清理半成品目录
- 半成品目录标记：`.importing` 文件存在则视为未完成，启动时清理

### 37.2 书库状态

```dart
enum BookStatus { importing, ready, failed }
```

- `ready` 才能进阅读页
- `failed` 在书库卡片上显示错误原因与"重试"
- 导入中显示进度条百分比

### 37.3 封面

四级回退：

```
1. OPF cover-image（EPUB3 properties 含 cover-image）
2. guide 里 type 含 cover 的 reference 指向的 XHTML 首图
3. spine 第一个文档里的第一张图
4. 生成占位：书名首字 + 由 uuid 派生的稳定背景色
```

封面图统一裁成 2:3，缓存到 `books/<uuid>/cover.jpg`，避免每次列表解码原图。

### 37.4 删除

```
删书 = 删数据库行（级联删标注/进度/spine/chapters）+ 删 books/<uuid>/ 目录
```

先删数据库再删文件：如果删文件中途失败，留下孤儿目录，启动时扫描清理 orphans（数据库中不存在的 uuid 目录）。

## 38. 中英混排、简繁与文字方向

### 38.1 阅微的情况

- **没有简繁转换**：全库检索 `traditional / Simplified / t2s / s2t` 无结果
- **有按脚本的字体分段**：`ContentDom` 的 `applyScriptFontFallback` / `buildScriptRanges`，把文本按字符脚本切成区间，分别套字体
- 竖排只做了"每字一行"，没有任何朝向控制（见 32.1）

### 38.2 中英混排规则（我们需要的）

| 规则 | 做法 |
|---|---|
| 字体分段 | CJK 段 → 中文字族；拉丁与数字 → 正文西文字族；两者都缺 → 回退链 |
| 断行 | CJK 单字可断，拉丁按词断，数字串不断开 |
| 标点 | 中文标点必须由中文字体渲染，否则全角标点会被西文字体画成异形（这是分段的真正目的） |
| 空格 | 不在中西文之间自动插入空格，书里有什么就是什么（自动加空格会改变原文） |
| 字重 | 中西文同一 `font-weight`；西文字体没有对应字重时用最近字重 |

### 38.3 简繁

**不做转换**。理由：

- 转换需要 OpenCC 级别的映射表（数万条 + 词组消歧），引入它意味着一个新的数据依赖与一套新的错误面
- 转换会破坏标注的 `quote` 与搜索索引（原文变了）
- 用户想看繁体可以直接换字体（部分繁体字体含简繁两套字形），或用支持 `locl` 特性的字体

如果将来要做，形态应该是**渲染期的字形替换**而不是文本转换，这样索引与标注不受影响。列为不做清单之外的可选项。

### 38.4 文字方向

| 场景 | 处理 |
|---|---|
| 书内 `dir="rtl"` | 只影响块级对齐方向，不做双向文本重排 |
| 阿拉伯/希伯来文 | 交给 Flutter 的 bidi 算法（`TextPainter` 内置），我们不介入 |
| 竖排 | 见第 32 章 |
| 标点挤压 | 不做 |

这一块的定位是：**跟随引擎的 bidi 能力，不自己实现双向算法**。

## 39. 选区系统

### 39.1 阅微的完整 API 面

`BodyKt` 的元数据把整套选区能力暴露得很清楚：

| 方法 | 作用 |
|---|---|
| `toSelectionPosition(node, offset)` | 字符偏移 → 选区位置 |
| `orderedPositions(pair)` | 把起止点排好序，得到 `SelectionSnapshot` |
| `cfiAt(node, offset)` | 字符偏移 → CFI |
| `selectionText(node, range)` | 取出选中的文本 |
| `selectionLineRects(TextLayoutResult, TextRange)` | 选中范围 → 逐行矩形 |
| `handleVisualForRange(node, range, isStart)` | 手柄位置 |
| `handleVisualAt(node, offset)` | 按偏移取手柄 |
| `removeSelectionPlaceholders` | 选区内的占位（行内图片）要排除 |
| `distanceSquaredTo(node, offset)` | 点到文本的距离，用于"点空白处附近选择" |
| `expandToInclude(a, b)` | 两个选区取并集 |

UI 侧同样完整：`SelectionBubbleMenu`、`SelectionStyleOption`、`SelectionColorOption`、`markColorTokenToColor`、`SelectionHandle`／`SelectionHandleDecoration`／`SelectionHandleCanvas(lineHeightPx, touchPaddingPx, dotDiameterPx, dotRadiusPx)`，以及三个定位算法 `calculateMenuPlacement`、`calculateCenteredOverlayOffset`、`calculateNoteFocusPlacement`。

### 39.2 我们的实现要点

```dart
class SelectionSnapshot {
  final int blockIndex, startOffset, endOffset;
  final EpubCfi startCfi, endCfi;
  final String text;
  final List<Rect> lineRects;   // 逐行矩形，用于高亮绘制
  final Offset startHandle, endHandle;
}
```

四个容易做错的点：

1. **占位元素要跳过**：行内图片、内联块在字符流里占一个位，选区矩形计算时要排除，否则高亮会盖住图片
2. **手柄吸附到行首/行尾**：手柄不是跟着手指坐标，而是要吸到行的起止位置，否则拖动时视觉抖动
3. **菜单定位要防出界**：选择点在屏幕顶部时菜单要翻到下方，`calculateMenuPlacement` 就是干这个的（含左右 padding 与额外高度）
4. **点空白处以最近文本为准**：`distanceSquaredTo` 提供"离哪段文字最近"，这是长按宽松命中的基础

### 39.3 与分页的交互

选区可以跨页，但用户一次只能看到一页。所以：

- 拖到页面边缘时触发翻页，翻页后选区终点落在新页
- 跨页选区的高亮按页分别绘制，只画当前页可见部分
- 选择模式下面板隐藏、点击不翻页（阅微 `ReaderUiState.isSelectionMode` 就是干这个的）

## 40. 选词与选句

### 40.1 阅微的实现痕迹

`BodyKt` 里有一组字符分类与范围查找：

| 方法 | 作用 |
|---|---|
| `wordRangeAt(node, offset)` | 取光标所在的"词" |
| `fallbackWordRange(content, pivot)` | 退化取词（无空格语言） |
| `isCjkLetter(char)` | CJK 字符判定 |
| `sentenceRangeAt(node, offset)` | 取光标所在的"句" |
| `isSentenceContentChar` / `isSentenceBreakChar` / `isSentenceTrimChar` / `isSentenceTrailingChar` | 句界判定的四类字符集 |

另有 `SelectionNearbyTokenRow(tokens: List<TextSegmenter.Token>, selectedWord, onTokenClick)`——选词后弹出"近邻词"供替换选择，底层是 `arch/text/TextSegmenter`（该类未包含在反编译交付里，只见到引用）。

### 40.2 规则设计

中文没有空格，选词必须靠字符类别：

```
词边界：
  CJK 字符连续段 → 一个"词"（不做词典分词）
  拉丁字母/数字连续段 → 一个词
  其余（标点、空白）→ 单独成词
句边界：
  句末标点 。！？!?… 之后
  后引号/后括号紧跟句末标点时，归入前一句（isSentenceTrailingChar 的作用）
  换行、段落结束、块级元素边界也是句界
```

**不做词典分词**。理由：分词需要词典与消歧，选词不需要那么准，"连续同类字符"已经够用；何况用户还能拖手柄。

### 40.3 这套东西的真正用途

句切分是阅读器里复用度最高的基础能力，至少四处要用：

1. 长按选句、点按选词
2. **TTS 朗读的切句单位**（见 41）
3. 划选后"分享这段"的默认粒度
4. 智能识别（人名、地名、生词查询）的输入单位

所以它应该放在 `reader_core` 的纯文本层，不依赖排版结果，只吃字符串和偏移。

## 41. TTS 朗读

### 41.1 参考情况

全库检索 `TextToSpeech / tts / Speak / speech` **无结果**——阅微没有朗读功能（至少在反编译交付的范围内没有）。这一块没有可抄的实现，但 `sentenceRangeAt` 给了切句基础。

### 41.2 设计

```dart
class TtsController {
  final List<Sentence> queue;      // 切好句的队列，按阅读顺序
  int currentIndex;
  Future<void> play();
  Future<void> pause();
  Future<void> nextSentence();
  void seekToCfi(EpubCfi cfi);     // 从当前位置开始读
}

class Sentence {
  final EpubCfi start, end;
  final String text;
  final int spineIndex;
}
```

核心链路：

```
当前页 → 收集该页所有句（用 40 的句切分）
  → 逐句送系统 TTS（flutter_tts / 原生）
  → 句子开始：高亮该句并确保可见（必要时翻页）
  → 句子结束：推进到下一句
  → 朗读位置变化写回进度（CFI）
```

### 41.3 四个必须处理的问题

1. **跨页连续**：读完当前页最后一句自动翻页，翻页动画与朗读不能打架——朗读驱动翻页时应禁用动画或用极短动画
2. **锁屏续读**：需要后台音频会话（iOS 的 `audio` category、Android 的前台服务），否则切后台朗读就停
3. **中断恢复**：来电、其他 App 抢音频焦点后要能恢复；恢复位置按"当前句开始"而不是"句中"
4. **句子与 CFI 的双向映射**：切句时同时产出 CFI 对，否则高亮和跳转对不上

### 41.4 不做

- 不做整章预切（大章节会产生上万句，内存与启动成本都不值），按页现切，翻页时预取下一页的句
- 不做语速/音色的自定义合成，只用系统 TTS 的现成参数

## 42. 墨水屏模式与阅读设置

### 42.1 阅微的墨水屏支持

`LocalIsEink` 是一个 CompositionLocal，出现在 `BodyKt`、`EpubWindowKt`（`rememberEpubWindowConfig(containerSizeOverride, isEink)`）、`StaticPagerKt`、`EpubContainerKt`、`EpubCoverPageKt`、`ReaderScreenKt`。

已知的具体影响：

- `FontProvider.builtInSerifFamily(einkBoldOnly)` —— 墨水屏模式下只用粗体字族，提升对比度
- 翻页动画退化为静态（`StaticPager` 在墨水屏上更合适）
- 图片显示模式可调（`ReaderUiState.imageViewMode`）

这说明墨水屏不是"换个主题"，而是**贯穿字体、动画、图片、背景的一层降级策略**。

### 42.2 我们的做法

```dart
class ReaderEnvironment {
  final bool isEink;         // 用户手动开关或按设备识别
  final bool isDark;
  final double devicePixelRatio;
}
```

墨水屏模式下统一应用：

| 项目 | 降级 |
|---|---|
| 翻页动画 | 强制无动画 |
| 字体 | 提升字重一级（或改用粗体字族） |
| 背景图 | 禁用（纯色） |
| 阴影/渐变 | 禁用（改为描边或不画） |
| 图片 | 按 `imageViewMode` 决定显示/隐藏/灰度 |
| 高亮 | 用下划线代替半透明色块 |

### 42.3 阅读设置项清单

从 `ReaderUiState` 的字段可以直接读出阅微的设置面：

| 字段 | 含义 |
|---|---|
| `flipStyle` | 翻页动画样式 |
| `clickLeftNextPage` | 点击左侧是否翻下一页（左撇子/习惯切换） |
| `volumeKey` | 音量键翻页 |
| `darkMode` | 深色 |
| `imageViewMode` | 图片显示模式 |
| `showCover` | 是否显示封面页 |
| `isSelectionMode` | 选择模式（内部状态） |
| `pageTurnRevision` | 翻页版本号（驱动重组） |
| `tapDirection` | 点击区域映射 |

排版参数是另一组（`ReaderEpubConfig`，见 21.1）：`textSize`、`lineHeight`、`paragraphSpacing`、`letterSpacing`、`padding`、`family`、`embeddedFonts`、`boldFont` 等。

两组分开的好处：**翻页样式变化不触发重排，排版参数变化必须重排**。这个边界要在代码里显式分开，混在一起会导致改个翻页动画就整章重排。

## 43. 无障碍

### 43.1 阅微这里完全空白

全库检索 `SemanticsProperties`、`heading()`、`LiveRegion`、`stateDescription`、`Modifier.semantics`：**零结果**。

`BodyKt` 里只有 `actions`（选区的复制/高亮等自定义动作）。也就是说正文是自绘的、没有挂任何语义节点，读屏用户打开这本书**什么都读不到**。

这不是小瑕疵。对自绘文本引擎来说，无障碍是必须主动补的一层，不是锦上添花。我们要把它做成方案的一部分。

### 43.2 技术路径

Flutter 的 `CustomPainter` 提供了 `semanticsBuilder` 回调，可以返回 `CustomPainterSemantics` 列表（每个带矩形与 `SemanticsProperties`）。这正是自绘内容的语义出口。

```dart
class PagePainter extends CustomPainter {
  @override
  SemanticsBuilderCallback get semanticsBuilder => (Size size) {
    return [
      for (final block in page.blocks)
        CustomPainterSemantics(
          rect: block.paintRect,
          properties: SemanticsProperties(
            label: block.text,
            textDirection: TextDirection.ltr,
            sortKey: OrdinalSortKey(block.readingOrder.toDouble()),
          ),
        ),
    ];
  };
}
```

### 43.3 节点粒度

| 层级 | 节点 | 说明 |
|---|---|---|
| 页 | 一个节点，label「第 N 页，共 M 页」 | 翻页时播报 |
| 块 | 每个段落/标题/图片一个节点 | 主体，label 为文本 |
| 标题 | 加 `header` 标记 | 支持"按标题跳转"导航 |
| 图片 | label 取 `alt`，无 alt 时「图片」 | |
| 高亮/笔记 | 作为块的附加描述 | 「含 1 条笔记」 |

按块而非按行建节点：一行一个节点会让读屏用户听 30 个碎片，30 段的整段朗读才自然。

### 43.4 阅读顺序

语义节点的 `sortKey` 必须按阅读顺序：

- 横排：自上而下，块内自左到右
- 竖排：自右到左的列序，列内自上而下

`OrdinalSortKey` 用块在页内的绘制序号即可，前提是绘制顺序与阅读顺序一致——这一点绘制层要保证，否则竖排会读反。

### 43.5 交互冲突

TalkBack / VoiceOver 开启时，单指滑动被读屏占用，我们的自定义翻页手势会失效。处理：

| 动作 | 无障碍模式下的方式 |
|---|---|
| 翻页 | 页级节点的自定义 action「下一页」「上一页」 |
| 选中段落 | 硬件/软件音量键，或页级 action |
| 复制/高亮/朗读 | 块级节点的自定义 `CustomSemanticsAction` |
| 位置播报 | 翻页后 `SemanticsService.announce('第 N 页，共 M 页')` |

关键是**不要试图在无障碍模式下保住自定义手势**，而是把能力搬进语义 action。

### 43.6 验收

- 开启 TalkBack 能从书的开头读到结尾，段落边界正确
- 竖排书的阅读顺序正确
- 翻页有播报
- 选中段落能复制、能朗读（与 TTS 联动）
- 图片有可读描述

## 44. 性能埋点

### 44.1 阅微没有可用参考

### 44.2 埋点清单

用 `dart:developer` 的 `Timeline` 打点，只在 debug/profile 生效：

| 埋点 | 起点 | 终点 | 目标 |
|---|---|---|---|
| `book.open` | 点开书 | 首屏内容可读 | < 1000ms |
| `chapter.layout` | 开始分页 | 该章最后一页产出 | < 400ms |
| `page.render.build` | 开始构建页渲染缓存 | 完成 | < 8ms |
| `page.render.reuse` | 翻页命中缓存 | —— | < 4ms |

| `font.load` | 调用 FontLoader | 可用 | < 300ms |
| `image.decode` | 开始解码 | 可用 | 按尺寸，记 P95 |

### 44.3 缓存命中率

三个必须监控的比率，比单次耗时更能定位问题：

```
页渲染缓存命中率 = 复用次数 / 总绘制次数
分页缓存命中率 = 已缓存章命中 / 章节访问次数
字形覆盖率     = 命中的字符数 / 总字符数   （字体回退是否频繁）
```

命中率掉下来通常意味着缓存键设计有问题（`windowKey` 抖动、DPR 变化没归一），比优化单点性能更值得先查。

### 44.4 内存

| 指标 | 目标 | 手段 |
|---|---|---|
| 单本峰值 | < 200MB | 页缓存只留当前 ±2 页；图片按显示宽度降采样 |
| 图片缓存 | 512 张上限，LRU | 与阅微一致 |
| 分页结果 | 当前章 ±2 章 | 见 17.4 |
| 字体 | 全局常驻 | 字体不能频繁加载卸载，反而更贵 |

用 DevTools 的 memory 视图按"页缓存 / 图片 / 字体 / 排版树"四类归因，不混在一起看总和。

### 44.5 埋点实现边界

- 所有埋点编译期可关闭（`const bool kProfile = ...` 或断言后的空实现），不进 release
- 不引入第三方 APM SDK，先把本地时间线跑准
- 每个埋点带 `spineIndex` / `pageIndex` / `textSize` 等维度，否则"慢"无法复现

## 47. CFI 解析与构造

CFI 是全书定位的唯一坐标（页范围、目录、书签、高亮、进度全用它），所以解析器的健壮性直接决定数据能不能活过版本迭代。

### 47.1 阅微的解析器

`EpubCFI.Companion.create(String)` 的实际逻辑：

```
1. 必须以 "epubcfi(" 开头（大小写敏感）
2. 去掉开头，removeSuffix(")")（只去一个）
3. 按 "/" 切分，丢弃空段
4. 最后一段若以 "[;s=b]" 结尾 → sideBias = before；若以 "[;s=a]" 结尾 → after，并去掉该后缀
5. 最后一段若含 ":" → 拆成两个整数，作为 CharacterOffset(start, end)
6. 前 3 段 = spine / itemref / body，其余 = steps
7. 若存在 characterOffset，最后一段不计入 steps（它只承载偏移）
```

结构体：`EpubCFI { spine, itemref, body, steps[], offset, sideBias }`，另有 `StepReference { index, idAssertion }`、`CharacterOffset`、`SideBias`、`contains(other)`、`compareTo`。

### 47.2 这个解析器的缺陷

按 EPUB CFI 规范，至少三处不支持：

| 规范特性 | 阅微 | 后果 |
|---|---|---|
| `!` 间接跳转（`epubcfi(/6/4!/4/2/1:0)`） | 只按 `/` 切，`!` 留在段内 | 引用其它文档的 CFI 解析失败 |
| 范围形式 `epubcfi(parent,start,end)` | 完全没处理括号内逗号 | 只能用两个独立 CFI 拼范围（它确实另建了 `EpubCFIRange`） |
| 转义字符 `^` | 不支持 | 含 `/`、`(` 的 id 解析错 |
| 时间/空间偏移 `~`、`@` | 不支持 | 音视频书用不到，但解析不应崩 |

另外 `removeSuffix(")")` 只去掉一个右括号，遇到带 `)` 的 id 会截错。

### 47.3 我们的解析器契约

```dart
class EpubCfi {
  final int spine;                 // /6：spine 元素步进，通常为 6，仅作结构校验
  final int itemref;               // /4：章节 itemref 步进（= (原序+1)×2，即 spineIndex）
  final String? itemrefAssertion;  // [chap01ref]
  final int? body;                 // /4（间接后）
  final List<CfiStep> steps;       // 含 index 与可选 assertion
  final int? charOffset;
  final int? charOffsetEnd;        // 范围形式的结束偏移
  final CfiSideBias side;          // before / after / none
}

sealed class CfiStep { }
class IndexStep extends CfiStep { final int index; }
class IndirectionStep extends CfiStep { }            // !
class AssertionStep extends CfiStep { final String id; }
```

必须支持的输入形态（每条都要有测试用例）：

| # | 输入 | 说明 |
|---|---|---|
| 1 | `epubcfi(/6/4[chap01]!/4/2/1:0)` | 标准全形式 |
| 2 | `epubcfi(/6/4/2/1:5)` | 无间接 |
| 3 | `epubcfi(/6/4!/4/2,/2/1:0,/3/1:5)` | 范围形式 |
| 4 | `epubcfi(/6/4[chap^/01]!/4/2)` | id 含转义 `/` |
| 5 | `epubcfi(/6/4!/4/2/1:3[;s=b])` | side bias |
| 6 | `epubcfi(/6/4!/4/2/1:3~3.5)` | 时间偏移（解析后忽略） |
| 7 | `epubcfi(/6/4!/4/2/1:3@2:1)` | 空间偏移（解析后忽略） |
| 8 | `epubcfi(/6/4!/4)` | 无字符偏移，指向元素 |
| 9 | 非法：缺 `epubcfi(`、括号不配对、步骤非数字 | 返回 null，不抛异常 |

**解析失败一律返回 null，绝不抛异常**。CFI 来自数据库、来自外部导入、来自用户粘贴，任何一条脏数据都不能让阅读器崩。

### 47.4 构造与比较

构造方向（节点 → CFI）必须与解析对称，且**只在解析文档树时计算一次**，之后节点一直带着自己的 CFI，不在布局阶段重新拼字符串。

比较规则（`compareTo`）必须满足全序，用于：

- 页范围包含判断（`range.contains(cfi)`）
- 目录二分查找最近章
- 选区起点终点排序

比较顺序：spine → itemref → 各 step 的 index（含间接标记）→ charOffset → sideBias（before < 无 < after）。

### 47.5 序列化稳定性

CFI 字符串会写进数据库、写进导出文件。两条硬要求：

1. **同一节点序列化结果必须完全一致**（不因 map 遍历顺序、不因可选 assertion 丢失而变）
2. 解析 → 序列化 → 再解析，结果必须等价（round-trip 测试，用 47.3 的 9 条用例全覆盖）

## 48. 浮动与占位的精确算法

### 48.1 阅微的模型

`BoxConstraints { containerWidth, contentWidth, occupiedList: List<BoxOccupied> }`。

`BoxOccupied` 记录"某段高度区间内被浮动/绝对定位元素占据的矩形 + 它属于哪条基线"。

`createPlaceholders(occupiedHeight, location, matchParent)` 返回 `(新约束, 占位节点列表)`：

```
遍历 occupiedList：
  若当前占位与上一个基线相同（同一行的第二个占位）或首次进入该基线：
    生成 PlaceholderDom：
        高度 = min(occupiedHeight, 占位元素高)
        宽度 = 占位元素宽
        位置 = 占位元素左上
        标识 = "float类型_left_top_width_height"
    若 occupiedHeight < 占位元素高度：
        剩余 = 元素高 - occupiedHeight
        把该占位裁剪为（left, baseline + occupiedHeight, 同宽, 剩余高）
        放回新列表 —— 下一页继续占位
    否则：
        丢弃（本页已用尽）
返回：清空 occupiedList 的新约束 + 本页占位节点
```

要点：**占位元素在分页时被"切开"**。一个跨页的浮动图片，第一页画出上半部分，剩余部分留在新列表里，下一页接着占位。这与文本按行切分是同构的。

### 48.2 我们的实现

```dart
class BoxOccupied {
  final Rect rect;        // 在文档坐标中的占据区域
  final double baseline;  // 所属行基线，用于"同基线合并"
  final FloatKind kind;   // left / right
}

class LayoutConstraints {
  final double containerWidth;
  final double contentWidth;
  final List<BoxOccupied> occupied;

  ({LayoutConstraints next, List<PlaceholderNode> placeholders})
      takePlaceholders(double availableHeight, EpubCfi at);
}
```

流程（与阅微一致，但显式写清）：

```
每排一个新的块 / 段落前：
  (next, placeholders) = constraints.takePlaceholders(当前剩余高度, 位置)
  把 placeholders 插入流中（它们自己不产生内容，只占据空间）
  用 next 作为该块的可用宽度
  排完后 constraints = next（占位已消耗，剩余的带回游标）
```

### 48.3 四个必须做对的点

1. **同基线合并**：一个浮动元素的左右两侧可能各有一个占位，合并成一条"可用宽度 = 容器宽 - 左占 - 右占"再排版，否则文字会压到浮动上
2. **裁剪必须精确**：跨页浮动的剩余高度 = 元素高 - 本页已用高度，算错会出现"下一页浮动位置跳变"
3. **`clear` 的语义**：`clear: left/right/both` 要能"等到所有符合条件的浮动结束"，实现上是把当前 y 推到浮动底部，同时把那些占位从列表移除
4. **绝对定位不参与流**：`position: absolute/fixed` 的元素不进 occupiedList，它在绘制阶段单独定位（阅微的 `compute` 里对 absolute 直接返回容器约束，就是这个意思）

### 48.4 与分页的接口

分页器每次调用 `takePlaceholders` 时传入的 `availableHeight` 是**当前页剩余高度**，不是整页高度。这样浮动元素天然在页边界被裁开，不需要为跨页浮动写特殊分支——这是这套模型最省事的地方。

反过来，如果占位元素比整页还高（超长浮动图），则本页只画一部分、下一页继续，永远不产生"放不下的浮动"。

## 49. 排版坐标系与页高

这一章定的是最容易埋雷、又最容易被忽略的契约：**排版用哪套单位、页高怎么算**。定错了，后面所有行高、边距、分页都会系统性偏移。

### 49.1 阅微的做法

`UIEpubWindow` 是个全局单例，持有排版所需的全部环境量：

| 成员 | 作用 |
|---|---|
| `density: Density` | 单位换算的依据 |
| `width` / `height` | 内容区尺寸 |
| `boundary: Rect` | 四周留白 |
| `padding` | 阅读器内边距 |
| `statusBarHeight` / `navigationBarHeight` / `safeAreaTop` | 系统区 |
| `screenRealSize` | 屏幕物理尺寸 |
| `defaultLineHeight` / `paragraphSpacing` / `letterSpacing` / `boldFont` | 阅读器排版参数 |
| `_rootStyle: Style` | 根样式，页高由它推 |

单位换算四件套：

| 方法 | 含义 |
|---|---|
| `dp(pixels)` | 像素 → dp |
| `dpFloat(pixels)` | 同上，返回浮点 |
| `px(dp)` | dp → 像素 |
| `sp(dp)` | dp → 字号单位 |

也就是说它把 `Density` 的 `dp↔px` 双向包了一层，业务代码里所有尺寸都在**同一个内部坐标系**里流动，只在测量与绘制两个边界上换成像素。

### 49.2 页高公式

`getDocumentContentMaxHeight(document)` 的实际计算：

```
页内容高 = rootStyle.height
         - body.boundaryHeight
         - boundary.top
         - boundary.bottom
         + 10.0f          // 容差
```

这个 `+10` 是经验值，用于吸收浮点累加误差与最后一行行距的半行差。分页器里还要再减首页顶部留白（见 8.3 的 `theFirstPageTopPadding`）。

两个细节值得抄：

- 页高从**根样式**推，不从容器实测推。这样分页可以在没有真实布局的情况下算出来，便于预分页与后台排版。
- `body.boundaryHeight` 参与扣减，意味着 body 上的 margin/padding 不会重复计入每页。

### 49.3 我们的契约

```dart
class LayoutMetrics {
  final Size viewport;          // 逻辑像素
  final double devicePixelRatio;
  final EdgeInsets boundary;    // 阅读器留白
  final double statusBar, navigationBar, safeTop;

  double get contentHeight =>
      viewport.height - boundary.vertical - statusBar - navigationBar - safeTop;
}
```

三条硬规定：

1. **排版坐标一律用逻辑像素**（与 Flutter 的 logical pixel 一致），不引入第二套内部单位。阅微要 `dp/px` 双向换算是因为 Compose 的 `Constraints` 用整数像素；Flutter 的布局天生是浮点逻辑像素，不需要再包一层。
2. **`devicePixelRatio` 只在两个地方出现**：位图解码的目标尺寸、`Canvas` 绘制的抗锯齿。排版、分页、CFI、缓存键都与它无关——但缓存键要与它间接相关（DPR 变了位图要重解），这一点通过 `windowKey` 里带上 DPR 实现（见 21.1）。
3. **页高用公式算，不用实测**。公式输入是 `viewport + boundary + 系统区`，与字体无关，因此字体加载完成前就能定出页数。

### 49.4 容差的处理

阅微用固定 `+10`。我们改成**按字号比例**：

```
容差 = max(4.0, fontSize * 0.5)   // 半行内的误差吸收
```

理由：固定 10 逻辑像素在 12sp 字号下过大（会把本该翻页的一行硬塞进本页），在 30sp 字号下又过小。用半行作为单位，随字号自动缩放。

这条要写进分页器的常量表，并纳入快照测试——容差变化会整体改变分页结果，属于"必须有意为之"的变更。

## 50. 图片管线

### 50.1 阅微的实现

`ImageProvider` 的字段与方法把整条管线暴露得很清楚：

| 成员 | 作用 |
|---|---|
| `bitmapCache` / `sizeCache` / `transparencyCache` | 三个缓存：位图、尺寸、是否含透明 |
| `inFlightLoads` + `loadMutex` | 并发去重，同一图片同时只解码一次 |
| `normalizeSource` / `requestCacheKey` | 源归一与缓存键 |
| `resolveRequestPixelSize` / `scaledSize` / `makeSize` | 按目标显示尺寸算解码尺寸 |
| `findSlimImage` + `shouldUseSlimImage` | 优先用预生成的缩略图 |
| `ensureLocalImage` / `localPathForNetwork` / `findExistingLocalForNetwork` | 网络图落本地再走本地链路 |
| `hasTransparency` | 透明度检测 |
| `einkImageOptimization` | 墨水屏图片优化开关 |
| `peekBitmap` | 不触发加载的窥视，用于同步判断 |

`UIEpubWindow` 那侧还有 `imageViewMode`（显示模式）、`illustrationOptimization`（插图优化）、`previewImage(imageUri, fromRect)` + `isPreviewing` + `dismissPreview`（点图放大预览）。

### 50.2 我们的管线

```dart
Future<ui.Image> load(String href, {required double displayWidth}) async {
  final key = cacheKey(href, displayWidth, dpr);
  if (bitmapCache.has(key)) return bitmapCache.get(key);
  if (inFlight.contains(key)) return inFlight[key]!;   // 并发去重
  final future = _decode(href, displayWidth);
  inFlight[key] = future;
  try { return await future; } finally { inFlight.remove(key); }
}
```

六个环节，每环都有明确的失败降级：

| 环节 | 失败降级 |
|---|---|
| 源归一（相对路径 + 大小写容错） | 找不到 → 占位框 + alt |
| 目标像素尺寸 = 显示宽 × DPR（封顶原图宽） | —— |
| 缓存查（位图/尺寸/透明） | 未命中 → 解码 |
| 并发去重 | —— |
| 解码（`instantiateImageCodec` 带 `targetWidth`） | 解码失败 → 占位框 |
| 透明检测 | 不透明图可跳过混合，省一层 |

### 50.3 三个必须做的优化

1. **按显示尺寸解码**，不按原图解码。一张 3000×4000 的插图在手机上只需要 800 宽，直接按 `targetWidth` 解码能省 90% 内存，这是移动端最容易爆内存的地方。
2. **并发去重**。列表滚动、翻页回退、排版与绘制同时请求同一张图的情况很常见，没有去重会重复解码同一文件多次。
3. **尺寸缓存单独存**。排版阶段只需要知道图片宽高比例来算占位高度，不需要像素数据；把尺寸与位图分开缓存，可以让"排版完成但图片还没解码"成为正常状态而不是阻塞。

### 50.4 显示模式与墨水屏

`imageViewMode` 决定图片怎么显示：正常 / 隐藏（只留占位） / 灰度。`einkImageOptimization` 在墨水屏上进一步降级。

我们的处理：

```
normal  → 正常绘制
hidden  → 画占位框（不请求解码，省内存）
gray    → 解码后加 ColorFilter.matrix 转灰度（结果进缓存，不每次算）
eink    → 强制 gray + 限制最大解码宽度
```

### 50.5 图片预览

阅微有 `previewImage(imageUri, fromRect)`，从点击位置放大。这是插图类书籍的高频操作，我们列为 P1：

- 点击图片 → 从图片矩形做 `Hero` 式放大到全屏
- 全屏支持双指缩放与双击复位
- 大图按屏幕宽度解码，不按原图

### 50.6 缓存上限

沿用阅微的量级，但按内存估算而非纯条数：

| 缓存 | 上限策略 |
|---|---|
| 位图 | 按总字节数封顶（如 64MB），LRU |
| 尺寸 | 512 条，LRU |
| 透明标记 | 128 条，LRU |

只按条数封顶的问题是一张全彩插图可能比一百张缩略图还占内存，按字节更稳。

## 51. 样式计算顺序与继承

### 51.1 阅微的确切顺序

`Style.compute(parent)` 分 11 段，顺序是硬编码的：

```
1.  fontSize                      ← 必须最先，后面所有 em 依赖它
2.  position, display, boxSizing
3.  borderImageWidth, borderImageOutset
4.  borderTopWidth, borderBottomWidth, borderLeftWidth, borderRightWidth
5.  paddingTop, paddingBottom, paddingLeft, paddingRight
6.  marginTop, marginBottom, marginRight, marginLeft
7.  width, height
8.  maxWidth, minWidth, minHeight, maxHeight
9.  borderTopLeft/RightRadius, borderBottomLeft/RightRadius
10. float
11. lineHeight, textIndent, fontWeight, letterSpacing,
    top, left, right, bottom,
    backgroundSize, textShadow, justifyContent, boxShadow,
    border{T}op/Left/Right/BottomColor, borderSpacing, rowGap, columnGap, textEmphasisColor
```

顺序里有三条依赖：

- `fontSize` 在一切之前：`em`、`ex`、`%` 字号都由它换算
- **边框宽度在 padding/margin 之前**：`box-sizing: border-box` 时 padding 的百分比基准受边框影响
- **width/height 在 padding/margin 之后**：`width: auto` 的内容框推导需要知道已经占了多少

### 51.2 继承字段的权威清单

`Style.inherit()` 复制的 18 项：

```
color  fontFamily  fontSize  fontStyle  fontWeight  lineHeight  letterSpacing
textAlign  textIndent  textShadow  writingMode  listStyleType
textEmphasisStyle  textEmphasisColor  textEmphasisPosition
textJustify  rubyAlign  whiteSpace
```

外加两个状态位：`customProperties`（`var()` 变量表）、`hasExplicitTextColor`（是否显式指定文字色，暗色替换要用）。

这份清单与我方案 §7.3 凭规范列的一致（`font-*` 展开为 4 项、`text-emphasis-*` 展开为 3 项即是这 18 项）。代码里比规范清单多出来的是**两个状态位**：`customProperties`（`var()` 变量表）与 `hasExplicitTextColor`（是否显式指定文字色，暗色替换要用），它们在实现里必须跟着继承走，否则 `var()` 在子元素里取不到值、暗色判断也会失准。

非继承类型另有 `inheritBorderStyle()`，说明边框是"可选择性继承"的特例（`border-style` 在规范里确实不继承，但它单独开了口子用于某些书内写法）。

### 51.3 盒模型合成的两条规则

`computeHorizontalMargin()` 与 `computeVerticalPadding()`：

```
水平外边距合成 = viewportLeft + viewportRight
               + (marginLeft > 0 ? marginLeft : 0)
               + (marginRight > 0 ? marginRight : 0)

垂直内边距合成 = paddingTop + paddingBottom
               + (marginTop > 0 ? marginTop : 0)
               + (marginBottom > 0 ? marginBottom : 0)
               + (borderTopStyle 有效 || borderImageSource 有效 ? borderTopWidth : 0)
               + (borderBottomStyle 有效 || borderImageSource 有效 ? borderBottomWidth : 0)
```

两条反直觉但正确的处理：

1. **只累加正的 margin**。负 margin 不参与"占位合成"，它由布局阶段单独处理（把后续内容往前拉），不能混进总高度。
2. **边框宽度只在有样式时才计入**。`border-width: 5px` 但 `border-style: none` 时边框不占空间——这是 CSS 的标准行为，但很多实现会忘。

### 51.4 我们的实现

`ComputedStyle` 用一次性构造而非可变对象逐步 set：

```dart
class ComputedStyle {
  factory ComputedStyle.compute(RawStyle raw, ComputedStyle? parent) { ... }
  final double fontSize;          // 已换算为逻辑像素
  final double? lineHeightFactor;
  final EdgeInsets margin, padding;
  final BorderWidths border;
  final BoxConstraints? size;     // width/height/min/max 已解析
  // …其余全部为最终值
}
```

三条约束：

1. **compute 只跑一次**。任何需要"父值"的属性在构造时解决，之后布局阶段不再回查父样式。
2. **计算顺序写进一份常量表**，不散落在代码里。顺序错了会表现为"百分比 padding 值偏小"这类难以定位的问题。
3. **`hasExplicitTextColor` 必须保留**。暗色模式替换只对"书里显式指定且足够深"的颜色生效，没有这个标记就无法区分"继承来的颜色"和"作者指定但恰好是黑色"。

## 52. 样式表缓存与失效

### 52.1 阅微的实现

`StyleSheetsProvider`：

| 成员 | 实现 |
|---|---|
| `mRuleSetCache` | Cache4k，`maximumCacheSize(2048)`，键为 CSS 文件路径字符串 |
| `clear()` | `invalidateAll()`，全清 |
| `attach(vararg cssPaths)` | 逐个路径查缓存，未命中则读文件、解析、回填，最后 flatten 成 `StyleSheets` |
| `attachRuleSets(cssPath, css, text)` | 真正的解析：处理 `@import` 递归、去注释、切规则块、注册 `@font-face` |

### 52.2 两个确认的缺陷

**1. `@import` 顺序反了。** 代码里：

```
导入文件的规则 → arrayList
本文件的规则 → mutableList
最后 mutableList.addAll(arrayList)     ← 本文件在前，导入在后
```

CSS 规范要求 `@import` 的内容**插入到它的位置**，即导入的规则应当在当前文件中位于其后声明的规则之前。这里反了，同权重时覆盖结果会错（报告 F04 已确认）。

**2. 循环 `@import` 会无限递归。** 递归调用发生在**缓存写入之前**，且没有 visited 集合：

```
attachRuleSets(a) → 发现 @import b → attachRuleSets(b) → 发现 @import a → attachRuleSets(a) → …
```

书里出现互相 `@import` 的两个文件就会栈溢出。

### 52.3 缓存键的问题

键是**文件路径**。移动端的问题：同一本书重排版时路径不变但内容可能变（书被更新、导入顺序不同）。路径键无法感知内容变化。

另外 `clear()` 是全局的——改字号不需要清 CSS 规则缓存（规则没变），但阅微在配置变化时会调 `clear()`，等于白白重解析整本书的 CSS。

### 52.4 我们的设计

```dart
class StyleSheetCache {
  final _rules = LruCache<String, List<CssRule>>(maxEntries: 2048);
  final _byContent = <String, String>{};   // 内容 hash → 规则 key

  List<CssRule> parse(String path, String text);
  void invalidateBook(int bookId);
  void invalidateAll();
}
```

三条改进：

1. **键用内容 hash**（`sha1(text)` 前 16 位），不用路径。内容相同则复用，内容变化自动未命中，不需要手动清。
2. **`@import` 按规范插入**，并带 `visited` 集合，检测到环时记录警告并跳过该分支，不中断解析。
3. **失效粒度分级**：

| 变更 | 需要失效 |
|---|---|
| 改字号/行高/边距 | **不失效**（书内 CSS 规则没变，阅读器覆盖层在后面单独应用） |
| 换书 | 失效该书（按 bookId 标记） |
| 文件被重新导入 | 内容 hash 变化自动失效 |
| 字体变化 | 不失效 CSS，但 `@font-face` 注册表要重建 |

4. **`@font-face` 单独管理**。阅微在解析 CSS 时顺带注册字体（`FontProvider.attach(cssPath, fontFaceRules)`），导致 CSS 缓存未命中就会重新注册字体。我们把它拆出来：CSS 解析产出 `fontFaceDecls`，由字体子系统独立持有，与 CSS 缓存解耦。

### 52.5 缓存上限的依据

2048 条对单本书足够（典型中文书 5～20 个 CSS 文件），真正的问题不是容量而是**跨书累积**：书库有 500 本书时，每本都往同一个缓存里塞规则会把内存吃满。

所以上限之外还要按 bookId 分区，换书时只保留当前书与最近两本的规则，其余整批释放。

## 53. CFI 构造器

### 53.1 阅微的接口

`EpubCFI.Builder` 是标准流式构造器：

```java
new EpubCFI.Builder()
    .itemRef(...)
    .body(...)
    .steps(...)
    .offset(...)
    .sideBias(...)
    .build();
```

配套 `newBuilder()` 用于在已有 CFI 上修改局部（比如只换 sideBias）。

### 53.2 我们的实现约定

```dart
class CfiBuilder {
  CfiBuilder itemRef(int index, {String? assertion});
  CfiBuilder body(int index, {String? assertion});
  CfiBuilder step(int index, {String? assertion});
  CfiBuilder indirection();                  // !
  CfiBuilder charOffset(int offset);
  CfiBuilder side(CfiSideBias side);
  EpubCfi build();
}
```

四条约定：

1. **构造时机唯一**：只在解析 XHTML 构建文档树时构造，每个节点创建后带一个不可变 CFI。布局、分页、绘制阶段一律不新建 CFI，只做 `copyWithSide`。
2. **ID 断言可选但优先**：如果元素有 `id`，把 id 写进断言（`[chap01]`），解析时若 index 对不上可以按 id 恢复。这是 CFI 抗文档结构变化的关键。
3. **`copyWithSide` 不能重建步骤**：页范围的 end 只是 start 的同一个 CFI 加 `side: after`，不能重新 walk 一遍树，否则跨页范围会错位。
4. **构造器不校验语义**：`build()` 只保证结构完整，不检查"这个 spine 索引是否存在"。语义校验在解析阶段做，构造器保持纯粹。

### 53.3 与页范围的关系

一页的 CFI 范围 = `(start.copyWithSide(before), end.copyWithSide(after))`，其中 `end` 是**下一页起点的前一个位置**，不是"最后一个字符的 CFI"。

这个差别在跨页续段时最容易错：文本段落在页边界切开，第一页的 end 指向切点（`side: after`），第二页的 start 指向同一位置的 `side: before`，两者的字符偏移相同但 side 不同——这就是 `SideBias` 存在的意义。

## 54. 导入期的资源修复

中文电子书的常见病：路径大小写错、反斜杠、带 `?`/`#` 的引用、缺扩展名、资源名被工具改成数字串。能不能打开这些书，决定了书库的可用率。

### 54.1 阅微的两步修复

`EpubFileExecutor` 有两个入口，都在导入期执行：

**第一步 `restoreObfuscated(rootDir, opfPath)`**：从 manifest 建两张表

- `hrefMap`：manifest 项声明的 href → 磁盘实际路径
- `nameMap`：item id / 文件名 → 实际文件

然后用它回写四类文件的引用：`restoreObfuscatedOpf`、`restoreObfuscatedCss`、`restoreObfuscatedToc`、`restoreObfuscatedHtmlOrXhtml`，图片另走 `restoreObfuscatedImage`。

**第二步 `normalizeResourceReferencesCase(rootDir)`**：

```
1. 递归列出所有文件，建 index: 小写相对路径 → 实际相对路径
   若同一小写路径对应多个实际文件 → 加入 conflicts 集合（不参与改写）
2. 按扩展名分派：
   .css → normalizeCaseCss
   .xml / .opf / .ncx → normalizeCaseXml
   .html / .xhtml → normalizeCaseHtmlOrXhtml
3. 每个引用经 normalizeUriCase：切路径段 → 解码 → 查 index → 换回实际大小写
```

### 54.2 几个辅助方法里的实用规则

| 方法 | 规则 | 为什么需要 |
|---|---|---|
| `stripQueryAndFragment` | 先切 `#` 再切 `?`，然后 trim | 文件系统里没有 query/fragment，`a.jpg?v=2#x` 必须剥离 |
| `splitPathSegments` | 按 `/` **和 `\`** 切，去空段 | Windows 工具生成的书会混用反斜杠 |
| `inferExtFromMediaType` | 从 `media-type` 推断扩展名 | 文件名被剥掉扩展名时靠它补 |
| `findExistingFile` | 在 OPF 目录下按解码后的路径找实体 | 处理 `%E4%B8%AD` 这类 URL 编码 |
| `toRelativePath` / `toAbs` | 相对/绝对互转 | 跨目录引用 |
| `tryAtomicMoveOrCopy` | 原子移动或复制 | 改写失败不留半成品 |

`isObfuscatedSegment` / `isObfuscatedMainName` 的判定很简单：**段内没有任何字母，且存在非字母数字字符**即视为混淆名（如 `12345_67890`）。纯数字不算，含字母不算。

这个启发式很窄，能识别"数字+分隔符"型改名，识别不了哈希串（含字母）。它只用于决定是否尝试改写，判断错也不致命。

### 54.3 我们为什么不改文件

阅微的修复是**回写磁盘**：改 OPF、改 CSS、改 XHTML。好处是阅读时路径都是对的，坏处是：

- 不可逆（除非保留原始包，阅微靠 `mergeTreeInto` 覆盖）
- 修复逻辑有 bug 时会把本来能读的书改坏
- 无法对拍"修复前/修复后"

我们的做法：**建索引，不改文件**。

```dart
class ResourceIndex {
  final Map<String, String> _exact;      // 原样相对路径 → 磁盘路径
  final Map<String, String> _lower;      // 小写路径 → 磁盘路径
  final Map<String, String> _byBaseName; // 文件名 → 磁盘路径（多候选时记歧义）
  final Map<String, String> _byMediaType;// media-type → 候选列表
  final Set<String> conflicts;           // 小写冲突的路径

  String? resolve(String href, {String? baseDir, String? mediaType});
}
```

`resolve` 的查找顺序：

```
1. 剥离 query / fragment，统一分隔符为 /
2. 精确匹配（相对 baseDir 解析）
3. URL 解码后再精确匹配
4. 小写匹配（不在 conflicts 里时）
5. 按文件名匹配（同目录优先）
6. 按 media-type + 文件名尾匹配
7. 都没有 → null（调用方降级为占位）
```

等价能力对照：

| 阅微 | 我们 |
|---|---|
| 回写文件修正大小写 | 第 4 级查找兜底，零写入 |
| 回写补扩展名 | 解码时按内容嗅探（见下） |
| 回写恢复混淆名 | 第 5/6 级兜底 + media-type |
| `conflicts` 后放弃改写 | 记录冲突，精确匹配优先，其余按唯一候选取 |

### 54.4 扩展名用内容嗅探，不用猜

阅微按 `media-type` 推断扩展名。我们更可靠：读文件头几个字节判断真实格式。

| 格式 | magic |
|---|---|
| JPEG | `FF D8 FF` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| GIF | `47 49 46 38` |
| WebP | `52 49 46 46` + 偏移 8 处 `57 45 42 50` |
| SVG | 文本内含 `<svg` |
| TTF / OTF | `00 01 00 00` / `4F 54 54 4F` |

嗅探只在"扩展名缺失或与 media-type 冲突"时触发，命中即用嗅探结果，因为解码器只认字节不认扩展名。

### 54.5 冲突处理策略

同一小写路径对应多个实际文件（`Images/A.jpg` 与 `Images/a.jpg` 同时存在）时：

1. **精确匹配优先**：引用写法与磁盘完全一致的直接用
2. **同目录优先**：引用来自 `Text/ch01.xhtml` 时，优先选 `Text/Images/` 下的候选
3. **仍多候选**：取路径最短者，并记录一条导入警告
4. **绝不因为冲突而拒绝导入**：最多是某张图错位，不能整本书打不开

## 55. 破损书的可读性分级

上面那套修复能力要有明确的产出定义，否则"能打开"是个模糊说法。

### 55.1 分级

| 级别 | 判定 | 用户体验 | 数据 |
|---|---|---|---|
| **L0 完整** | OPF/spine/目录/样式全部可解析 | 正常阅读 | 全功能 |
| **L1 可修复** | 路径、大小写、编码、扩展名有问题，索引兜底后全部可解 | 正常阅读，导入时提示"已自动修复 N 处引用" | 全功能 |
| **L2 部分** | 有 spine 项缺失、目录损坏、CSS 解析失败 | 能读正文，缺目录或样式降级 | 保留，标记警告 |
| **L3 仅正文** | OPF 可读但 spine 大量失效；或 OPF 缺失但能按 XHTML 文件名排序拼出章节 | 能读，进度与目录不可靠 | 保留，明确提示"结构异常" |
| **L4 拒绝** | 不是 ZIP、无 container.xml 且无 OPF、没有任何可读 XHTML | 导入失败，给出原因 | 不留半成品 |

L3 是可选能力。**建议实现**——中文书库里靠 XHTML 文件名排序就能拼出章节的情况并不罕见，比直接拒绝有价值得多。

### 55.2 分级结果要落库

```dart
class ImportReport {
  final int level;                 // 0..4
  final List<String> warnings;     // 修复与降级明细
  final int repairedRefs;          // 修复的引用数
  final int missingSpineItems;
  final bool tocFallbackUsed;      // 是否用了退化目录
  final bool cssFailed;
}
```

`books` 表加一列存 `level` 与 `warnings` 摘要，书库卡片上对 L2/L3 显示角标，点开能看到具体问题。

**必须让用户知道书是被修复过的**。静默修复会让用户误以为是我们的排版错了。

### 55.3 拒绝时的错误信息

L4 的提示要能指导用户，不是一句"导入失败"：

| 情况 | 提示 |
|---|---|
| 不是 ZIP | 「这不是 EPUB 文件（无法解压）」 |
| 无 container.xml | 「缺少 META-INF/container.xml，可能不是标准 EPUB」 |
| container 指向的 OPF 不存在 | 「EPUB 结构损坏：找不到 OPF 文件 X」 |
| OPF 无 spine | 「EPUB 没有阅读顺序（spine），无法分页」 |
| 全部 XHTML 解析失败 | 「书内容无法解析，可能是加密或格式异常」 |

### 55.4 与测试样本的对应

§45.3 的「破损书 ×4」按这个分级设计：

- 样本 A：大小写全错 + 反斜杠路径 + 带 query 的引用 → 期望 L1
- 样本 B：NCX 损坏但 nav 可用 + 一个 spine 项指向不存在的文件 → 期望 L2
- 样本 C：无 OPF，只有一堆按序命名的 XHTML → 期望 L3
- 另附一个非 ZIP 文件 → 期望 L4

每个样本都要断言"产出级别"与"警告条数"，这是导入层唯一可靠的回归方式。

## 57. 核心接口

跨模块只通过这些接口交互，实现类不跨层暴露。

```dart
abstract interface class EpubDocument {
  BookMeta get meta;
  List<SpineItem> get spine;
  List<TocEntry> get toc;
  ImportReport get report;
  Future<SpineDocument> readSpine(int spineIndex);
}

abstract interface class SpineDocument {
  int get spineIndex;
  EpubNode get root;           // 已算好样式的排版树
  String get plainText;        // 纯文本：搜索、进度、TTS
  int get charCount;
}

abstract interface class ResourceResolver {
  Future<Uint8List?> bytes(String href, {String? baseDir});
  Future<ui.Image?> image(String href, {required double displayWidth, required double dpr});
}

abstract interface class StyleResolver {
  ComputedStyle compute(Element element, ComputedStyle? parent);
  ComputedStyle get rootStyle;   // 页高与字号基准
}

abstract interface class LineBreaker {
  TextLayout break(TextBlockNode block, double maxWidth, ComputedStyle style);
}

abstract interface class Paginator {
  Future<List<PageSlice>> paginate(
    SpineDocument doc, LayoutMetrics metrics, CancelToken token,
  );
}

abstract interface class PageRenderer {
  void paint(Canvas canvas, PageSlice page, PaintContext ctx);
  SemanticsBuilderCallback? semantics(PageSlice page);
}

abstract interface class LocatorCodec {
  Locator? parse(String s);        // 失败返回 null，不抛
  String serialize(Locator l);
  int compare(Locator a, Locator b);
  Locator forNode(EpubNode node, {int charOffset = 0});
}

abstract interface class AnnotationStore {
  Future<List<Annotation>> list(int bookId);
  Future<void> upsert(Annotation a);
  Future<void> delete(String id);
}
```

约束：

- **接口只吃已解析的对象**（`EpubNode`、`ComputedStyle`），不吃原始 HTML/CSS 字符串，避免各层重复解析。
- **`LocatorCodec.parse` 与 `ResourceResolver.bytes` 失败都返回 null**，不抛异常——这两处是脏数据入口。
- **`Paginator.paginate` 必须可取消**，且每完成一页就产出，供 UI 增量显示（§27.3）。

## 58. 关键时序

### 58.1 打开一本书

```
1. Database.books(id)            → BookMeta + lastReadAt
2. EpubDocument.open(contentDir) → 解析 container/OPF/spine/TOC（导入期已建索引，此处便宜）
3. VirtualPager.recenter(lastCfi ?? 章首)
   ├─ spineIndex = lastCfi.itemref ?? 2
   ├─ readSpine(spineIndex)
   │    ├─ parser.document     → EpubNode 树 + 节点 CFI
   │    ├─ StyleResolver       → ComputedStyle 逐节点计算
   │    └─ ResourceResolver    → 仅登记尺寸，不解码像素
   ├─ Paginator.paginate       → 增量产出 PageSlice（每 20 块让出）
   └─ 首屏可读后返回（不等全部排完）
4. ReaderView 绘制当前页        → LineRender 段落缓存
5. 后台预取前后各 1 章
```

关键：**第 3 步不等整章排完**。首屏显示第一页即可交互，其余分帧推进（§27.2）。

### 58.2 翻页

```
1. GestureDetector 位移 → Pager 计算目标页
2. VirtualPager 查映射
   ├─ 命中已加载页 → PageSlice
   └─ 落在未加载区 → ensureWindow 扩张 → 等该页产出（显示 loading）
3. PageRenderer.paint（命中缓存 < 4ms）
4. 写进度：Locator → percent（§22.3），节流 1s
```

### 58.3 改字号

```
1. SettingsPanel 改 textSize → 新 ReaderConfig
2. windowKey 变化（§21.1）
3. 记录 lastVisibleCfi ← 当前页 start
4. 清：ComputedStyle 缓存、PageSlice 缓存、VirtualPager 映射
   （不清：图片位图、字体、CSS 规则）
5. VirtualPager.recenter(lastVisibleCfi)
6. 重排完成后淡入
```

### 58.4 搜索

```
1. search.build(bookId)          → 2-gram 索引（导入期已完成，此处只加载）
2. 查询 → 命中列表 (spineIndex, charOffset, 上下文)
3. 点击结果：
   ├─ LocatorCodec.forOffset(spineIndex, charOffset)  ← 查导入期存的偏移→节点映射
   ├─ VirtualPager.recenter(locator)
   └─ PageRenderer 叠加临时高亮 3s
```

### 58.5 选区与高亮

```
1. 长按 → TextHit(blockIndex, charOffset) → Locator
2. 拖拽 → 更新终点 → SelectionSnapshot（lineRects）
3. 工具条点"高亮"
   ├─ 取 quote = selectionText（≤200 字）
   ├─ AnnotationStore.upsert（startCfi/endCfi/quote/color/style）
   └─ 重绘当前页（不触发重排，§21.3）
4. 再次进入该书：按 CFI 重定位；CFI 失效则用 quote 搜索（§30.4）
```

## 60. 块测量实现规格

### 60.1 两阶段

每个块级节点走两步，不能合并：

```dart
// 阶段一：分配约束、测量子树、登记占位
void onLayout(LayoutConstraints c, BoxBaseline baseline, {bool skipBoundary = false});

// 阶段二：合成自身尺寸（contentSize / boundaryWidth / boundaryHeight）
void calculateSize(double measuredWidth, double measuredHeight, LayoutConstraints c);
```

阶段一结束时所有子节点尺寸已定，阶段二只做加法。这样"父测子、子回报、父合成"不会来回震荡。

### 60.2 约束分派顺序

`BoxConstraints.compute(dom)` 的分派顺序是有先后的，顺序错了会出怪异结果：

```
1. position: absolute / fixed  → 直接返回"容器约束"（不参与流，尺寸自算）
2. float: left / right          → 走 computeWithFloat
3. writing-mode: horizontal-tb  → 常规横排：宽度收缩修正
4. 其他                          → 竖排分支：宽度取内容宽 + 边界
```

浮动与绝对定位**在流程上要先被摘出去**，否则它们会被当成普通块推进基线。

### 60.3 基线推进规则

`onLayout` 收尾的处理决定排版是否有重叠：

```
若 float 有效 或 position 为 absolute
    → 只更新自身尺寸，**不推进基线**，直接 return
否则
    → baseline += 自身高度（块级正常占流）
```

这条在实现里最容易漏。浮动图片如果不小心推进了基线，正文会在图片下方留一个大洞；绝对定位如果再推进一次，后续内容会整体下移。

### 60.4 inline 容器的尺寸

子节点全部是 inline 时（如 `span`、`a`、`em`），容器尺寸取子节点的**最大值**：

```
width  = max(child.width)
height = max(child.height)
```

不是求和——行内元素在水平方向上并排，只有跨行时才叠加。

### 60.5 浮动首选宽度

`width: auto` 的浮动元素要算"内容自然宽度"（fit-content）：

```
calculateSize$scanPreferred(dom):
  若 dom 是文本块：
     width = 测量整段文本不换行时的宽度
     遍历文本的每个字符索引，累加各段宽度
  若 dom 是容器：
     递归扫描每个子节点，累加
  取与约束宽度的较小值
```

结果再与容器可用宽度取 min。没有这一步，浮动图会撑满整行。

### 60.6 clear 的处理

容器的子节点里存在 `float` 元素时，检查是否有后续元素带 `clear`：

```
若 存在 float 子节点 且 存在 clear 子节点：
    height += padding.bottom      // 把浮动区一并算进容器高
```

这是简化的 clear 实现——不做"清除到哪一侧的浮动"的精确计算，只在容器收尾时补足高度。阅微就是这么做的，够用但**遇到复杂图文绕排会偏高**，验收时要盯这一项。

### 60.7 首元素负 margin 的钳制

body 的第一个元素如果带负 `margin-top`，会把内容顶出可视区。有专门的钳制逻辑（`shouldClampBodyFirstElementNegativeTopMargin`）：

```
若 是 body 的首个块级子元素 且 marginTop < 0：
    marginTop = 0（或钳到安全区边界）
```

不做的话，某些书的第一页开头会被裁掉半行。

### 60.8 跨页可见裁剪

这是块跨页时的表达方式，也是"同一个块在两页显示不同部分"的机制：

| 字段 | 含义 |
|---|---|
| `offsetTop` / `offsetBottom` | 本页内容相对块顶的偏移区间 |
| `drawFixHeight` / `drawRealHeight` | 本页实际绘制高度 / 块真实高度 |
| `getVisibleMargin()` | 只保留落在本页区间内的 margin |
| `getVisiblePadding()` | 同上，padding 版本 |
| `getVisibleOffsetY()` | 本页可见部分在块内的 y 偏移 |
| `setIsPageTopElement` | 标记"本块从本页顶部开始" |

绘制时用 `drawRect = (offsetTop, offsetTop + drawFixHeight)` 裁剪，`drawFixHeight < drawRealHeight` 就说明这块跨页了。

我们的等价实现：

```dart
class BlockSlice {
  final int blockIndex;
  final double clipTop, clipBottom;   // 相对块顶部
  final bool continuesBefore, continuesAfter;
}
```

### 60.9 绝对定位

绝对定位元素单独收进一个集合（`absoluteDomSet`），布局阶段只登记、不占流；绘制阶段按 `top/left/right/bottom` 定位，父容器不为它留空间。

跨页时绝对定位元素是否重复绘制取决于是否 `fixed`：

- `absolute`：只在它所属块的页绘制
- `fixed`：每页都绘制（页眉页脚类）

### 60.10 不变量

测量结束后必须成立，建议写成断言：

1. `contentSize.width <= constraints.contentWidth`
2. `boundaryWidth = content + padding + border + margin`
3. 任意子节点的 `top >= 0` 且 `bottom <= parent.contentSize.height`（绝对定位除外）
4. `baseline` 单调不减（同一容器内，浮动与绝对定位不参与）
5. 跨页块的 `drawFixHeight <= drawRealHeight`

## 61. 文本行切分规格

### 61.1 行模型

```dart
class LineBox {
  final int start, end;        // 字符区间（半开）
  final double top, height;    // 相对文本块顶部
  final double baseline;
  final double width;          // 行实际宽（用于对齐余量）
}
```

行高 = 该行所有 run 的 `fontSize × lineHeight` 最大值；半行距按 CSS 规则分配到基线上下：

```
leading    = lineHeight - fontAscent - fontDescent   // fontAscent/Descent 是字体原始度量
leadingTop = leading / 2
baseline   = top + leadingTop + fontAscent
```

> **S1 实测（2026-10-22，`方案/spike/s1-result.md`）**：`LineMetrics.height` 精确等于上式行高；但 `LineMetrics.ascent/descent` 是**行框度量**，已包含半行距且 `ascent + descent == height`，所以实现里应直接取 `baseline = top + m.ascent`，不要再拿行框 ascent 套一遍 `leading / 2`。同时 `TextStyle` 必须显式设置 `leadingDistribution: TextLeadingDistribution.even`；默认的 `proportional` 在 28×2.0 下基线偏差 4.745px，不满足 0.5px 容差。字体原始度量用 `height: null` 的辅助测量获取，只用于公式校验。

### 61.2 断行流程

```
break(block, maxWidth, style):
  clusters = segment(block.text)            // CJK 单字 / 拉丁词 / 数字串 / 标点
  pos = 0; lines = []
  while pos < clusters.length:
      // 贪心累积到超宽
      fitEnd = 贪心找到使 width(pos..fitEnd) <= maxWidth 的最远 cluster 边界
      // 禁则回退
      fitEnd = applyKinsoku(clusters, pos, fitEnd)
      if fitEnd == pos:                     // 单个 cluster 比整行还宽
          fitEnd = pos + 1                  // 强制断
      line = 测量(pos..fitEnd) 取实际宽度与高
      lines.add(line); pos = fitEnd
  return TextLayout(lines)
```

宽度来源两种，取决于 S4 结论（§19）：

- 引擎支持中文禁则：直接用引擎给的行边界，只做行高与基线换算
- 引擎不支持：自建断行器，宽度靠逐字 advance 缓存

**S4 已测（2026-10-22，`方案/spike/s4-result.md`）：走第一条。** 正文宽度下限按 3em 钳制，规避省略号对在 2em 宽被拆开的已知缺陷；`applyKinsoku` 与逐字 advance 缓存留作后备，不在一期实现。

### 61.3 与 Flutter 的接口映射

| 需要 | Flutter API | 备注 |
|---|---|---|
| 行数 | `TextPainter.computeLineMetrics().length` | 文本改动后需重新 layout |
| 行高 / 基线 | `LineMetrics.height` / `.baseline` | 已是逻辑像素 |
| 行宽 | `LineMetrics.width` | 用于对齐余量 |
| 行边界字符 | `TextPainter.getLineBoundary(TextPosition)` | 逐行调用，O(行数) |
| 单行不换行布局 | `TextPainter.layout(maxWidth: infinity)` | 切出来的子串用它排版 |
| 字符位置 | `TextPainter.getOffsetForCaret` | 仅在竖排与选区需要 |

### 61.4 跨页切分

核心是"按行序号切开，尾段重排"：

```
若 整块高度 <= 剩余高度：
    整块收进本页
否则：
    从 0 开始找满足 lineTop(i) + lineHeight(i) <= 剩余高度 的最大 i
    若 i < 0（一行都放不下）：
        记录本页剩余空白，把该块整体带到下一页重排
    否则：
        前段 = 行 0..i        → 本页，标记 continuesAfter = true
        尾段 = 字符 offset(lines[i+1].start) 之后的部分
        尾段重新 break()，offsetBottom = 剩余高度 - lineBottom(i)
```

两个必须保留的细节：

1. **尾段要重排**，不能复用前半段的行框。因为切点之后的首行是新的起点，行内禁则、两端对齐都要重算。
2. **`offsetBottom` 要带回游标**。它表示"本页在该块底部还剩多少空间"，下一页排该块时用来做首行对齐微调，丢了会出现页与页之间行距不一致。

### 61.5 行级对齐

对每个非末行（`justify` 时）：

```
extra = maxWidth - line.width
若 extra > 0 且 该行含 CJK 且 该行不是硬换行结尾：
    ls = extra / 该行字符数
    该行所有 CJK run 的 letterSpacing += ls
```

末行不拉伸，硬换行（`<br>` 或段尾）不拉伸。西文行改为拉伸词间空格，不动字距。

### 61.6 边界条件清单

实现时逐条验：

| # | 情况 | 期望 |
|---|---|---|
| 1 | 段落只有一行且超出页高 | 整段移下一页，不切 |
| 2 | 段落在页底刚好放下一行 | 放下，不提前切 |
| 3 | 段落在页底一行都放不下 | 记剩余空白，整段下移 |
| 4 | 切点落在标点前 | 禁则把它与前一字一起移下 |
| 5 | 行内有行内图片 | 图片算作一个不可拆的 cluster |
| 6 | 行内有 ruby | ruby 不影响行宽（覆盖绘制） |
| 7 | `letter-spacing` 为负 | 允许，但行宽不小于 0 |
| 8 | 字号极大（一行一字） | 每行一个 cluster，不崩 |
| 9 | 空段落 | 产出零行，跳过 |
| 10 | 尾段只有一个字符 | 正常产出单字行 |

## 62. 表格实现规格

### 62.1 三遍流程

表格不能像普通块那样一遍过，必须分三遍：

```
第一遍 列宽：扫描所有单元格，算每列的自然宽与显式宽，调和出最终列宽数组
第二遍 单元格：逐格用"覆盖到的列宽之和"重排，格内文本按新宽度断行
第三遍 行高：逐行取行内（非跨行）单元格高度最大值作为行高
```

顺序不能换：列宽没定就无法断行，断行没完就没有行高。

### 62.2 列宽计算

```
colNatural[j] = 0; colExplicit[j] = NaN

遍历每个单元格 cell（第 c 列，跨 colSpan 列）：
    natural = (cell.contentWidth + cell.borderBoxWidth) / colSpan
    explicit = (width 不是 auto) ? width : NaN
    对 j in [c, c+colSpan)：
        colNatural[j]   = max(colNatural[j], natural)
        colExplicit[j]  = 取非 NaN 的那个（多个冲突时取最大）
```

三个来源要调和：

| 来源 | 用法 |
|---|---|
| 单元格自然宽（文本不换行宽度） | 下限，保证不挤字 |
| 单元格显式 `width` | 优先，但不得小于自然宽 |
| 表格可用宽 | 上限，列宽和超出时按比例压缩 |

**跨列单元格均摊**是这里唯一的巧处：一个 `colspan=3` 的格，它的自然宽除以 3 才参与列宽竞争，否则它会把自己撑得过大。

### 62.3 单元格宽度回填

```
对每格：
    cellWidth = sum(colWidth[c .. c+colSpan))
    cell.style.width = cellWidth - cell.boundaryWidth     // 边界宽要扣掉
    cell.onLayoutOnlyConstraints(containerConstraints(cellWidth))
    记录 cell 高度
```

注意 `- boundaryWidth`：列宽是"边框盒"宽度，单元格内容宽要再扣掉自己的 padding/border/margin。

### 62.4 行高

```
行高 = max(该行 rowSpan == 1 的单元格高度)
```

`rowSpan > 1` 的格不参与行高取最大值，它由跨行逻辑单独分摊——否则一个跨三行的格会把第一行撑得过高。

### 62.5 与分页的衔接

表格跨页是行级切分（§26），分页器对表格的处理是多一个"续页表头"的可选步骤：

```
剩余高度能放下 k 行：
    绘制前 k 行
    若 表格有 thead 且 k < 行数：
        下一页顶部先画 thead，再画剩余行
        可用高度 -= thead 高度
    剩余行带入下一页，跨行单元格按 RowSpan 记录已绘制高度（§26.1）
```

### 62.6 边界条件

| # | 情况 | 期望 |
|---|---|---|
| 1 | 单列表格 | 正常，列宽 = 表格宽 |
| 2 | 单元格为空 | 高度为 0 + padding，不报错 |
| 3 | `border-collapse: collapse` | 相邻边框只画一条 |
| 4 | 列宽总和 > 表格宽 | 按比例压缩，最低不小于自然宽的 60%（再小就挤成竖排） |
| 5 | 单元格内含块级元素 | 按块流排，不用行内规则 |
| 6 | 单元格内嵌图片 | 图片宽不超过列宽，超出等比缩 |
| 7 | `rowspan` 跨到下一页 | 续绘时只画落在本页行区间内的部分 |
| 8 | 表格只有一行且高于整页 | 允许单页只画一行（不切格子） |

第 4 条的 60% 下限是经验值，作用是避免极端书把表格压成"每列一个字"。低于下限时宁可让表格横向溢出并允许折叠，也不压到不可读。

## 63. 选区命中与手柄

### 63.1 命中测试

**点击/长按 → 文本位置**：

```
hitTest(Offset p):
    1. 在页内按绘制顺序找包含 p 的块（块的外接矩形）
    2. 在该块内用 TextPainter.getPositionForOffset(p - blockOrigin) 取字符偏移
    3. 归一到 cluster 边界（避免落在代理对中间）
    4. 返回 TextHit(blockIndex, charOffset) → 转 Locator
```

**点空白处**：阅微有 `distanceSquaredTo(node, position)`，取距离最近的文本块。我们照做：

```
若 p 不在任何块内：
    取所有块中 (p 到块矩形的最短距离) 最小者
    若距离 < 24 逻辑像素（可配）→ 视为命中该块，取最近的行
    否则 → 取消选区
```

24 是手指容差经验值，长按选词的宽松命中靠它。

### 63.2 三者优先级

落点必须先在 cluster 级别归一，再决定是"词"还是"字符"：

```
长按 → wordRangeAt(offset)：先试词，失败退到 fallbackWordRange（连续同类字符）
双击 → wordRangeAt
三击 → sentenceRangeAt（句，用 §40 的句界规则）
拖拽手柄 → 字符级，不扩展
```

`wordRangeAt` 对中文不做词典分词，靠"连续 CJK 字符段"（§40.2）。

### 63.3 手柄吸附

手柄**不跟随手指坐标**，而是吸附到行的起止位置：

```
handleVisualForRange(range, isStart):
    行 = isStart ? 起点所在行 : 终点所在行
    x  = isStart ? 行内起点字符的左边缘 : 行内终点字符的右边缘
    y  = 行顶（起点）/ 行底（终点）
    rect = Rect.fromCenter(x, y, handleSize)
```

不吸附的话，拖动时手柄会在字符之间抖动，视觉上很廉价。

手柄尺寸与触摸热区要分开：

```dart
const kHandleDot = 8.0;        // 视觉直径
const kHandleTouchPadding = 16.0;  // 触摸扩展（阅微的 touchPaddingPx 同义）
```

### 63.4 选区矩形

`selectionLineRects(layout, range)` 产出逐行矩形：

```
对 range 覆盖的每一行：
    lineStart = max(range.start, 行起点)
    lineEnd   = min(range.end,   行终点)
    rect = 从 lineStart 的左边缘 到 lineEnd 的右边缘
           高 = 行高的 1.1 倍，垂直居中对齐字形墨迹
```

三个细节：

1. **跨行断开**：每行一个矩形，不能合并成一整块
2. **跳过占位**：行内图片不参与选区矩形（阅微的 `removeSelectionPlaceholders`）
3. **行高 1.1 倍**：按行框画会盖到上下行的空隙，按墨迹高度又偏小，1.1 是折中

### 63.5 跨页选区

```
选区跨页时：
    当前页只算"与当前页交集"部分的矩形
    拖到页面边缘 → 触发翻页（延时 300ms，避免误触）
    翻页后终点落在新页，重新算当前页矩形
    选区数据始终是 (startLocator, endLocator)，与页无关
```

### 63.6 手柄拖拽的增量更新

拖拽是高频操作，不能每帧重排整页：

```
拖动中：
    只更新 endLocator 与受影响行的矩形
    不重新排版、不重新分页
    每帧只重绘选区图层（独立 RepaintBoundary）
松手：
    落库（若是标注）或直接消失（若是临时选择）
```

选区图层必须与正文图层分离。混在一起的话，拖拽手柄会触发整页重绘，中低端机上会明显掉帧。

## 64. 绘制实现规格

### 64.1 一页的可执行顺序

```
paint(canvas, page):
  1. canvas.save(); canvas.clipRect(内容区)
  2. 页背景（纯色或图片，平铺）
  3. for block in page.blocks:              // 按绘制顺序（= 阅读顺序）
       drawBlock(block)
  4. 装饰层（ruby / 着重号 / 下划线 / 阴影）
  5. canvas.restore()
```

`drawBlock` 内部顺序与阅微的修饰器链一致（`cssTranslate` → `cssMargin` → `cssBoxShadow` → `cssRotate` → `cssBackground` → `cssBorder` → `cssPadding` → 内容）：

```
1. 平移（margin 起点 + 跨页 clipTop 偏移）
2. box-shadow（在背景之下）
3. transform（rotate / translate）
4. 背景（纯色 → 图片 → 渐变，多层按 CSS 顺序）
5. 边框（四边，圆角裁剪）
6. canvas.save(); clipRect(内边距区)
7. 内容（文字行 / 图片 / 表格线）
8. canvas.restore()
```

**阴影必须在背景之前画**（阴影是被背景遮住的下层），边框必须在背景之后（边框压在背景边缘上）。这两条顺序反了视觉上立刻能看出。

### 64.2 文本绘制

两种模式，取决于 S2 结论（§15）：

| 模式 | 做法 | 适用 |
|---|---|---|
| 整行段落 | 每行构造一个 `ui.Paragraph`（子串，`maxWidth: infinity`），`canvas.drawParagraph` | 默认 |
| 逐 run 定位 | 每 run 一个段落，按 run 的 x 偏移逐个绘制 | 需要精确控制字符间距（竖排、字距特殊） |

整行段落模式下行内样式合并进一个 `ParagraphBuilder`，代价是行内样式切换要多 push/pop，收益是绘制调用次数少。

### 64.3 注解绘制顺序

文字画完之后统一处理注解，顺序有依赖：

```
1. 背景高亮（在文字之下，需先于文字绘制 —— 见下）
2. 文字
3. 下划线 / 删除线（drawLine，按行内字符区间分段）
4. 着重号（drawCircle 或绘制字形，位于字符中心或下方）
5. ruby（基字上方或右侧，单独文本绘制）
6. 文字阴影（在文字之下，用 blur + offset 重画一遍）
```

严格说高亮与阴影**在文字之前**，其余在文字之后。实际实现分两趟：

```
趟一：块背景 → 高亮矩形 → 文字阴影
趟二：文字
趟三：下划线 → 着重号 → ruby
```

### 64.4 分层与重绘范围

四层，各自独立 `RepaintBoundary`：

| 层 | 内容 | 何时重绘 |
|---|---|---|
| 背景层 | 页背景图/纯色 | 换书、换主题 |
| 正文层 | 文字、图片、表格 | 翻页、重排 |
| 装饰层 | 高亮、下划线、ruby | 标注变更 |
| 交互层 | 选区、手柄、菜单 | 每帧（拖拽时） |

分层的目的是把高频更新的交互层与昂贵的正文层隔开（§63.6）。

### 64.5 跨页块的绘制

块跨页时按 `BlockSlice` 裁剪：

```
canvas.save()
canvas.clipRect(Rect.fromLTRB(0, -clipTop, width, -clipTop + visibleHeight))
drawBlock(block)                 // 按块的真实坐标画
canvas.restore()
```

即：**块按完整坐标系绘制，由裁剪决定露出哪部分**。不要试图修改块的内部坐标——那样分页器与绘制层要共享一套偏移量，很容易错位。

### 64.6 Paragraph 缓存生命周期

```dart
class ParagraphCache {
  final _byPage = <int, List<ui.Paragraph>>{};   // pageIndex → 行段落
  List<ui.Paragraph> getOrBuild(PageSlice page);
  void evictExcept(Set<int> keep);
}
```

| 事件 | 处理 |
|---|---|
| 翻页 | 保留当前 ±2 页，其余释放 |
| 重排 | 全部释放（行切点变了，旧段落作废） |
| 主题变化（只改颜色） | 保留结构，重建段落（颜色在样式里） |
| 标注变更 | 不释放（标注在装饰层，不影响段落） |

缓存的键是页索引，不是页码——页码会因虚拟页窗口（§17）变化，页对象本身不变。

### 64.7 图片绘制

```
canvas.drawImageRect(
  image,
  src: 全图,
  dst: 计算出的显示矩形,
  paint: Paint()..filterQuality = FilterQuality.medium,
)
```

`FilterQuality.medium` 是折中：`low` 在缩小时有锯齿，`high` 在低端机上慢。墨纸背景这类大图用 `low` 即可。

不透明图片跳过混合：`Paint()..blendMode = BlendMode.src`，省一层合成（依赖 §50 的透明检测）。

前四步没跑通之前，后面所有绘制都是错的。

## 66. 搜索实现规格

### 66.1 索引构建

与导入期的字符统计合并成一次扫描（§34.4），不额外读盘：

```
for each spine item:
    text = 抽纯文本（跳过 script/style/nav，块间插 \n）
    charStart = 累计字符偏移
    写 spine_items.char_count / char_start
    写 chapter_text(spine_index, text)
    grams = buildGrams(text)
    批量插入 search_grams
```

### 66.2 2-gram 生成规则

```
遍历 text：
  若 c 是 CJK：取 (c, c+1) 若 c+1 也是 CJK，否则跳过
  若 c 是拉丁字母/数字：按"词"切分，词内取 2-gram（保持词内顺序）
  标点、空白：作为分隔符，不产生 gram
```

三种文本的处理差异：

| 文本 | 处理 | 理由 |
|---|---|---|
| 中文 | 逐字 2-gram | 无需分词，任意子串可命中 |
| 英文 | 按词 2-gram | 避免 "ell" 之类的伪匹配 |
| 数字 | 整串作为一个 gram | 页码、年份要整体匹配 |

查询时对关键词做同样切分，取 gram 交集后再做原文验证。

### 66.3 表结构

```sql
-- 章节原文（供上下文提取与验证）
CREATE TABLE chapter_text (
  book_id     INTEGER NOT NULL,
  spine_index INTEGER NOT NULL,
  text        TEXT NOT NULL,
  char_start  INTEGER NOT NULL,
  PRIMARY KEY (book_id, spine_index)
);

-- 2-gram 倒排：gram → 位置
CREATE TABLE search_grams (
  book_id     INTEGER NOT NULL,
  gram        TEXT NOT NULL,        -- 2 字符
  spine_index INTEGER NOT NULL,
  char_offset INTEGER NOT NULL,
  PRIMARY KEY (book_id, gram, spine_index, char_offset)
) WITHOUT ROWID;

CREATE INDEX idx_grams_lookup ON search_grams(book_id, gram);
```

`WITHOUT ROWID` 是必要的：倒排表行数远大于普通表，省掉隐式 rowid 能让索引体积小近一半。

### 66.4 查询

```sql
-- 示意，不是可直接执行的 SQL：gram 交集在 Dart 侧做，见下文
SELECT spine_index, char_offset
FROM search_grams
WHERE book_id = ? AND gram = ?          -- 先取最稀有 gram 的全部命中
ORDER BY spine_index, char_offset;
```

实际实现按 gram 个数分两路：

- gram 数少（≤2）：逐个查，内存里求交集
- gram 数多：取最稀有 gram（先统计 `SELECT COUNT(*)`）作为主查询，其余在内存过滤

```dart
List<SearchHit> search(String query) {
  final grams = buildGrams(query);
  if (grams.isEmpty) return [];
  final rarest = _pickRarestGram(grams);
  final candidates = _queryGram(rarest);              // 已排序
  return candidates
      .where((c) => _verify(c, query))                // 原文子串校验
      .map((c) => _hit(c, query))                     // 带上下文
      .toList();
}
```

**必须做原文校验**：2-gram 交集只是候选集，同一组 gram 可能对应不同字符串。

### 66.5 上下文与定位

```
上下文 = text[max(0, offset-12) .. offset + len + 12]
定位   = Locator(spineIndex, charOffset)  → 查导入期存的"偏移 → 节点路径"映射（§29.3）
```

`chapter_text` 表在搜索结果点击后可释放——原文缓存只在导入与搜索期间需要，读完就删，别常驻内存。

### 66.6 性能

| 指标 | 目标 | 手段 |
|---|---|---|
| 建索引（50 万字） | < 3s | 批量事务插入，每 5000 行提交 |
| 查询 | < 100ms | 稀有 gram 优先 + 原文校验 |
| 结果分页 | 每页 50 条 | `LIMIT`/`OFFSET`，首屏先出前 20 |
| 索引体积 | ≈ 原文 2 倍 | 中文 2-gram 的固有代价 |

大书（500 万字）的结果列表要支持中断：查询放在可取消任务里，用户改动关键词时取消上一次。

### 66.7 FTS5 降级路径

若 SQLite 编译不支持 FTS5：

```sql
CREATE VIRTUAL TABLE chapter_fts USING fts5(...)   -- 失败
```

退回到上面这套 `search_grams` 表——**它本来就是不依赖 FTS5 的方案**，FTS5 只是可选的加速。这一点在 M0 的依赖验证里要确认一次（`sqlite3_flutter_libs` 的编译选项），但无论结果如何设计方案不变。

## 67. 无障碍实现规格

### 67.1 语义树构建时机

每页排版完成后构建一次，随 `PageSlice` 一起缓存：

```dart
List<CustomPainterSemantics> buildSemantics(PageSlice page) {
  final nodes = <CustomPainterSemantics>[];
  nodes.add(_pageNode(page));                    // 页级
  for (final (i, block) in page.blocks.indexed) {
    if (block.kind == BlockKind.image) {
      nodes.add(_imageNode(block, i));
    } else if (block.text.trim().isNotEmpty) {
      nodes.add(_textNode(block, i, page));
    }
  }
  return nodes;
}
```

### 67.2 节点属性

```dart
CustomPainterSemantics(
  rect: block.paintRect,
  properties: SemanticsProperties(
    label: block.text,
    textDirection: TextDirection.ltr,
    isHeader: block.isHeading,                 // h1..h6
    sortKey: OrdinalSortKey(i.toDouble()),
    customSemanticsActions: _actionsFor(block),
  ),
)
```

三类补充信息：

| 情况 | 处理 |
|---|---|
| 块内有高亮/笔记 | label 末尾追加「，含 N 条笔记」 |
| 图片 | label 取 `alt`，无 `alt` 时用「图片」 |
| ruby 注音 | label 用基字文本，注音并入括号（`汉字（かんじ）`风格可选） |

### 67.3 阅读顺序

`sortKey` 必须按阅读顺序，竖排要反过来：

```
横排：块按自上而下 → sortKey = 块序号
竖排：块按自右向左的列序 → sortKey = 列起始 x 降序映射的序号
```

实现上不要依赖"绘制顺序恰好等于阅读顺序"——两者在竖排下不一致。排版阶段就给每个块算好 `readingOrder` 序号，绘制与语义各自用它。

### 67.4 自定义动作

```dart
static final nextPage = CustomSemanticsAction(label: '下一页');
static final prevPage = CustomSemanticsAction(label: '上一页');
static final copyBlock = CustomSemanticsAction(label: '复制本段');
static final highlightBlock = CustomSemanticsAction(label: '高亮本段');
static final speakBlock = CustomSemanticsAction(label: '朗读本段');
```

挂在页级节点的是翻页，挂在块级节点的是复制/高亮/朗读。

**无障碍模式下的手势要让位**：单指滑动交给读屏，翻页只能走 action 或音量键。不要试图同时支持两套手势，冲突时读屏优先。

### 67.5 播报

```dart
// 翻页后
SemanticsService.announce('第 $page 页，共 $total 页', TextDirection.ltr);
```

只在无障碍开启时播报（`MediaQuery.accessibleNavigation`），否则会干扰普通用户。

### 67.6 焦点与滚动

TalkBack 的焦点框由 `rect` 决定。三个要求：

1. `rect` 必须是**本页可见部分**的矩形（跨页块用裁剪后的矩形，不是块的真实外接框）
2. 焦点不能在页外，翻页后焦点要重置到新页首块
3. 块很高时（整屏一段）`rect` 可以超过页面高度，但不能为负

### 67.7 验收脚本

每次发布前在真机上跑一遍，逐项记录：

```
1. 开启 TalkBack，从书首开始连续朗读到章末
2. 每页焦点按阅读顺序推进，无跳跃
3. 页级节点能"下一页/上一页"
4. 块级节点能复制、高亮、朗读
5. 图片节点有可读描述
6. 竖排书的节点顺序正确
7. 翻页有页码播报
8. 关闭无障碍后，播报与手势都恢复正常
```

第 6 条是竖排专项，横排正常不代表竖排正常——语义顺序是按 `readingOrder` 走的，竖排的 `readingOrder` 与绘制顺序不同源，最容易漏。

## 68. 字体实现规格

### 68.1 三条注册路径

| 来源 | 时机 | 命名 |
|---|---|---|
| 书内 `@font-face` | 解析该书 CSS 时收集，允许内嵌字体开关打开才注册 | `bi_<bookId>_<n>`（book inline） |
| 内置字体（assets） | 应用启动 | `builtin_song` / `builtin_kai` / `builtin_hei` |
| 用户导入字体 | 用户添加时 | `user_<fontId>` |

阅微的 `FontProvider.attach(cssPath, fontFaceRules)` 只解析三个字段：`font-family`、`font-weight`、`src`。`src` 只支持 `url(...)` 本地文件，不支持 `local()` 与 `unicode-range`。

### 68.2 字族命名与样式映射

Flutter 的 `FontLoader` 以 **family 为单位**加载字节，字重由字体文件自身的 OS/2 表决定（S5 待验证）。两种方案：

**方案 A（默认，若 S5 通过）**：同一 family 注册多个文件

```dart
final loader = FontLoader('bi_1_0');
loader.addFont(_load('fonts/body-regular.ttf'));
loader.addFont(_load('fonts/body-bold.ttf'));
await loader.load();
// 样式里直接写 TextStyle(fontFamily: 'bi_1_0', fontWeight: FontWeight.w700)
```

**方案 B（S5 不通过时）**：按字重拆 family 名

```dart
// 注册为 bi_1_0_400 / bi_1_0_700
// 样式计算阶段按 font-weight 选出 family 名
String familyFor(int bookId, int fontIndex, int weight) =>
    'bi_${bookId}_${fontIndex}_${_bucket(weight)}';   // bucket: 400/700 两档
```

方案 B 要在 `ComputedStyle` 里把 `font-family` 提前解析成具体 family 名，多一层映射，但行为确定。

### 68.3 中文别名映射

书里写 `font-family: 宋体` 的书非常多，必须有别名表落到内置字体：

```dart
const _alias = {
  // 宋体系
  '宋体': 'builtin_song', 'simsun': 'builtin_song', 'songti': 'builtin_song',
  'st': 'builtin_song', 'song': 'builtin_song', 'serif': 'builtin_song',
  // 楷体系
  '楷体': 'builtin_kai', 'kaiti': 'builtin_kai', 'kt': 'builtin_kai',
  'stkaiti': 'builtin_kai', 'kai': 'builtin_kai',
  // 黑体系
  '黑体': 'builtin_hei', 'simhei': 'builtin_hei', 'heiti': 'builtin_hei',
  'sans-serif': 'builtin_hei',
};
```

匹配规则：**先全等、再小写全等、最后去空格比较**。不要做包含匹配——`宋体黑` 这种名字会被错误命中。

### 68.4 回退链

```dart
TextStyle(
  fontFamily: primary,
  fontFamilyFallback: [userFont, builtinSong, builtinHei, 'Noto Sans CJK SC'],
)
```

按段指定字族优于整段回退：CJK 段走中文字族，拉丁与数字段走西文字族，避免中文全角标点被西文字体画成异形（§28.3）。具体的分段算法见 §77。

实现位置在 `LineBreaker` 之前：文本先按脚本切成 run，每个 run 带自己的 family，再交给测量。

### 68.5 加载时机与"字体后到"问题

这是实际会踩的坑：内嵌字体加载是异步的，若排版先跑，用的是回退字体；字体到位后**必须重排**，否则字形与行宽都不对。

策略：

```
打开书：
  1. 启动字体加载（书内 @font-face，最多等 300ms）
  2. 超时则先排版（用回退字体），字体到达后标记 needRelayout
  3. 若用户在 reading，等当前章翻页后再静默重排；
     若正停在某页，重排后用 CFI 恢复到原位
```

不做"边读边换字体"——那会让当前页文字跳动。宁可延迟到翻页。

### 68.6 失败与降级

| 情况 | 处理 |
|---|---|
| 文件不存在 | 跳过该 `@font-face`，记警告，回退链继续 |
| 格式不支持（ttc/woff/woff2） | 同上，并在书籍详情里提示"部分字体无法使用" |
| 加载超时（> 3s） | 放弃该书内字体，视为不可用 |
| 字体文件损坏 | `FontLoader.load()` 抛错，捕获后降级 |

**失败必须不阻断阅读**。字体是装饰，正文可读才是底线。

### 68.7 解混淆后的字体

字体解混淆（§5.3）产出的文件写在 `books/<uuid>/content/_deobf/`，注册时用解混淆后的路径。原文件保留不动。

第一次打开需解密（几十毫秒到几百毫秒），结果按文件 hash 缓存，第二次打开直接用。

### 68.8 版权提示

内嵌字体是书籍资产，导出/分享含内嵌字体的书可能侵权。产品层要在"书籍详情"里标明"本书含内嵌字体"，但**不做提取导出**。

## 69. TTS 实现规格

### 69.1 状态机

```dart
enum TtsState { idle, talking, paused, error }

class TtsController {
  TtsState state = TtsState.idle;
  List<Sentence> queue = [];
  int cursor = 0;
}
```

合法迁移：

```
idle → talking     play()
talking → paused   pause()
paused → talking   resume()
talking → idle     stop() / 读完
任意 → error       引擎报错
error → idle       reset()
```

### 69.2 切句与队列

```
play():
  1. 取当前页所有句（§40.3 的句界规则），按 readingOrder 排序
  2. 追加到 queue 尾部（若已有队列则接着读）
  3. 逐句送系统 TTS，每句一个 utterance
```

**按页切，不按章切**：整章预切会产生上千句，内存与启动成本都不值（§41.4）。翻页时追加下一页的句。

跨页连续：

```
读完当前页最后一句 → 自动翻页 → 追加新页的句 → 继续
```

翻页由 TTS 驱动时**必须禁用翻页动画**，否则动画未完成就开始朗读下一页，视觉与听觉错位。

### 69.3 高亮同步

```
句子开始 → 高亮该句（用装饰层，不是标注层）
         → 确保可见：若句子不在当前页则先翻页
句子结束 → 清除高亮，推进 cursor
```

高亮是**临时装饰**，不写入标注表。用独立的 `ttsHighlight` 状态，避免与用户高亮混淆。

### 69.4 平台接口

```dart
abstract interface class TtsEngine {
  Future<void> init(String language);
  Future<void> speak(String text);
  Future<void> stop();
  Future<void> setRate(double rate);
  Stream<TtsEvent> get events;   // start / complete / error
}
```

宿主实现用 `flutter_tts`（移动端）。注意它的 `speak` 是异步但不等待完成，必须靠 `setCompletionHandler` 回调推进队列，不能靠 `await`。

### 69.5 中断与恢复

| 事件 | 处理 |
|---|---|
| 来电 / 其他应用抢音频焦点 | 暂停，记住当前句索引 |
| 应用进后台 | 继续播（需后台音频会话），或按设置暂停 |
| 锁屏 | 继续播（同上） |
| 用户翻页 | 停止朗读，不自动跟读（除非开了"跟随翻页"） |
| 切书 | 停止并清空队列 |

**恢复按句开始位置**，不按句中——从句中继续会听起来很怪。

### 69.6 后台播放配置

- iOS：`AVAudioSession.Category.playback`，Info.plist 声明 `audio` 后台模式
- Android：前台服务 + `FOREGROUND_SERVICE` 权限，通知栏提供暂停/继续

这部分是平台代码，`reader_core` 不涉及，由宿主层实现。

### 69.7 错误处理

| 情况 | 提示 | 后续 |
|---|---|---|
| 系统无 TTS 引擎 | 「设备未安装语音引擎」 | 引导去系统设置 |
| 语言包缺失 | 「缺少中文语音包」 | 引导下载 |
| 朗读中引擎崩溃 | 「朗读已停止」 | 重置为 idle，可重试 |

错误不能静默——用户点了播放却没声音，必须给明确原因。

### 69.8 与进度的关系

朗读不写进度（否则用户听书会覆盖阅读位置）。但提供选项「朗读位置同步为阅读进度」，默认关闭。

手动关闭朗读时，跳转到当前朗读句所在位置——这是用户期望的「听到哪就看到哪」。

## 70. 版本与迁移

### 70.1 两个版本号，别混用

| 版本 | 位置 | 何时变 | 影响 |
|---|---|---|---|
| **数据库 schema 版本** | 全局（drift `schemaVersion`） | 表结构变更 | 启动时全库迁移 |
| **书排版版本** | `books.layout_version` | 排版引擎算法变更 | 该书重新分页，不动数据 |

混用会出两类问题：把排版版本放进 schema 版本，会导致改一次排版算法就要写一个数据库迁移；把 schema 版本放进 books，会导致每本书的表结构可能不同，无法统一查询。

### 70.2 数据库迁移

```dart
@override
MigrationStrategy get migration => MigrationStrategy(
  onCreate: (m) => m.createAll(),
  onUpgrade: (m, from, to) async {
    var v = from;
    if (v < 2) { await m.addColumn(books, books.layoutVersion); v = 2; }
    if (v < 3) { await m.createTable(searchGrams); v = 3; }
    // 每步单调递增，不合并
  },
  beforeOpen: (details) async {
    await customStatement('PRAGMA foreign_keys = ON');
  },
);
```

三条纪律：

1. **每步单调递增，不合并**。用户可能从 v1 直接升到 v5，必须逐级执行。
2. **不删列**。SQLite 删列要重建表，风险高。改为"标记废弃 + 不再读写"。
3. **索引单独迁移**，与建表分开，避免大表加索引时锁太久。

### 70.3 排版版本

```dart
const kLayoutVersion = 3;   // 行分割或分页算法改动时 +1
```

启动或打开书时比较：

```
若 book.layout_version < kLayoutVersion：
    清该书的页缓存与进度页号（保留 CFI）
    下次打开时重新分页
    更新 layout_version
```

**进度只存 CFI，所以重排后位置不丢**——这是当初选 CFI 做唯一坐标的收益（§6.1）。

### 70.4 迁移测试

```
1. 准备 v1 到 vN 各版本的种子数据库（每次改 schema 都要留一份）
2. 对每个版本执行 迁移 → 校验：
   - 表结构符合预期（PRAGMA table_info）
   - 关键数据行数与抽样内容一致
   - 外键完整（PRAGMA foreign_key_check）
3. 迁移失败时回滚到备份，不能留半迁移状态
```

种子库文件放进 `test/fixtures/db/v1.db` 这类路径，随代码提交。没有种子库的迁移只能靠手测，迟早出事。

### 70.5 备份与回滚

打开数据库前先复制一份 `app.db` 到 `app.db.bak`（仅在有迁移时）。迁移抛错时用备份替换并降级为"只读书库元数据"模式，不要让应用起不来。

普通升级不需要备份，只有 `from < to` 且存在破坏性操作时才备份。

## 71. 启动与生命周期

### 71.1 冷启动顺序

```
main()
 1. WidgetsFlutterBinding.ensureInitialized()
 2. 打开数据库 → 迁移（阻塞，通常 < 100ms）
 3. 清理孤儿目录（异步，不阻塞 UI）
 4. 载入设置（同步读 SharedPreferences/DB）
 5. runApp(书库页)
```

第 3 步必须异步：遍历 `books/` 目录删孤儿，书多时很慢，不能让用户盯着白屏。

### 71.2 打开一本书

```
ReaderPage.initState()
 1. EpubDocument.open(bookId)          ← 索引已在库里，成本低
 2. 字体子系统启动加载（最多等 300ms，§68.5）
 3. VirtualPager.recenter(lastCfi)
 4. 首屏页可读即 setState 显示          ← 不等全书排完
 5. 后台预取前后章
```

第 4 步是体验的关键：**首屏只等第一页**。

### 71.3 资源释放

| 时机 | 释放 |
|---|---|
| 关闭阅读页 | 页渲染缓存、Paragraph 缓存、分页结果、书内字体（可选） |
| 切换书籍 | 上一条 + 排版树、样式缓存（按 bookId 分区，见 §52.5） |
| 进入后台且内存告警 | 图片位图缓存、页渲染缓存 |

书内字体卸载要谨慎：重新加载要几百毫秒，如果用户只是切出去看一眼再回来，卸载反而更慢。**默认不卸载，只在切书时清**。

### 71.4 生命周期与取消

所有异步任务都要能取消，且与页面生命周期绑定：

```dart
class ReaderSession {
  final CancelToken token = CancelToken();
  void dispose() => token.cancel();
}
```

- 分页任务、字体加载、图片解码、搜索查询都挂在这个 token 上
- `dispose` 后到达的回调用 token 判断并丢弃，不碰已销毁的 state
- 跳转类任务另加自增 token 防竞态（§17.4 第 5 条）

### 71.5 异常兜底

```
FlutterError.onError       → 记录并上报（本地日志，不上传内容）
PlatformDispatcher.onError → 同上，尽量保持页面可用
```

阅读页的构建异常不能整页白屏：外层包一个错误边界，显示「本页渲染失败」+ 「重试」+ 「跳到下一章」。破损书（§55 的 L2/L3）必然会在某页触发一次异常，兜底不到位就是闪退。

### 71.6 启动性能预算

| 阶段 | 预算 |
|---|---|
| 到书库首帧 | < 800ms |
| 书库可交互 | < 1.2s |
| 打开书到首屏可读 | < 1s（§44.2） |
| 冷启动总内存 | < 120MB |

## 72. 文档树构建规则

### 72.1 不是按标签分派，是按 display 分派

阅微的 `BodyDom.convertToDom` 只对两个标签做特殊处理（`li` 的项目符号、`img` 的占位），其余全部按**计算后的 `display`** 决定节点类型。

这个选择是对的，我们要沿用：

```
标签
  → UA 默认表与作者样式算出 ComputedStyle
  → 读 style.display
  → 决定节点类型
```

好处是 `display:block` 的 `<a>`、`display:none` 的 `<p>`、`display:table` 的 `<div>` 都能正确处理——按标签分派做不到。

### 72.2 节点类型分派

| `display` | 节点类型 | 说明 |
|---|---|---|
| `none` | 跳过（连同子树） | 不产生任何节点 |
| `block` / `flex` / `list-item` | `BlockNode` | 块级容器，参与块流 |
| `inline` / `inline-block` | 文本 run 或 `TextBlockNode` | 行内内容聚合 |
| `table` / `table-row` / `table-cell` | `TableNode` 及其子结构 | 走表格布局 |
| `inline-block`（含图片） | `InlinePlaceholder` | 参与行内流的占位 |

### 72.3 文本聚合

相邻的行内节点要合并进**同一个** `TextBlockNode`，不能一个 `<span>` 一个块：

```
<p>从前有<span>座山</span>，山里有座庙</p>

正确：一个 TextBlockNode，text = "从前有座山，山里有座庙"，
      runs = [0..3 正常, 3..6 正常（span 无样式差异时也合并）, 6..end 正常]
错误：三个 TextBlockNode
```

聚合规则：

1. 连续的文本节点与行内元素 → 同一 `TextBlockNode`
2. 遇到块级元素（含 `display:block` 的 `span`）→ 断开，开启新块
3. `display:none` 的元素 → 跳过，不打断聚合
4. 行内图片 → 在 `TextBlockNode` 里占一个字符位，记入 `placeholders`

聚合错了的直接后果是"一段话被切成几页"，而且 CFI 偏移会错位。

### 72.4 空白处理

| 位置 | 处理 |
|---|---|
| 标签之间 | 折叠成一个空格；`white-space: pre` 时保留 |
| 块首尾 | 去掉 |
| 行内元素边界 | 至少保留一个空格（否则 `a<b>b</b>` 会粘成 `ab`） |
| 换行符 | 折叠为空格；`<br>` 转成显式换行标记 |

中文书里这条尤其重要：XHTML 源码里标签间的换行缩进如果原样保留，正文会出现大量诡异空格。

### 72.5 特殊节点

| 来源 | 处理 |
|---|---|
| `<img>` / `<image>` | `InlinePlaceholder` 或块级 `ImageNode`，取决于 display |
| `<table>` | `TableNode`，内部转换行列、跨行跨列 |
| `<li>` | 按 `list-style-type` 生成前缀文本（`•`、`1.`），**插在 `li` 的第一个子文本前**，不单独成节点 |
| `<ruby>` | 基字进文本，注音进 `rubyMap`（键 = 基字起始偏移） |
| `<sup>` / `<sub>` | 行内 run，带 `baselineOffset` |
| `<br>` | 显式换行标记（影响行分割与对齐） |
| `svg` | 按占位处理，绘制走矢量路径（§33） |

`<li>` 的前缀生成依赖元素兄弟序号（`ol` 的 `start` 属性也要算进去），不能只看 `li` 自身。

### 72.6 锚点与 id

所有带 `id` 的元素在构建时登记 `id → 节点`，供内部跳转（脚注、目录）使用。登记表挂在 `SpineDocument` 上，随章释放。

### 72.7 CFI 绑定时机

每个节点创建时立即计算并绑定 CFI（§53.2 第 1 条），之后布局与绘制不再重算。绑定的输入是：

```
spineIndex（= itemref 步进，见 §34.2）
父节点的 CFI 步骤链
本节点在同级元素中的序号（偶数步）
```

文本节点额外带字符偏移。


这样"标签的默认语义"只有一个来源，排查样式问题不用两头找。

### 73.3 `body` 上那条 `!important` 的用意

```
body { font-size: 1em !important }
```

优先于书内 `body { font-size: 0.8em }`，作用是**把正文字号锚定在阅读器的根字号上**。

不加这条的话，用户把字号调到 24，书里写死 12px 的 `body` 会让整本书保持 12px——用户会认为"字号调节失效"。这是阅读器必须覆盖的少数几处之一。

### 73.4 与阅读器覆盖层的关系

UA 表是层叠的**第一层**（§7.2），阅读器覆盖层是最后一层。两者的分工：

| 层 | 管什么 |
|---|---|
| UA 表 | 标签的默认语义（标题多大、段落有没有间距） |
| 阅读器覆盖层 | 用户的排版偏好（字号、行高、段距、字距、字体、颜色） |

字号这条两处都碰：UA 表把 body 锚到 1em，覆盖层再把 1em 定义成用户字号。缺一层都不对。

## 74. 手势与交互规格

### 74.1 点击区域

阅微的 `TapGesturesBox` 用的是 `detectTapGestures` + `awaitPointerEvent` 底层组合，配置项只有 `clickLeftNextPage`（左侧点击是否翻下一页）与 `gesturesEnabled`。

我们的区域模型：

```
把内容区按水平方向切成三块：左 30% / 中 40% / 右 30%
左区  → 上一页（若 clickLeftNextPage 为 true，改为下一页）
中区  → 呼出/隐藏工具栏
右区  → 下一页（若 clickLeftNextPage 为 true，改为上一页）
```

`clickLeftNextPage` 是给左利手与特定阅读习惯留的开关，很多中文阅读器都有。

竖排（`vertical-rl`）时左右语义要反转：右区是上一页、左区是下一页——因为竖排书从右往左读，翻页方向本来就相反（§32.5）。

### 74.2 手势表

| 手势 | 行为 | 备注 |
|---|---|---|
| 单击左/中/右 | 上下页 / 工具栏 | 区域见上 |
| 双击 | 无（阅读器里双击不常用） | 保留给图片预览放大 |
| 长按（500ms） | 进入选区，选中词 | §63.2 |
| 长按拖动 | 扩展选区 | 与翻页手势互斥 |
| 横向滑动 | 翻页（跟手位移 + 松手判定） | 见 74.3 |
| 纵向滑动 | 无（分页模式） | 滚动模式才启用 |
| 双指缩放 | 仅图片预览层启用 | 正文不支持缩放（会破坏分页） |
| 音量键 | 翻页（可关） | `volumeKey` 配置 |
| 系统返回手势 | 退出阅读 → 回书库 | 边缘滑动区域要让给系统 |

### 74.3 滑动翻页的判定

```
拖动阶段：页码跟手位移，位移量 = dx
松手判定（满足任一即翻页）：
    位移 > 屏幕宽 × 0.3
    速度 > 800 px/s
否则回弹到当前页
```

两个参数要分开可调：`0.3` 是距离阈值，`800` 是速度阈值。只有距离或只有速度都不够——慢慢拖到一半（距离不够但意图明确）和快速轻扫（距离不够但速度够）都应该翻页。

### 74.4 状态机

```dart
enum PagerState { idle, dragging, settling, animating }
```

```
idle → dragging     按下并移动超过 8px
dragging → settling 松手（回弹或翻页动画）
settling → idle     动画结束
idle → animating    点击区域翻页（无拖动）
animating → idle    动画结束
```

`dragging` 与 `animating` 期间**不接受新手势**，否则连续快速翻页会串页。

### 74.5 冲突与优先级

从高到低：

```
1. 无障碍模式        → 自定义手势全部让位，翻页走 CustomSemanticsAction（§67.4）
2. 选区模式          → 只响应选区相关手势，点击空白退出选区
3. 图片预览层        → 双指缩放、单击关闭
4. 工具栏弹出        → 点击外部关闭工具栏，不翻页
5. 常规翻页          → 上面都不满足时才生效
```

这个顺序必须写死在代码里，不能靠"谁先注册谁先响应"——那是不可预测的。

### 74.6 与翻页动画的耦合

- 拖动阶段只做位移，**不改变动画进度**（动画由松手后的 settling 阶段接管）
- 覆盖式翻页（Overlay）在拖动时下一层页提前绘制，但只画不交互
- 无动画翻页（Static）在点击时直接切页，拖动仍可用于翻页但无跟手效果

TTS 驱动的翻页必须禁用动画（§69.2），此时手势翻页仍可用，但会打断朗读。

### 74.7 参数表

| 参数 | 默认值 | 可配置 |
|---|---|---|
| 左右区宽度占比 | 30% | 是 |
| 中区呼出工具栏 | 是 | 是 |
| `clickLeftNextPage` | 否 | 是 |
| 滑动翻页距离阈值 | 屏宽 30% | 否 |
| 滑动翻页速度阈值 | 800 px/s | 否 |
| 长按触发时长 | 500ms | 否 |
| 拖动起点容差 | 8px | 否 |
| 音量键翻页 | 开 | 是 |
| 跟手位移阻尼 | 1.0（无阻尼） | 否 |

「可配置」列是用户能改的，其余是内部常量。常量集中放一处，别散落在手势回调里。

### 74.8 边缘手势冲突

Android 的系统返回手势占屏幕左/右边缘约 20px。我们的翻页区域如果覆盖到这里，用户会误触退出。

处理：**左右各留 24px 的安全边**，这部分不响应翻页手势。iOS 的 `UIScreenEdgePanGestureRecognizer` 同理。

## 75. 翻页动画实现规格

### 75.1 三种形态

| 形态 | 实现方式 | 适用 |
|---|---|---|
| `static` | 直接换页，无过渡 | 墨水屏、低端机、TTS 驱动 |
| `overlay` | 新页从边缘推入，旧页被覆盖 | 默认 |
| `curl` | 页面卷曲仿真 | 可选，性能要求最高 |

### 75.2 覆盖式（overlay）

位移与绘制：

```
拖动进度 t ∈ [0,1]（dx / 屏宽）
当前页：translate(-t * width * direction)
下一页：translate((1-t) * width * direction)，先于当前页绘制（在下层）
方向：横排下一页从左进（direction = 1）；竖排反向
```

阴影：旧页右（或左）边缘画一条渐变阴影，宽 24px，alpha 随 `t` 从 0 到 0.3。阴影用 `LinearGradient` 一次绘制，不要逐帧生成位图。

松手后的 settling：

```
t > 0.3 或 v > 800px/s → 动画到 t = 1（翻页完成）
否则                    → 动画回 t = 0（回弹）
曲线：easeOutCubic，时长 200ms（回弹 180ms）
```

**下一页必须在拖动开始时就已经排好**。如果拖到一半才开始排版，会出现"页面空白跟着手指走"。这就是虚拟页窗口（§17）要保证前后各 ≥3 页的原因。

### 75.3 卷曲式（curl）

阅微的做法是**先把当前页截图成位图再对位图做形变**（`CurlPager_androidKt.captureBitmap`），不对文本做逐字变换。这是关键的性能决策——逐字变换在文本多时会直接掉帧。

我们的实现路径：

```
1. 拖动开始时：RepaintBoundary.toImage() 取当前页快照（一次，约 4～8ms）
2. 把快照切成 N 条竖带（N = 24），每条按卷曲曲线做水平位移与透视缩放
3. 卷起区域露出下一页（同样预截图）
4. 松手判定与回弹同 overlay
```

曲线简化：真正的柱面卷曲要解几何方程，成本高。用**分段贝塞尔近似**（把卷曲边缘当一条参数曲线）视觉上足够，代码量小一个数量级。

性能约束：

| 指标 | 目标 |
|---|---|
| 快照耗时 | < 10ms |
| 每帧变形绘制 | < 8ms |
| 内存 | 两张全屏位图（约 8MB @1080p） |

达不到就降级为 overlay，**不要把卷曲做成可卡顿的选项**。

### 75.4 快照的时机与释放

```
取快照：手势进入 dragging（不是按下时，避免点击也截图）
释放：settling 结束后立即释放 ui.Image
```

忘记释放是常见的内存泄漏点：`ui.Image` 不走 GC，必须显式 `dispose()`。

### 75.5 与手势状态机的衔接

```
idle → dragging   开始截图、准备下一页
dragging          只更新 t，不改动画控制器
settling          动画控制器接管，禁用新手势
idle              释放快照
```

状态机定义见 §74.4。**动画期间不接受新手势**，否则快速连翻会丢页。

### 75.6 降级策略

```
若 设备判定为低端（内存 < 3GB 或首帧耗时超阈值）→ 强制 static
若 用户开启"减少动画"（系统无障碍设置）        → 强制 static
若 TTS 正在朗读                                → 强制 static
```

系统"减少动画"设置要从 `MediaQuery.disableAnimations` 读，不要自己造开关。

### 75.7 竖排与方向

竖排（`vertical-rl`）的翻页方向与横排相反：下一页从左侧进入。所有位移公式里的 `direction` 由 `writing-mode` 决定，不写死在动画代码里。

## 76. 进度与目录跳转实现规格

### 76.1 进度的定义

```
percent = (章前累计字符 + 章内已读字符) / 全书字符总数
```

三个量都在导入期算好并存在 `spine_items`（§36.1）：

| 字段 | 含义 |
|---|---|
| `char_count` | 本章正文字符数 |
| `char_start` | 本章在全书中的起始偏移 |

`章内已读字符` 由当前页的 `start` CFI 换算：CFI → 文本节点 + 字符偏移 → 加上本章内该节点之前的累计字符。这个累计在排版时顺带记录，不额外扫描。

### 76.2 排除项

不参与进度计算的：

| 项 | 原因 |
|---|---|
| 封面页 | 否则进度起点不在 0 |
| 后壳页 | 否则读完了也到不了 100% |
| `linear="no"` 的 spine 项 | 不是主线内容 |
| nav 文档 | 目录页不算正文 |

排除后要在书库卡片上仍显示"总字数"，那个数字包含全部正文。

### 76.3 量化

百分比按整数显示，避免浮点抖动：

```dart
int percentInt = (percent * 100).round();
```

阅微的 `quantize(value, factor = 100)` 就是 `roundToInt(value * factor)`，同一做法。

**只显示整数，但存储保留小数**——否则同一位置反复进出会因四舍五入漂移。

### 76.4 目录跳转

```
1. 目录项自带 cfi（构建时算好，§35.3）
2. VirtualPager.recenter(cfi)
3. recenter 内部：定位 spine → 分页该章 → 建立映射 → 推送页码修正
```

二分查找当前章：

```
chapters 按 (spine, 字符偏移) 升序排列
找到最后一个 cfi <= 当前位置的项
若该项 depth > 1（子节），仍算当前章——高亮用最深的那个
```

"当前章"的判定用**当前位置之前最近的目录项**，不是"包含当前范围的目录项"——目录项是一个点（锚点），不是一个范围。

### 76.5 跳转的边界

| 情况 | 处理 |
|---|---|
| 目标 CFI 在未加载章 | 先分页该章再跳，显示 loading（§27.2） |
| 目标是章首（无 fragment） | 用该章 spine 起始 CFI |
| 目标 CFI 解析失败 | 回退到该章章首，并记一条警告 |
| 目标超出 spine 范围 | 钳到最后一章 |
| 跳转中用户又点了别的 | 自增 token，旧任务丢弃（§17.4） |

### 76.6 写入与节流

```
翻页 → 更新内存里的 lastCfi
     → 节流 1s 写库（避免每翻一页写一次）
     → 退出阅读页时强制写一次
```

朗读**不写进度**（§69.8），除非用户显式开启"朗读位置同步"。

### 76.7 重排后的百分比变化

字号改变会改变分页，但因进度用字符偏移计算，**百分比几乎不变**（只会在章边界附近有极小差异）。这是选字符偏移而非页数进度的第二个收益（第一个是重排后能恢复位置）。

验收方法：同一本书在 5 档字号下，翻到同一段文字，百分比差异应 < 1%。

## 77. 中英混排与脚本分段实现规格

### 77.1 阅微的分段依据：逐字字形覆盖

`ContentDom.buildScriptRanges` 的实现不是按 Unicode 区块切分，而是**逐字符查字体覆盖**：

```
for i in 0..text.length:
    c = text[i]
    for family in familyNames:          // 用户/书内声明的字体族列表
        if embeddedHasGlyph(family, c):  // 查该 family 的 cmap
            选定 family; break
    if 本字 family != 上一字 family:
        flush 一个 SpanStyle 区间（覆盖上一段连续同 family 的字符）
```

也就是说：**分段依据是"这个字形该由哪个字体渲染"，不是"这个字符属于哪个语种"**。这比按码点区块切分更准——同一个「中」字，宋体有就归宋体，没有才回退。

### 77.2 Flutter 侧的限制与两条路

Flutter **不暴露字形表**，拿不到 `hasGlyph(codepoint)`。两条替代路径：

**路径 A（一期采用）：按 Unicode 区块分段**

```dart
enum ScriptClass { cjk, latin, digit, punct, other }

ScriptClass classify(int cp) {
  if ((cp >= 0x4E00 && cp <= 0x9FFF) ||   // CJK 统一表意
      (cp >= 0x3400 && cp <= 0x4DBF) ||   // 扩展 A
      (cp >= 0xF900 && cp <= 0xFAFF) ||   // 兼容表意
      (cp >= 0x3040 && cp <= 0x30FF) ||   // 日文假名
      (cp >= 0xAC00 && cp <= 0xD7AF))     // 韩文
    return ScriptClass.cjk;
  if (_isAsciiDigit(cp)) return ScriptClass.digit;
  if (_isAsciiLetter(cp)) return ScriptClass.latin;
  if (_isCjkPunct(cp)) return ScriptClass.punct;   // 。，、；：？！「」等
  return ScriptClass.other;
}
```

连续同类合并成 run，每个 run 指定 family：

| 类别 | family |
|---|---|
| `cjk` | 中文字族 |
| `latin` / `digit` | 西文字族（无则用中文字族的拉丁字形） |
| `punct` | **必须中文字族**（见 77.4） |
| `other` | 当前段落的 family |

**路径 B（二期可选）：自建 cmap 覆盖检测**

解析 TTF/OTF 的 `cmap` 表（format 4 与 12），得到码点集合，再按"是否有字形"选 family。工作量约 300 行，收益是缺字场景下能精确回退。

一期不做，因为路径 A + `fontFamilyFallback` 已经能覆盖绝大多数情况。

### 77.3 与断行的交互

run 边界影响断行：

```
断行以 cluster 为单位，cluster 不跨 run
西文词如果跨 run（例如部分字符用了另一字体），按 run 边界切开
```

极端情况：一个英文单词里有 3 个字符用了回退字体，会切成 4 个 run，但**断行仍按整词判定**——否则单词中间会出现断点。

实现上：cluster 切分先于 run 切分，run 只是给 cluster 附加样式。

### 77.4 中文标点必须由中文字体渲染

这是分段最实际的目的。若标点落到西文字体：

- 全角标点会被画成半角或异形
- 逗号句号的字面位置偏移，行内视觉基线不齐

所以 `punct` 类强制走中文字族，即使它出现在一段英文里。

### 77.5 ASCII 标点与全角标点要分开

| 字符 | 归类 | 字体 |
|---|---|---|
| `,` `.` `;` | `latin` | 西文字族 |
| `，` `。` `；` | `punct` | 中文字族 |

混排文本里两者都可能出现，不能一律按"标点"处理。

### 77.6 回退链的落点

```dart
TextStyle(
  fontFamily: runFamily,
  fontFamilyFallback: [userFont, bookFont, builtinSong, 'Noto Sans CJK SC'],
)
```

`fontFamilyFallback` 是 Flutter 引擎级的兜底：主字体缺字时按顺序找。它比我们逐字判断更可靠，但只在"整段都用同一个 family"时有效。

两者结合：**分段决定主 family，fallback 处理意外缺字**。

## 78. SVG 渲染实现规格

### 78.1 走哪条路

```
1. 首选 vector_graphics / flutter_svg
2. 解析失败但含合法 path 数据 → 自研极简渲染器（本章）
3. 仍失败 → 占位框 + alt
```

**不预先自研**（§33.2）。本章只定义"需要时的规格"，避免到时候边写边设计。

### 78.2 path 数据解析

```dart
sealed class PathCommand {}
class MoveTo extends PathCommand { final double x, y; }
class LineTo extends PathCommand { final double x, y; }
class CubicTo extends PathCommand { final double x1,y1,x2,y2,x,y; }
class QuadTo extends PathCommand { final double x1,y1,x,y; }
class ArcTo extends PathCommand { final double rx, ry, rot; final bool large, sweep; final double x, y; }
class ClosePath extends PathCommand {}
```

词法分析：

```
循环读字符：
  命令字母（MmLlHhVvCcSsQqTtAaZz）→ 切换当前命令
  数字/符号（含 . - + e）→ 累积成数字
  命令重复（如 "L 10 10 20 20"）→ 后续数字按当前命令的参数个数成组消费
```

相对命令（小写）要累加上一个点。`H/V` 只给一个坐标。`S/T` 是前一条曲线的反射控制点。

### 78.3 圆弧转贝塞尔

`A rx ry rot large sweep x y` 是 SVG 里最麻烦的命令。标准做法是端点参数化转中心参数化：

```
1. 若 rx=0 或 ry=0 或起终点重合 → 当直线处理
2. 求椭圆中心 (cx, cy)：
   用半径平方修正（若半径不足以连接两点，等比放大）
3. 求起始角 θ1 与扫描角 Δθ：
   large/sweep 决定 Δθ 的符号与是否取超过 π 的那段
4. 把 Δθ 切成若干段（每段 ≤ π/2），每段用三次贝塞尔近似：
   α = (4/3) * tan(Δθ_seg / 4)
   控制点 = 端点 ± α * 切线
```

每段不超过 90° 是精度要求：超过后贝塞尔近似误差明显。

### 78.4 viewBox 变换

```
scaleX = width / viewBox.width
scaleY = height / viewBox.height
```

`preserveAspectRatio` 决定是否等比：

| 值 | 处理 |
|---|---|
| 缺省 / `xMidYMid meet` | `s = min(scaleX, scaleY)`，居中 |
| `... slice` | `s = max(scaleX, scaleY)`，居中并裁剪 |
| `none` | 不保持比例，直接用 scaleX/scaleY |

9 种对齐（`xMinYMin` 到 `xMaxYMax`）只是居中偏移量不同，用一张偏移表实现。

### 78.5 描边与填充

| 属性 | 处理 |
|---|---|
| `fill` | 纯色；`none` 时不填充；`currentColor` 取父样式 color |
| `stroke` | 纯色；`none` 时不描边 |
| `stroke-width` | 逻辑像素，随 viewBox 缩放 |
| `stroke-linecap` | butt / round / square 映射到 `StrokeCap` |
| `stroke-linejoin` | miter / round / bevel 映射到 `StrokeJoin` |
| `stroke-dasharray` | 转 dashPath 效果，用 `PathMetric` 分段绘制 |

`fill-rule`（evenodd / nonzero）在 Flutter 里对应 `PathFillType`。

### 78.6 明确不支持

| 特性 | 处理 |
|---|---|
| `filter`（模糊、阴影） | 忽略，绘制纯形状 |
| `mask` / `clipPath` | 忽略 clip，直接绘制 |
| `<text>` | 忽略（字体渲染交给正文引擎，SVG 内文本直接用基字近似不了） |
| `<image>` 嵌套 | 转成普通图片请求 |
| `gradient` 填充 | 一期忽略，用首个色标纯色；二期补 |
| 外部引用 | 忽略，占位 |

### 78.7 性能与缓存

- 解析结果（命令列表）按 resource hash 缓存，绘制时不再解析
- 复杂 path（命令数 > 2000）降级为占位，避免一页卡死
- 按目标尺寸缩放绘制，不预先栅格化成位图（矢量在小尺寸下更清晰）

### 78.8 验收

用 `compatibility-probe.epub` 与两本含 SVG 装饰的样本，逐项确认：

1. 章节花边、分隔线能正常显示
2. `viewBox` 与 `preserveAspectRatio="none"` 的拉伸正确
3. 圆弧类图形无断裂
4. 描边虚线间距合理
5. 解析失败的 SVG 退化为占位而非崩溃

## 79. 实验设计（五个 Spike + 两个确认项）

§15 给了通过标准，这一章给可执行的实验步骤。全部在 M0 的临时工程里做，不写产品代码，产出是**一张结论表**（见 79.7）。

### 79.1 S4 中文避头尾禁则（优先级最高）

**要回答**：Flutter 的文本引擎断行时是否处理中文禁则，还是需要自建断行器。

**准备**：一个最小 Flutter 工程，能跑 `flutter test`；构造下列字符串，容器宽度设为"每行恰好 10 个全角字符"。

**步骤**：

```dart
final painter = TextPainter(
  text: TextSpan(text: case1, style: const TextStyle(fontSize: 16)),
  textDirection: TextDirection.ltr,
)..layout(maxWidth: 160);   // 10 字宽
```

对 §19.1 的 10 个场景逐个渲染，记录每行的首尾字符。

**记录字段**：场景编号 / 每行首字符 / 每行末字符 / 是否出现行首标点 / 是否出现行尾开括号。

**判定**：

| 结果 | 结论 |
|---|---|
| 10 个场景中禁则相关 5 项全部符合 | 走引擎断行 |
| 任一不符合 | 走自建断行器（工作量 +1200 行，§19.2） |

**产出**：`方案/spike/s4-result.md`，含每个场景的首尾字符表。

### 79.2 S5 同一 family 下的多字重

**要回答**：`FontLoader` 在同一 family 注册 regular + bold 两个文件后，`TextStyle(fontWeight: FontWeight.w700)` 是否能选中粗体文件。

**准备**：两个字体文件（同一字族的 Regular 与 Bold），放进 assets。

**步骤**：

```
A. FontLoader('TestFam') 加载两个文件 → layout 同一段文字，weight 400 与 700
B. 分别用 FontLoader('TestFam400') / ('TestFam700') 各注册一个 → 同样两段
C. 把 A 与 B 的渲染结果栅格化，逐像素比较：
   若 A(700) ≈ B(700) 且 A(400) ≈ B(400) → 引擎按 weight 选对了
```

**记录字段**：两组渲染的像素差比例（`compare_web_screenshots` 类工具或 `toImage()` 后比较）。

**判定**：A 与 B 的差异 < 1% 像素 → 方案 A 可用；否则走方案 B（按字重拆 family 名，§68.2）。

### 79.3 S1 行高模型

**要回答**：`TextPainter` 给出的行高/基线能否稳定复现 CSS 的行高模型。

**准备**：三组参数（fontSize × lineHeight）：`16×1.5`、`20×1.2`、`28×2.0`；每组建一个含中英混排的 3 行段落。

**步骤**：

```
1. painter.layout(maxWidth: 固定)
2. 取 computeLineMetrics() 的 height 与 baseline
3. 与公式比对：
     行高 = fontSize * lineHeight
     baseline = 行顶 + (行高 - ascent - descent) / 2 + ascent
```

**判定**：误差 < 0.5 逻辑像素。超差则自建行高计算，只用 `TextPainter` 取行宽（§8.2 后备方案）。

**实测（2026-10-22）**：通过。`height` 误差 0；`leadingDistribution: even` 时基线误差最大 0.0000067px，默认 `proportional` 最大 4.745px。结论与实现约定见 `方案/spike/s1-result.md` 与 §61.1。

### 79.4 S2 行段落构建耗时

**要回答**：每行构造一个 `ui.Paragraph` 并缓存，一页 30～90 个段落的构建耗时是否可接受。

**准备**：模拟一页文本（30 行 × 每行 40 字，其中 20% 的行含行内样式切换）。

**步骤**：

```
for i in 0..30:
    ParagraphBuilder + pushStyle + addText + build
计时：总耗时 / 30 = 单行均值；× 90 = 一页上界
再测「命中缓存直接复用」的耗时（应接近 0）
```

**判定**：单页构建 < 8ms，翻页命中缓存 < 4ms。超差则合并为整页单段落（§64.2 后备方案）。

### 79.5 S3 字距对齐精度

**要回答**：给行内 CJK 加 `letterSpacing` 做两端对齐，行宽误差与字形重叠风险。

**准备**：一行 20 个汉字，16 号字下自然宽 320；目标宽取 `320 / 336 / 400` 三组；另加一组中英混排样本验证 gap 规则。

**步骤**：

```
1. 不带 letterSpacing 测量行宽 W0（本实验 320）
2. 取可分配 gap 索引（跳过换行、跳过两侧都是拉丁字母/数字的间隙）
3. 整行方案：ls = (target - W0) / 字符数，整段套 letterSpacing
   gap 方案：ls = (target - W0) / gap 数，给每个 gap 左侧字符加单字符 SpanStyle
4. 记录 |LineMetrics.width - target|、字框重叠、末字位置
```

**判定**：误差 < 1px、无重叠。超差则走逐字自绘（§8.4 后备）。

**实测（2026-10-22）**：通过。整行与 gap 方案宽误差均 < 0.001px，字框重叠 0；gap 方案把整行方案末字后的一个 `ls` 移入字符间隙，末字起点更靠右。`TextAlign.justify` 单独对纯中文不生效。细节见 `方案/spike/s3-result.md` 与 §8.4。

### 79.6 其他两个小实验

顺带在 M0 做掉，成本很低但影响设计：

| 实验 | 要回答 | 做法 |
|---|---|---|
| S6 | SQLite 是否启用 FTS5 | `PRAGMA compile_options` 或建一张 FTS5 虚表，失败即不支持（§66.7） |
| S7 | `ui.Image` 解码的目标宽度是否生效 | `instantiateImageCodec(targetWidth: 800)` 后检查 `image.width`，验证省内存的前提（§50.3） |

1. **一次只改一个变量**：字体、字号、宽度分开测，混在一起测出来的数没法解释。

4. **一个人做核心链路**：分页器 + 行分割 + 绘制是一条强耦合的链，拆给两个人协调成本大于收益。

### 81.8 遍历时的不变量

任何持有这些结构的代码都应满足：

1. `EpubNode.cfi` 一旦设定不再变（布局不新建 CFI，只 `copyWithSide`）
2. `readingOrder` 在同一 `PageSlice` 内严格递增且无重复
3. `LineBox` 覆盖全文且不重叠：`lines[i].end == lines[i+1].start`
4. `BlockSlice` 的 `clipTop < clipBottom`，且 `clipBottom - clipTop` 不超过块真实高度
5. `ComputedStyle` 全部字段是**最终值**，不含单位、不含 `auto`
6. `Locator` 与 `EpubCfi` 可互相转换，转换结果对同一位置稳定

第 5 条是最容易违反的：一个 `CssLength` 混进布局层，后面所有计算都要带着单位判断，很快失控。

## 82. 其他参考项目可借鉴项

前面 81 章主要参考阅微（唯一做到"HTML/CSS → 排版树 → 行级分页 → 自绘"的移动端实现）。工作区另外四个开源项目各有可取之处，也有明确的反面教材；Reeden 2.0.0 逆向分析作为**规格级补充**单列 §82.7，证据索引见 §2.2。

### 82.1 flutter_readium：值得采纳的三点

它封装的是 Readium 官方 toolkit（Flutter 侧是原生视图，内部由 WebView 排版），架构无法照搬，但**模型层是行业标准**，比自己设计更可靠。

**① Locator 的多锚点模型（建议采纳）**

```dart
Locator(
  href: '/OEBPS/chapter1.xhtml',
  type: 'application/xhtml+xml',
  title: 'Chapter 1',
  locations: Locations(
    progression: 0.42,        // 资源内比例
    totalProgression: 0.07,   // 全书比例
    position: 14,             // 页序号（若有）
    cssSelector: '#p42',      // 元素锚点
    fragments: ['page=42'],
  ),
  text: LocatorText(
    before: '...', highlight: '被标亮的文本', after: '...',
  ),
)
```

对比我们现在的设计：CFI 唯一坐标 + 一个 `quote` 兜底（§30.2）。Readium 的模型多三个锚点：

| 锚点 | 作用 | 我们现状 |
|---|---|---|
| `cssSelector` / 元素 id | 结构漂移时按元素找 | 无（CFI 的 id 断言部分覆盖） |
| `progression` / `totalProgression` | 比例兜底，最稳 | 无（只在进度条用） |
| `text.before/highlight/after` | 文本重定位，带上下文 | 只有 `quote`，没前后文 |

**为什么值得改**：`docs/plans/locator-field-priority.md` 记录了一个真实事故——同一个 Locator，Android 按 `cssSelector` → `fragments` → `progression` 解析，iOS 完全忽略 `cssSelector` 只认 `fragments.first`，结果**只带 cssSelector 的锚点在 iOS 上跳到章首**。

教训不是"某个平台有 bug"，而是：**保存位置时必须写多个锚点，让消费方按自己的能力选**。我们的 CFI + quote 只有两级，且 CFI 一旦解析失败只剩文本搜索（慢、可能多命中）。建议升级为：

```dart
class Position {
  final EpubCfi cfi;              // 主锚点
  final String? elementId;        // 元素 id（可用时）
  final double? chapterProgress;  // 章内比例，兜底
  final String quote;             // 被标亮文本
  final String? before, after;    // 各 20 字上下文
}
```

**② 装饰（Decoration）模型（部分采纳）**

```dart
ReaderDecoration(id, locator, style: (DecorationStyle.highlight | underline, tint))
```

它只有两种样式（背景高亮、下划线）加一个 tint，简单到极致。我们的 `Annotation`（§81.6）已有 4 种样式 + 颜色 + 笔记 + 时间戳，比它丰富，**不需要改**。

但有一个我们缺的概念：**active 状态**（`decoration-active-flag`）。用户点中某条高亮时，它要能"浮起来"以区别于其他高亮。建议在 `Annotation` 上加 `active` 的**运行期状态**（不入库），而不是每条都存一个布尔。

**③ 错误码体系（建议采纳）**

`ReadiumErrorCode` 的做法：

```
code（wire 字符串，跨平台一致）
  × category（opening / audioStream / tts / navigator / unknown）
  × isFatal | isInformational
  + details.reason（细分原因，不进 wire code）
```

关键设计：**只有"客户端会因此分支处理"的差异才升为 code，更细的原因放 `details.reason`**。我们目前错误处理散在 §55.3（导入）、§69.7（TTS）、§71.5（异常兜底），只有文案没有码，导致：埋点难归类、客服反馈无法定位、同类错误不同页面文案不一致。

建议补一套（§82.4）。

### 82.2 epub_viewer_pro：一个反面教材与一点可用

**反面教材：笔迹用页面坐标**

```dart
class DrawingStroke { List<DrawPoint> points; ... }   // points 是 (x, y) 页面坐标
class TextNote { double x, y; ... }
```

在**可重排** EPUB 里用页面坐标存标注，字号一变、屏一转，笔迹和笔记就飘到别的段落上。它这么做是因为底子是 widget 渲染（`flutter_widget_from_html`），拿不到稳定的文本锚点。

我们自绘引擎本来就有 CFI 与字符偏移，**永远不要用页面坐标存任何持久化数据**。页面坐标只允许存在于「当前帧的渲染中间态」。

（`TextNote` 也一样：它用 x/y 定位，等价于把标注绑死在某一版式上。）

**可用的一点：`ReaderSelectionGuard` 的思路**

widget 方案下原生选择菜单会与自定义工具条打架，它的解法是"抑制下一次 context menu + 定时重置"。我们自绘选区没有这个问题，但「抑制系统菜单」这个需求在长按图片、长按链接时仍会出现。

**另一个可用点：AnnotationType 的枚举划分**（pen / highlighter / note / eraser）。"橡皮擦"提示我们：如果将来做笔迹，删除应该是独立交互而不是逐条点选。

### 82.3 katbook_epub_reader：粒度思路可用，排版内核不可用

它的 `ReadingPosition`：

```dart
chapterIndex + paragraphIndex + totalParagraphs + paragraphOffset(0~1)
进度 = (paragraphIndex + paragraphOffset) / totalParagraphs
```

**可用点 1**：段落级粒度。我们按字符偏移算进度（§76.1），精度更高但要维护"偏移→节点"映射。段落级的好处是导入期只要数段落数，不必逐节点建表——**如果将来导入性能不达标，可以先用段落级进度过渡**。

**可用点 2**：它的分页确实是原生测量（`book_page_view.dart` 用 `TextPainter` 预测量段落高度后装页，再交给 `PageView`），是开源侧最接近我们测量路径的最小样例；可以作为 M0 分页器的对照实现读一遍。

**不可用**：它的渲染是把每个元素转成原生 Widget（§2 的表），CSS 只用正则拆内联样式（`css_parser.dart`），没有选择器匹配、层叠与继承，无法支撑 §23 的 91 项属性；章节解析也只做扁平结构。排版内核不能参考它，`TableOfContents` 的层级处理与图片提取有一点罗列价值。

### 82.4 补上错误码体系（采纳 Readium 的分类思路）

```dart
enum ErrorCategory { opening, layout, resource, annotation, tts, io, unknown }
enum ErrorSeverity { fatal, recoverable, informational }

class EpubError {
  final String code;            // 稳定字符串，跨版本不变，如 'opening.opfMissing'
  final ErrorCategory category;
  final ErrorSeverity severity;
  final String message;         // 用户可读（中文本地化）
  final Map<String, Object?> detail;   // 细分原因，不参与分支
  final String? bookId;
}
```

错误码表（按现有章节的降级点整理，全部来自已写内容）：

| code | 分类 | 严重度 | 触发 | 出处 |
|---|---|---|---|---|
| `opening.notZip` | opening | fatal | 不是 ZIP | §55.3 |
| `opening.containerMissing` | opening | fatal | 缺 container.xml | §55.3 |
| `opening.opfMissing` | opening | fatal | OPF 不存在 | §55.3 |
| `opening.spineEmpty` | opening | fatal | 无 spine | §55.3 |
| `opening.contentUnparsable` | opening | fatal | 全部 XHTML 解析失败 | §55.3 |
| `layout.layoutAborted` | layout | recoverable | 分页被取消/异常 | §71.5 |
| `layout.pageRenderFailed` | layout | recoverable | 单页绘制异常 | §71.5 |
| `resource.missing` | resource | recoverable | 资源找不到 | §54.3 |
| `resource.decodeFailed` | resource | recoverable | 图片/字体解码失败 | §50.2 |
| `resource.fontUnsupported` | resource | informational | ttc/woff 不支持 | §68.6 |
| `resource.fontObfuscationFailed` | resource | recoverable | 解混淆失败 | §5.3 |
| `annotation.relocateFailed` | annotation | informational | CFI 失效且文本搜索无果 | §30.4 |
| `annotation.storeFailed` | annotation | recoverable | 写库失败 | §30.2 |
| `tts.noEngine` | tts | fatal | 无 TTS 引擎 | §69.7 |
| `tts.languageMissing` | tts | fatal | 缺语音包 | §69.7 |
| `tts.utteranceFailed` | tts | recoverable | 单句合成失败 | §69.7 |

三条纪律（来自 Readium 的做法）：

1. **code 稳定、不随文案变**：本地化只改 `message`，`code` 永远不动。
2. **只有需要分支处理的才升为 code**，其余进 `detail`，否则码表会膨胀到没人看。
3. **informational 不等于没事**：`resource.fontUnsupported` 要显示在书籍详情里（§68.6），只是不弹窗。
