## 0. 使用说明

### 0.1 文档定位

本文件是 [技术方案.md](技术方案.md) 的执行层。设计章讲「为什么」，实现规格章讲「怎么写」，本文件讲「谁在什么顺序做、做完怎么验」。两者冲突时以技术方案为准，并回来修任务。

### 0.2 编号规则

- 任务编号 `P<阶段>-<序号>`：阶段 0～6，序号 01～99 连续不跳号。
- 模块编号 `P<阶段>.<模块>` 只是分组，不参与任务编号。
- 依赖只写任务编号，且必须指向更早的阶段或更小的序号，保证无环。

### 0.3 字段口径

| 字段 | 要求 |
|---|---|
| 目标 | 一句话说清完成什么能力，不写实现过程 |
| 产出 | 必须落到具体文件路径、测试名或文档位置 |
| 依赖 | 无依赖写「无」，有依赖列编号 |
| 验收 | 可执行、可观察：命令、样本名、阈值、页面范围，禁止「功能正常」 |
| 工时 | 单人净工时，1～10h，不含等待与评审 |
| 参考 | 1～2 条，名称 + 可访问链接 + 用途；官方文档优先，开源参考注明借鉴点 |

### 0.4 勾选与进度维护（必须遵守）

1. **任务**：完成后把任务正文的 `- [ ]` 改为 `- [x]`。
2. **任务总览表**：由脚本同步，不手工改。勾选任务正文后运行 `perl tool/render_plan.pl`，§2 的「状态」列会自动更新；GitHub 表格不渲染可点击复选框，状态是字面标记。
3. **里程碑**：阶段内全部任务勾选、且该阶段真机记录齐全后，勾选 §1.2 对应条目。
4. **进度看板**：同一次脚本运行会重算 §1.1 的完成数、工时与百分比，并校验 200 项、字段、依赖与工时合计。禁止手工改这些数字。
5. **打包类任务**：必须先有真机记录（`方案/验收记录/`）再勾选，禁止只跑通模拟器就勾选。
6. 每次只勾选本次实际完成的任务，与代码提交同批更新，不提前勾选、不批量勾选。

### 0.5 工时口径

按「熟悉 Flutter 与文本排版的单人」计，合计 640h（80 人日）。与技术方案 §80 的 63 人日（504h）差异来自本文件额外拆出了打包、真机验证、发布准备与风险缓冲，逐阶段对照见附录 C。

### 0.6 真机验证口径

凡标注「⚠️ 打包 APK 并在真机测试」的任务，交付物必须包含一条真机记录：设备型号、Android 版本、Flutter/Dart 版本、构建命令、覆盖场景、通过项、问题清单、日志与截图路径。模板见 [验收记录/真机测试模板.md](验收记录/真机测试模板.md)。

### C.3 完成定义（DoD）

一个任务算完成，必须同时满足：

1. 产出物已合入且通过 CI；
2. 验收标准有可复现的证据（测试输出、快照、记录文档）；
3. 任务正文与里程碑已勾选；
4. 打包类任务附真机记录；
5. 未解决的已知问题写入交付说明，不藏在代码注释里。
