## 1. P0 任务记录

### P0-01 建立多包仓库骨架（4h）

- **状态**：已完成（2026-10-22）
- **做了什么**：用 `flutter create` 建出 `packages/reader_core`、`packages/reader_ui`、`apps/reader_mobile`（android/ios/macos）；配置包间 path 依赖；应用壳改为空白页并引用两个包；新增根 README、`.gitignore` 规则与统一脚本 `tool/run_all.sh`。
- **过程**：
  1. `flutter create --template=package --project-name reader_core packages/reader_core`，同法建 reader_ui。
  2. `flutter create --template=app --project-name reader_mobile --org com.spectacular --platforms=android,ios,macos apps/reader_mobile`。
  3. reader_ui 依赖 reader_core，app 依赖两者（相对路径）。
  4. 替换模板计数器页面为空白 `Scaffold`，启动时断言两个包的标识常量，确保依赖真的连通。
  5. 编写 `tool/run_all.sh` 串行执行三个包的 `pub get → analyze → test`。
- **结果/验证**：
  - `bash tool/run_all.sh` → 三个包 analyze 均 `No issues found!`，3 个测试全部通过，输出 `全部通过：3 个包`。
  - `flutter run -d macos --debug` → `✓ Built .../reader_mobile.app`，VM Service 启动（`http://127.0.0.1:51964/...`）；当前无图形会话，未能截屏，前台激活报警 `Failed to foreground app`。
- **结论**：骨架可用，依赖链路连通；移动端构建需先接受 Android licenses（见 §3 风险），macOS 可作为桌面预览目标。
- **来源**：
  - https://docs.flutter.dev/packages-and-plugins/developing-packages —— 多包目录与 path 依赖写法。
  - https://dart.dev/tools/pub/package-layout —— 包目录规范。
  - 本地命令输出（见上）。

### P0-02 配置严格静态检查（2h）

- **状态**：已完成（2026-10-22）
- **做了什么**：新增根 `analysis_options.yaml`，开启 `strict-casts` / `strict-inference` / `strict-raw-types`，启用 5 条 lint，并把 6 类严格诊断提升为 error；三个包的 `analysis_options.yaml` 通过相对路径继承根配置。
- **过程**：
  1. 根配置 `include: package:flutter_lints/flutter.yaml`，补充 analyzer 严格选项与 linter 规则。
  2. 三个包的配置改为 `include: ../../analysis_options.yaml`；Flutter CLI 首次 analyze 时自动追加 `analyzer.exclude: build/**`（app 另加 android/ios/macos），保留该自动写入（C-01）。
  3. 编写 `tests/analysis/verify_strict_flags.sh`：动态写入探针文件，验证集合类型推断与 `dynamic` 隐式转换都会让 analyze 失败，结束后清理。
- **结果/验证**：
  - `bash tool/run_all.sh` → 三个包 `No issues found!`，测试全过。
  - `bash tests/analysis/verify_strict_flags.sh` → `通过：strict-inference 与 strict-casts 均按错误级别生效（analyze 退出码非 0）`，退出码 0。
  - 手工探针：`final list = [];` → `inference_failure_on_collection_literal`，analyze 退出码 1；`dynamic → int` 隐式赋值 → `invalid_assignment`，退出码 1。
- **结论**：严格规则以 error 级别生效，后续任务新增的隐式类型问题会直接让 CI 失败。
- **来源**：
  - https://dart.dev/tools/analysis —— `strict-*` 与 analyzer errors 配置。
  - https://dart.dev/tools/linter-rules —— lint 规则说明。

### P0-03 实现 reader_core 依赖边界检查（3h）

- **状态**：已完成（2026-10-22）
- **做了什么**：新增 `tool/check_core_boundary.sh`，同时检查源码 import 与 `pubspec.yaml` 依赖，禁止平台插件/宿主包进入 `reader_core`；新增 `tests/tool/verify_core_boundary.sh` 覆盖正常、import 违规、pubspec 违规三条路径。
- **过程**：
  1. 以《技术方案》§59.2 的禁止清单为基础，补充 `shared_preferences`、`sqflite`、`image_picker` 等常用宿主包，共 18 项。
  2. 脚本支持 `CORE_LIB` / `CORE_PUBSPEC` 环境变量，便于测试夹具替换路径。
  3. 测试脚本先验证正常通过，再注入 `package:path_provider` 的 import 和 `path_provider` 依赖，分别断言脚本失败并输出中文原因。
- **结果/验证**：
  - `bash tool/check_core_boundary.sh` → `通过：reader_core 无平台插件/宿主包依赖`，退出码 0。
  - `bash tests/tool/verify_core_boundary.sh` → 三项全部通过，退出码 0；负例分别命中「不得 import」「不得依赖：path_provider」。
- **结论**：边界检查可本地与 CI 复用；当前 `reader_core` 只有 Flutter SDK 依赖，无违规。
- **来源**：
  - 技术方案 §59.2（本地文档）：禁止清单与 CI 检查原型。
  - https://docs.flutter.dev/packages-and-plugins/using-packages —— 插件包与普通包的区别。

### P0-04 搭建 CI 流水线（4h）

- **状态**：已完成（2026-10-22）
- **做了什么**：新增 `.github/workflows/ci.yml`，在 push/main 与 PR 上执行格式检查、`reader_core` 边界检查、三个包的 pub get/analyze/test；启用 flutter-action 缓存与并发取消。
- **过程**：
  1. 固定 Flutter 3.47.5 stable，使用 `subosito/flutter-action@v2` 的 cache。
  2. 先跑 `dart format --set-exit-if-changed`，再跑边界脚本，最后 `tool/run_all.sh`。
  3. 本地用等价命令逐条验证；用 Ruby 解析 YAML 排除语法错误。
- **结果/验证**：
  - `dart format --output=none --set-exit-if-changed ...` → `Formatted 6 files (0 changed)`，退出码 0。
  - `bash tool/check_core_boundary.sh` → 通过。
  - `bash tool/run_all.sh` → 三包 analyze/test 全过。
  - `ruby -ryaml -e 'YAML.load_file(".github/workflows/ci.yml")'` → 解析成功。
  - 推送后 GitHub Actions 真实运行结果见 §2 更新记录（C-03 说明本地无法完全复现红绿与缓存）。
- **结论**：CI 配置具备可执行性；真实红绿以 GitHub run 为准，已推送触发。
- **来源**：
  - https://github.com/subosito/flutter-action —— Flutter 安装与缓存 action。
  - https://docs.github.com/actions —— workflow 语法与并发控制。
