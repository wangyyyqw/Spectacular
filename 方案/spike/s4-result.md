# S4 中文避头尾（禁则）实验结果

> 实验日期：2026-10-22　执行人：Lead
> 对应方案：§15 / §79.1，判定口径见 §15 与 §79.7

## 1. 结论

**走引擎断行，不自建断行器。**

- Flutter 的 `TextPainter`（SkParagraph）在本轮 10 个场景中，**行首禁标点、行首禁后括号/后引号、行尾禁前括号/前引号、数字串不拆、破折号不断在中间** 全部符合预期。
- 唯一不符合：`「……」` 在**恰好 2 个字宽**时，被拆成 `「…` / `…」`；≥3 字宽时不拆。
- 按 §79.1 的“任一不符合即不通过”严格口径，S4 记为**不通过**；但失败只出现在 2em 这一极端宽度，且 1em 时任何实现都无法避免拆分。为一个边缘场景引入约 1200 行自建断行器，收益不成立。
- 因此实际决策为**条件通过**：采用引擎断行，把“省略号对在 2em 宽拆分”列为已知缺陷，用宽度下限（正文内容宽 ≥ 3em）兜底；若产品验收要求 100% 禁则，再回到自建断行器方案。

### 省略号宽度扫描

同一段 `「……」` 在 1～6 字宽下的断行：

```
u=1 -> [「, …, …, 」]        必然拆，无法避免
u=2 -> [「…, …」]            可避免但被拆  ← 唯一问题
u=3 -> [「……, 」]            不拆
u=4..6 -> [「……」]           不拆
```

### 零宽粘合尝试（未采用）

在 `…` 之间插入 U+2060（WORD JOINER）或 U+FEFF（ZWNBSP）后，引擎仍在同一位置断开；两种字符都是零宽，但对 SkParagraph 的断行没有约束力。该方案不可行。

## 4. 对 §61 的落地

- §61.2 的分支取“引擎支持中文禁则”：`TextPainter.computeLineMetrics()` + `getLineBoundary()` 取行边界，只做行高与基线换算（§61.1），不做逐字累积。
- §8.4 的 `letterSpacing` 两端对齐方案保持不变（S3 尚未测）。
- 不进入“自建断行器 + 逐字定位”分支，省掉方案预估的约 1200 行及其绘制改造。
- 新增一条实现约束：**正文内容宽度下限 ≥ 3em**（按当前字号折算），低于此值时排版层给出警告并钳制；同时把它写进 §79.7 的结论备注。
- 若后续产品验收要求省略号 100% 不拆，可加一个局部后处理：检测到“上一行以 `…` 结尾且下一行以 `…` 开头”时，把该段的行宽临时缩 1em 重排该段（不引入全量断行器）。

## 7. 工程口径定稿（P0-12）

> 本节把 S4 的取舍固化为可执行约束，供 P2-01 与后续验收直接引用。技术方案原文不改，冲突与说明见《P0 文档》附录 A-04。

### 7.1 采用方案

- **采用引擎断行**（`TextPainter` / SkParagraph），不引入自建断行器。
- 不启用 `justify` 引擎对齐来补偿禁则；对齐仍走 §8.4 的 gap 方案。
- 不插入 U+2060 / U+FEFF 等零宽字符（实验证明对 SkParagraph 断行无约束力）。

### 7.2 硬性约束

1. 正文内容宽下限 **3em**（基准字号 16px 时为 48px）；低于该值由布局层钳制到 3em，并只记录一次告警（`layout.tooNarrow`）。
2. 验收只在内容宽 ≥3em 时检查禁则；2em 及以下不在验收范围。
3. 已知缺陷登记：`「……」` 在恰好 2em 宽时可能被拆为 `「…` / `…」`；正常宽度（≥3em）不拆。
4. 若产品后续要求 100% 禁则（含 2em），再按技术方案 §15 的后备路径评估自建断行器（约 +1200 行），当前不预留开关。

- **P2-01**：实现断行时按本节执行宽度钳制与告警；验收命令为 `cd 方案/spike/s4_kinsoku && flutter test`（覆盖 10 个场景）加 P2-05 的边界单测。
- **P3-22 / P5-16**：分页与混排不得放宽 3em 下限。
- 检索键：`3em`、`tooNarrow`、`S4 工程口径`、`「……」`。
