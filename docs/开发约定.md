# 开发约定

> 适用仓库：Spectacular Reader。目标是把《技术方案》与《开发方案》落成可审核、可回滚的改动。

## 1. 分支与提交

- 主分支 `main`，始终可构建、可分析、可测试。
- 功能分支命名：`feat/p1-cfi`、`fix/p2-lines`、`docs/p0-handover`；完成后合并回 `main`。
- 一个逻辑变更一个提交；禁止把格式化、重构与功能混在同一提交。
- 暂存只用具体路径，禁止 `git add -A`、`git add .`、`git commit -a`。
- 提交信息模板：

  ```text
  <type>：<一句话概括>

  验证：<命令> → <结果>
  验证：<命令> → <结果>
  ```

  `type` 取 `feat`/`fix`/`refactor`/`perf`/`test`/`docs`/`build`/`chore`/`revert`。复杂变更补「问题」「修复」两段。
- 推送前必须看 `git status` 与 `git diff --staged`；不使用 `--no-verify`。

## 2. 代码与目录

- 包结构：`packages/reader_core`（纯逻辑）、`packages/reader_ui`（视图）、`apps/reader_mobile`（宿主）。
- `reader_core` 禁止平台插件/宿主包，由 `tool/check_core_boundary.sh` 在 CI 强制。
- 公共 API 放 `reader_core/lib/api.dart`；实现类不得跨层暴露。
- 新增依赖前说明用途与替代方案；`reader_core` 新增依赖必须同时更新边界脚本的允许范围（如需）。
- 单文件 ≤500 行，函数 ≤40 行；公共 API 写中文 doc comment。

## 3. 测试

- 跨包脚本、样本校验、集成验证放仓库根 `tests/`。
- 包内单元/组件测试放 `<package>/test/`（`flutter test` 的工具链要求）；测试不与 `lib/` 源码混放。
- 提交前至少执行：

  ```bash
  bash tool/run_all.sh
  bash tool/check_core_boundary.sh
  bash tests/analysis/verify_strict_flags.sh
  bash tests/tool/verify_core_boundary.sh
  ```

- 涉及渲染/分页/解析的行为变更必须有测试或快照；纯文档变更可不跑测试，但要在提交信息里说明。

## 4. 真机与验收

- 真机任务按 `方案/验收记录/真机测试模板.md` 记录：机型、系统、Flutter 版本、构建命令、场景、问题、日志路径。
- 「打包 APK 并在真机测试」的任务，没有记录不得勾选。
- 验收记录放 `方案/验收记录/`，命名 `M{n}-<主题>.md`。

## 5. 任务勾选

1. 在阶段文件把任务正文的 `- [ ]` 改为 `- [x]`。
2. 运行 `perl tool/render_plan.pl` 同步总览、看板与阶段文件进度。
3. 阶段全部完成且真机记录齐全后，勾选主文档 §1.2 的里程碑。
4. 勾选与代码提交同批完成，不提前、不批量勾选。

## 6. 文档与冲突

- 技术方案、开发方案的行文不改；执行中发现冲突或需要补充，在对应阶段文件末尾的「附录」登记：冲突点、处理方式、参考资料、检索键。
- 每次任务完成，在 `方案/交接文档.md` 追加记录：做了什么、过程、结果、结论、来源。
- 引用外部资料必须附链接与用途；优先官方文档。

## 7. 子代理协作

- 子代理只在主代理划定的文件域内工作，禁止执行 git 操作。
- 子代理返回：文件清单、验证命令与真实输出、偏离说明。
- 主代理复核 diff、重跑验证、写交接记录，再提交。
